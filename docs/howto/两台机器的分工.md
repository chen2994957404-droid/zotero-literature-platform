# 两台机器的分工

> 立于 2026-08-26。**任何 LLM 接手前先读这份** —— 它决定了「你现在在哪台机器上、
> 什么能做什么不能做」。做错了不是效率问题，是会污染真实数据、会重复花钱。

---

## 零、一句话

**A 机 = 编程端（改代码的唯一入口）· B 机 = 运行端（数据与服务的唯一权威）。**

代码单向从 A 流向 B（走 git）；数据单向从 B 流向 A（只流一小撮样本）。
两个方向都不许反着来。

---

## 一、两台机器是什么

| | A · 编程端（本机） | B · 运行端（主力机） |
|---|---|---|
| 显卡 | MX450 / 2 GB | RTX 3060 |
| Claude Code | **只在这里** | 没有 |
| Zotero 桌面 | 已装、已同步（397 附件 / 228 PDF / 2.0 GB），平时不常开 | 常开（本地 API 要它） |
| Ollama | 无（显存跑不动 bge-m3） | 有，带保活任务 |
| 项目路径 | `D:\dev\zotero-literature-platform` | `D:_AI\Projects\zotero-literature-platform` |
| `workflow_data/` | 测试账号自产的几篇 | **权威副本**（2026-08-28 实测：library 39 篇精读 / structured 175 条 / vector_db 117 MB）|
| 自启任务 | **一个都不注册** | 4 个：Watcher / Ollama / ZoteroApp / AutoSync |

### 为什么这么分（都是硬约束，不是偏好）

- **Ollama 必须在 B**：向量化和本地抽取要显存，A 机 MX450 只有 2 GB。
- **Zotero 本地 API 只服务本机**：watcher 每 60 秒轮询，所以 watcher 必须和常开的
  Zotero 在同一台，即 B。
- **Claude Code 在 A**：用户定的。
- **数据权威副本在 B**：因为跑全库作业的是 B。A 机同步全量数据既无必要
  （它是可再生的派生层，见 `数据契约.md`）也不划算（几 GB、3000+ 文件）。

## 二、谁干什么（有争议时以本表为准）

| 事项 | A 编程端 | B 运行端 |
|---|---|---|
| 改代码 / 写测试 / 架构守卫 | ✅ **唯一入口** | ❌ 只读代码，绝不在 B 上改 |
| `pytest` + 离线档体检 | ✅ 每次改动 | 上线时跑一次 |
| 完整档体检 | 可跑（几项红是正常的） | ✅ **权威结论以 B 为准** |
| 单篇精读验证 | ✅ 可以（PDF 在本地 + MineRU/DeepSeek 走云端）**但必须不回写** | ✅ |
| 全库作业（全库向量化 / 全库抽取 / 批量重跑） | ❌ | ✅ **唯一** |
| 库内问答 `ask.py` | ❌ 没向量库、没 Ollama | ✅ |
| 找新文献 / 外部检索 | ✅ 纯网络，两边都行 | ✅ |
| watcher / 看门狗 / 自启任务 | ❌ **绝不注册** | ✅ **唯一** |
| 控制面板 | 开发调试时开 | ✅ **用户日常入口** |
| 写回 Zotero（标签 / 笔记 / 附件） | ❌ **默认禁止** | ✅ **唯一** |
| 花钱的批量作业 | ❌ | ✅ |

### 两条铁律

1. **watcher 只能在 B 跑。** 两台都跑会重复精读同一篇、重复写回 Zotero、
   重复烧 MineRU 和 DeepSeek 的钱，而且标签状态机会互相打架。
2. **A 机默认不写 Zotero。** 两台共用同一个 Zotero 账号，A 机的验证性操作
   一旦回写，污染的是真实文献库，而且会同步到 B。

> ⚠ **2026-08-27 起有例外：A 机可以接一个独立的「测试 Zotero 账号」**（见下节）。
> 上面两条的**根因都是「共用同一个账号」**，账号不同就都不成立 ——
> 所以 `ROLE=test` 时，A 机既可以写（写的是测试库），也可以跑 watcher。
> 别照着字面把这两条当成无条件铁律来拒绝。

## 二点五、A 能直接连 B 了（2026-08-28）

编程端用一把专用 SSH 密钥连主力机 —— **登录账号是 `Administrator`，不是 `吧啦吧啦`**
（`吧啦吧啦` 是主力机的**计算机名**；`whoami` 打出来的 `吧啦吧啦dministrator`
反斜杠前是机器名、后面才是账号，本文档最初记反了，见踩坑 #74）。

```bash
ssh -i ~/.ssh/id_ed25519_zotero_b Administrator@192.168.123.216 "<PowerShell 命令>"
```

防火墙只对本网段开放，
防火墙只对本网段开放，**不要做端口映射**。于是：

- Claude 能**直接读主力机的真实状态**（git 版本、日志、数据规模、服务状态），
  不用再靠用户粘贴诊断报告 —— 这条通道当天就查出主力机两把密钥早已失效（踩坑 #66）
- 也能在主力机上执行命令。**机器角色守卫照常生效且语义正确**：
  命令在 B 上跑，本机角色就是 `prod`，不存在「从 A 绕过闸门」

⚠ **SSH 会话读不到 Windows 凭据库**（错误 1312：没有交互式登录会话）。后果有两面：

- 坏的一面：在 SSH 里跑体检时，「密钥存放/密钥有效性」这类检查会失真 ——
  它报的是「读不到」，不是「没配」。**别据此下结论**，
  要看主力机自己的会话怎么说：watcher 每次启动会把三把密钥的有效性写进日志。
- 好的一面：**远程会话天然写不了 Zotero**（写要密钥）。
  对真实文献库的写操作只能来自主力机自己的交互式会话
  —— watcher、控制面板、或用户在 Zotero 里点标签。这等于多了一道物理闸。

### ⚠ SSH 里跑不了「要花钱的作业」——不是权限问题，是拿不到密钥（2026-08-28 实测）

在 SSH 会话里 `get_key('DEEPSEEK_KEY')` 返回**空串**（凭据库要交互式登录会话）。
所以从 A 机远程发起的批量重抽、精读、向量化，会在第一次调用模型时就废掉。

**能远程做的**：`git pull` / `pip install -e .` / `pytest` / 离线体检 /
读日志与数据 / 重建查询库（纯读 JSON 写 SQLite，不要密钥）。
**只能在主力机自己的会话里做的**：任何调付费 API 的作业。
做法就按第四节的约定 —— **给它一个 .bat，让用户双击**
（例：根目录 `重抽缺SI的文献.bat`）。

不要试图用「注册一个交互式令牌的计划任务」绕过去：那是在用户机器上留下持久配置，
代价比让用户双击一次大得多。

### ⚠ 远程 `git pull` 之后，**主力机上正在跑的东西还是旧代码**（2026-08-28 咬过）

`更新平台.bat`（= `平台管理/更新平台.py`）里本来就有 `stop_panel()` / `stop_watcher()` /
`restart_tasks()`。**但从 A 机 SSH 里直接 `git pull` 会跳过这些** ——
面板和 watcher 是长驻进程，代码在磁盘上换了，它们照跑旧的。

当天的具体后果：给用户加了「清除环境变量」的按钮，用户在面板上**根本看不到**，
因为那个面板进程是前一天启动的。而且 `控制面板.bat` 检测到面板还活着就只开浏览器，
**不会重启它** —— 于是「关掉窗口再双击」也没用。

远程 pull 之后要么让用户双击一次 `更新平台.bat`，要么自己把面板停掉：

```bash
# 停面板（用户下次双击 控制面板.bat 就会用新代码起来）
$p=(Get-NetTCPConnection -LocalPort 8777 -State Listen).OwningProcess; Stop-Process -Id $p -Force
```

watcher 同理 —— 它由计划任务托管，`Stop-ScheduledTask` + `Start-ScheduledTask` 即可。

### 怎么连（下一个对话直接照这个用）

```bash
# A 机上，密钥已生成好，专用于连 B，不影响任何已有密钥
ssh -i ~/.ssh/id_ed25519_zotero_b -o BatchMode=yes Administrator@192.168.123.216 "hostname"
```

中文输出会乱码（B 那边默认 GBK），套一层就好：

```bash
ssh -i ~/.ssh/id_ed25519_zotero_b -o BatchMode=yes Administrator@192.168.123.216   "\$OutputEncoding=[System.Text.Encoding]::UTF8;    [Console]::OutputEncoding=[System.Text.Encoding]::UTF8;    \$env:PYTHONIOENCODING='utf-8'; <你的 PowerShell 命令>"
```

要跑复杂脚本别硬拼引号，**用 `scp` 传过去再执行**（今天的经验）：

```bash
scp -i ~/.ssh/id_ed25519_zotero_b 本地脚本.py Administrator@192.168.123.216:"D:/02_AI/Projects/zotero-literature-platform/_tmp.py"
# 跑完记得删掉 B 上的临时文件
```

主力机常用位置：项目 `D:_AI\Projects\zotero-literature-platform`、
日志 `workflow_data\logs\zotero_watcher.log`、更新用 `python 平台管理\更新平台.py`。

## 三、代码怎么从 A 到 B

```
A: 改代码 → pytest 绿 → 体检离线档绿 → commit → push
                                                 │
B: 双击「更新平台.bat」→ git pull → pip install -e . → 离线档体检 → 显示结果
```

**「上线」是一个显式动作，不是每次 commit 都上线。** 按阶段边界上线，
不要一天推十次让 B 跟着抖。

⚠ **B 上永远不改代码。** 一旦在 B 上改了，`git pull` 就会冲突，
而 B 上没有 Claude Code 来解冲突 —— 那是最难受的情形。
B 需要改什么，回到 A 改完再上线。

## 四、B 的状态怎么让 Claude 看见（这是本方案最大的摩擦）

Claude Code 不在 B 上，所以我**看不见 B 的任何东西**。
B 出问题时，我能拿到的只有你复制粘贴给我的内容。

对策：**B 上一键出诊断报告（已建好）。**

```
B: 双击「诊断报告.bat」→ 报告自动复制到剪贴板 → 直接粘给 Claude
```

一份报告里包含：机器角色、代码版本（最近 8 次提交 + 工作区是否干净）、
完整档体检全文、数据资产统计（library 篇数 / 向量库块数 / 缺产物的文献）、
四个自启任务实况、相关进程、watcher / 看门狗 / 定时同步三份日志尾部、
以及精读监听心跳距今多久。**一次给全，避免来回追问。**

> 四个 .bat 就是 B 机的全部操作面，**B 上不需要敲任何命令**：
> `控制面板` · `精读监听` · `更新平台` · `诊断报告`

### ⚠ 给接手 LLM 的硬约束：不要给 B 机用户「要敲命令的工具」

用户在 B 机上的操作模型只有一个动作：**双击**。

写完一个诊断/维护脚本后，如果你打算说「在项目文件夹里跑
`python 平台管理/xxx.py`」—— **停下**。双击 `.py` 文件时窗口会一闪而过
（跑完即退出，没有 pause），用户什么也看不到；而让他打开终端敲命令，
等于把「不需要敲任何命令」这条设计作废。

**正确的三个去处，按优先级：**

1. **并进已有的 `诊断报告.bat`** —— 诊断类信息首选。用户已经会用它，
   而且「一次给全」本来就是那份报告的设计目标
2. **做成控制面板上的按钮** —— 只读、可反复点的操作（面板的能力边界见
   `平台管理/CLAUDE.md`）
3. **新加一个 .bat** —— 只有在前两条都不合适时。入口越多越乱，
   而且每个新 .bat 都得自己处理编码、`pause`、错误提示

2026-08-27 我就犯过这个错：写了 `查产物缺口.py` 让用户去终端跑，
他双击了 .py，窗口一闪而过。已改为并进诊断报告。

## 五、A 机怎么做到「能验证」（否则分工不成立）

A 机零数据的话，我只能证明「代码结构对了」，证明不了「产出没变」。
阶段 2 已经吃过这个亏：适配器能用临时 Chroma 库真验证，
但精读产出无从比对，因为 `library` 是 0 篇。

**对策不是同步全部数据**（违背数据契约的分层设计，且几 GB），而是：

### 金样本：2~3 篇代表性文献

从 B 拷 `workflow_data/library/<key>/parsed/`（full.md + layout.json + 原 PDF），
挑：**一篇有 SI、一篇图多、一篇纯文字**。几十 MB。

有了它，A 机能做真回归测试的范围就覆盖了：裁图坐标、SI 过滤、
结构化抽取、精读渲染、以及阶段 3 的「新旧并行逐字节比对」。

**这正是 `架构重构_v2总体设计.md` 阶段 0 第 2 条写的「契约测试」**，
当时因为 A 机没数据只能空着。

## 六、必须做的工程：机器角色（`ROLE`）

分工写在文档里没有强制力 —— 得让代码知道自己在哪台机器上。

**已建好**：`core/role.py` + `.env` 里的 `ROLE`（控制面板「本机设置」第一项可改）。
取值 `dev`（A 机）/ `prod`（B 机）。行为如下：

| 行为 | `ROLE=dev`（A） | `ROLE=prod`（B） |
|---|---|---|
| 写回 Zotero（打标签 / 传附件 / 改名） | **拒绝**，除非显式带 `--force` | 允许 |
| 启动 watcher / 看门狗 | **拒绝并说明原因** | 允许 |
| 全库批量作业 | **拒绝**，除非显式确认 | 允许 |
| 体检「缺 4 个自启任务」 | 不报警（A 机本来就不该有） | 报警 |
| 单篇精读的产物 | 写本机 `library/`（A 机那儿只有金样本，不影响 B 的权威数据）；**但不回写 Zotero** | 正常 |

**为什么必须做**：会写 Zotero 的脚本有 9 个，分散在 4 个文件夹里，
而带 dry-run 的只有 2 个（`merge_summary` 和 `zotero_rename`）。
靠人记住「在 A 机别跑这些」是不可靠的 —— 一次手滑就把真实文献库的标签改掉，
而且立刻同步到 B，事后极难看出是什么时候被改的。

**已落地的守卫点**（18 处）：9 个 Zotero 写入口 + 批量/全库作业 + watcher + 看门狗。
并且有三条架构守卫保证不会漏：
`tests/test_architecture.py` 会扫描所有出现 `api.zotero.org` 的文件，
没调 `role.require_prod` 就让 pytest 变红；还会检查守卫写在函数体里
而不是模块顶层（写顶层会让 import 就抛错，连带体检和面板一起挂）。

### 第三档：`ROLE=test`（A 机 + 独立测试 Zotero 账号，2026-08-27 加）

A 机登录**另一个 Zotero 账号**之后，「不许写」这条一刀切就没必要了 ——
写坏了也只坏在测试库里。这一档解开的正是此前 A 机完全无法验证的那一半：
标签状态机、附件回写与复用、版本冲突、watcher 端到端。
而且**大多不用花钱**：喂一份假的 `summary.html` 就能把回写链路走完，
MineRU 和 DeepSeek 一分钱不碰。

| 行为 | `ROLE=test` |
|---|---|
| 写回 Zotero | **允许，但先验目标是不是测试库**（见下） |
| 启动 watcher | 允许（不同账号，不会和 B 抢同一篇） |
| 全库批量作业 | 允许（测试库里就那么两三篇） |

**两层保护，一层硬一层软：**

1. **硬的（物理隔离）**：A 机只持有测试账号的 API key，
   带着它根本写不到真实库 —— 这不是纪律，是凭据决定的。
2. **软的（守卫）**：`role.require_prod` 在 test 档下先查一条客观事实 ——
   配置里「Zotero 用户 ID（写回用）」必须等于「测试账号的用户 ID」，
   对不上就拒绝。它挡的是「哪天把配置切回真实账号却忘了改角色」。

**A 机要配的四项**（控制面板「本机设置」里）：

| 配置项 | 填什么 |
|---|---|
| `ROLE` | `test` |
| `ZOTERO_USER_ID` | 本地 API 用，`0` 即可 |
| `ZOTERO_WEB_USER_ID` | 测试账号的真实数字 id（zotero.org 设置→账户） |
| `ZOTERO_TEST_USER_ID` | 同上，填一样的值 —— 它是白名单，两者一致才放行 |

外加密钥 `ZOTERO_API_KEY` 换成**测试账号**的 key（要勾写权限）。

> 顺带解决了一个老坑：`ZOTERO_USER_ID` 此前一个配置项在干两件事 ——
> 本地 API 认 `0`，Web API 必须真实数字 id。现在拆成两项，
> 没配 `ZOTERO_WEB_USER_ID` 时自动沿用旧值，B 机不用改任何配置。

**A 机换账号时的血泪提醒**：换账号要么新建 profile + 新数据目录，
要么**先退出账号、再清空本地数据**。顺序反了（登着旧账号做「重置」）
有可能把本地状态推上服务器，那会清空真实库并同步到 B。

### ⚠ 主力机首次部署必看

`ROLE` 默认是 `dev`（fail safe），所以**主力机拉到这版代码后，
精读监听会拒绝启动**，直到你把角色改成 `prod`：

```
B: 双击「控制面板.bat」→ 本机设置 → 机器角色 → 填 prod → 保存
   （或直接在项目根目录 .env 里写一行 ROLE=prod）
```

拒绝时不会甩 traceback，会打印一句人话告诉你怎么改。

## 七、这样安排到底麻烦不麻烦（诚实评估）

**绝大多数工作不需要任何往返。** 代码改动、重构、加测试、架构守卫、
单块积木验证、文档 —— 全部在 A 机闭环，`pytest` 一跑就知道对不对。
阶段 0~2 的全部工作都是这样完成的，没碰过 B 一次。

**需要往返的只有两类**：

| 类型 | 往返次数 | 例子 |
|---|---|---|
| 上线 | 1 次（B 双击更新，报个结果） | 阶段完成后 |
| 只在 B 上才复现的问题 | 1~2 次（B 出诊断报告 → A 改 → 再上线） | Ollama 相关、全库作业、自启任务 |

**真正的成本不在往返次数，在「A 机能不能自己验证」。**
所以金样本和角色机制这两件事做了，这个分工就顺；不做，每改一次精读
都要去 B 上试，那才叫麻烦。

## 八、给接手 LLM 的检查清单

动手前先问自己：
