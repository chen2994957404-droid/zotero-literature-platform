# 演进规划与模块地图 · Roadmap & Module Map

> **这份文档是项目的总纲，任何 LLM/人接手时先读它**（再读 架构总览 / 数据契约 / 变更记录 / 踩坑记录）。
> 目的：解决「接手得啃全部代码」的痛点——读这一份就知道项目分几块、各块干什么、怎么演进。
>
> 背景：本平台由不懂编程的研究者主导，长期靠 LLM 维护。因此可维护性 =
> 「LLM 能多快看懂、多安全地改」，而非传统人力工程。设计一切以此为纲。

---

## 一、模块地图（当前 26 个脚本，自然聚成 6 组）

依赖其实很浅：多数脚本是独立小工具，真正耦合只在少数几处（extract_* 复用
extract_structured 的 SCHEMA；watcher 调 deepread/mineru/extract）。

| 模块 | 职责 | 脚本 | 对外能力（未来 MCP 化的候选接口） |
|------|------|------|-----------------------------------|
| **① Zotero 接口层** | 读写 Zotero 库/附件/标签/正文 | zotero_watcher, zotero_upload_attachment, zotero_rename, zotero_add_thesis, autotag, tag_to_nested | find_pdf(key)、upload_summary(key,html)、get_fulltext(key)、swap_tag |
| **② 解析层** | PDF → 结构化 full.md + 图坐标 | mineru_parse | parse_pdf(pdf) → parsed/ |
| **③ 精读线** | 文献 → 中文图文精读 HTML | deepread_v4, deepread_batch, rerun_pro | deepread(key) → summary.html |
| **④ 向量问答线** | 全库 → 向量库 → RAG 问答 | vectorize, vectorize_library, ask, brainstorm | vectorize(key)、ask(question) |
| **⑤ 结构化抽取线** | 文献 → 对齐字段 JSON → 对比表 | extract_structured(精层), extract_library(粗层), extract_batch, filter_domain | extract(key)、build_compare()、filter_domain |
| **⑥ 库维护工具** | 查文献/去重/补元数据/看门狗 | find_papers, delete_junk, list_junk, backfill_meta, watchdog | 各自独立，按需调 |

**共享地基**：`workflow_data/library/<key>/`（数据契约）是所有模块的交换枢纽——
② 产出 parsed/full.md，③④⑤ 都消费它。谁先跑谁生成，别人复用（见数据契约）。

## 二、分阶段演进路线（用户定：两者都要，分阶段）

### 阶段 0（现状）：脚本堆 + docs 雏形
能用，但逻辑散在脚本里，靠读代码理解。已有 数据契约/架构总览 是好基础。

### 阶段 1（当前该做）：理成「清晰模块 + 契约说明」——不急 MCP
目标：让任何 LLM 读文档就能用某个模块，不必啃全部代码。做法：
1. 每个模块配一份「模块说明书」（干什么·怎么调·输入输出·依赖·已知坑），
   放 `docs/modules/<模块名>.md`。本文件的表格是索引，说明书是详情。
2. 收敛重复逻辑：find_pdf 现有 3 份拷贝（watcher/extract_batch），
   应抽成 ① Zotero 接口层的单一函数，别处 import。（技术债，见下）
3. 每个模块留一个「自测入口」，改动后能一键验证没坏。

### 阶段 2（某条线稳定 + 要接更大系统时）：选择性 MCP 化
不是全包，只包**成熟、会被反复外部调用**的能力。优先级：
- 先包 **⑤ 结构化抽取** 和 **④ 向量问答**（最可能被 agent 串联：找→抽→问）
- **③ 精读** 次之（输出稳定后）
- ① Zotero 接口层作为底层被上面调用，可不单独暴露
判据：这条线「基本不用再改」了，才值得 MCP 化；还在频繁改的先别包（否则给乱摊子加壳）。

### 阶段 3（远期）：agent 编排
当各能力成 MCP 积木后，可让 agent 自动串多步（找文献→精读→抽取→横向分析→提 idea），
或被其他工具调用。这才是「接入更复杂操作」的终点。

## 三、为什么先模块化、后 MCP（关键判断）

- MCP 的价值是「把能力变成 LLM 标准可调的积木」，适合阶段 2-3 的**外部调用/编排**。
- 但 MCP **不解决代码乱**——现在原样包只是给乱摊子加壳，内部照样难维护。
- 且 MCP 有运行成本（跑 server、维护协议）。对「单机自用、靠 LLM 维护」的现状，
  先做零成本的「模块 + 契约文档」收益更高、风险更低。
- 所以顺序是：**先让 LLM 看得懂、改得安全（阶段1），再让能力被标准调用（阶段2）**。

## 四、已知技术债（阶段 1 逐个还）

- **find_pdf 三处拷贝**：zotero_watcher.py 和 extract_batch.py 各有一份，改一处要同步另一处
  （易漏，是隐患）。应抽到 ① Zotero 接口层单一实现。
- **密钥注入脆弱**：deepread key 靠命令行第5参、watcher 靠环境变量继承，易 401
  （踩坑 #17）。工单板有「支持 .env 统一配置」一条（用户自行处理）。
- **schema 硬编码方向**：结构化 SCHEMA 绑定「软物质/动态键」方向，换方向要改代码。
  未来可考虑 schema 配置化（外置成可编辑文件）。
- **无自动化测试**：每次改动靠手工验证。阶段 1 应给每模块加自测入口。

## 五、给接手 LLM 的建议动作

1. 先读本文件 → 定位要动的模块。
2. 读该模块的说明书（`docs/modules/`，阶段1建成后）+ 相关踩坑编号。
3. 改动前看「并发/写入领地」（CLAUDE.md）与「数据契约」，别破坏交换枢纽。
4. 改完当场记 变更记录，新坑记 踩坑记录，新需求记 待办与需求。
