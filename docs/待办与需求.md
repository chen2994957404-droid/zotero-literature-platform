# 待办与需求 · 两侧工单板

> **这是应用侧 ↔ 设计侧之间的需求传递通道。**
> 用户在两个对话间搬运信息：应用侧用平台时发现「需要架构性改动」的问题就记这里，
> 设计侧接手时先扫这份，挑能做的实现，做完改状态。
>
> **和另外两份日志的区别：**
> - `踩坑记录.md` = 已诊断清楚的问题 + 根因 + 解法（知识沉淀）
> - `变更记录.md` = 已经做完的改动（交接流水账）
> - `待办与需求.md`（本文件）= **还没做、需要另一侧处理的事**（工单）
>
> ## 怎么用
> - **应用侧**发现「用不顺、需要改架构」→ 加一条：现象 + 期望 + 提出方 + 状态`待处理`。
>   （小 bug 应用侧自己修并记变更记录即可，不用进这里；这里只放需要设计侧动的。）
> - **设计侧**接手先读本文件 → 实现后把状态改 `已解决`，注明改了哪些文件 / 关联踩坑编号。
> - **用户**是两侧传声筒：把应用侧的诉求带到设计侧对话，让设计侧看这个文件接单。
>
> 格式：`- [状态] 标题 · 现象 · 期望 · 提出方/日期 · (解决说明)`
> 状态取值：`待处理` / `处理中` / `已解决` / `搁置`

## watcher 重复实例（面板发现，2026-08-06）

一天内第二次出现 2 个 zotero_watcher 并存。看门狗 `restart_watcher()` 先 taskkill 再启动，
但仍有漏网 —— 疑似「任务计划自启的那份」与「看门狗启的那份」互不相识。
影响：两份都在轮询，会抢同一篇文献的处理权，可能重复精读/重复上传。
建议解法：给 watcher 加**单实例锁**（启动时抢一个 lock 文件，抢不到就退出），
比让看门狗去杀更可靠 —— 从源头杜绝而不是事后补救。
面板已能一眼看出该问题（重复实例会标红）。
