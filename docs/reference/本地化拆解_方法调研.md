# 本地化拆解 · 专业方法调研（2026-09-20）

> 用户的问题：精读的六处模型调用几乎全落在本地最重的 T3 档，说明还没拆到位。
> 用户的判断：**先搞清最小的、互不依赖的单元和它们之间的联系，再谈用什么模型**，不能凭感觉定大小。
> 本文是查出来的东西，每条带出处；「对我们意味着什么」单独标出。

## 一、把大模型换成小模型的工程方法（NVIDIA，2025）

来源：Belcak 等，*Small Language Models are the Future of Agentic AI*（[arXiv 2506.02153](https://arxiv.org/abs/2506.02153v2)）。

核心论点：agent 里的每次模型调用**只用到模型能力的一个窄面**；把系统拆成「乐高式」的多个专用小模型，
比一个大模型通吃更便宜、更稳、更好调试。三个案例估算：MetaGPT 约 60%、Open Operator 约 40%、Cradle 约 70% 的大模型调用可换成小模型。

它给的六步转换法（S1–S6），照抄：
1. **S1 记录**：把每一次模型调用的输入、输出、耗时都记下来
2. **S2 攒够样本**再脱敏
3. **S3 聚类**：对真实调用做无监督聚类，找出反复出现的「同一种活」—— 这就是候选的专用任务
4. **S4 按任务挑小模型**
5. **S5 用攒下的真实样本微调**（LoRA 之类），可以蒸馏
6. **S6 定期重训**

**对我们意味着什么**：拆分的依据是**真实调用的聚类**，不是拍脑袋按栏目分。我们已经有 S1 的一半（budget 账本记了次数与 token，
但**没记输入输出内容**）—— 补上这一点，跑一批精读，就能按 S3 看出「同一种活」究竟有几种。
S5 微调我们暂时不做，但它提示了一件事：**分栏缓存里攒下的几千对「材料 → 产出」就是现成的训练/校准数据**。

## 二、把「说什么」和「怎么说」分开（NLG 流水线，Reiter & Dale）

来源：Reiter & Dale 的经典 NLG 架构（[Reiter, *Natural Language Generation*, Springer 2025](https://www.cambridge.org/core/journals/natural-language-processing/article/natural-language-generation-by-ehud-reiter-springer-2025-isbn-9783031685811-hb-5719-isbn-9783031685842-pb-5719-and-isbn-9783031685828-ebook-3999-xiii202-pages-66-bw-illustrations-doi-httpsdoiorg1010079783031685828/C39D19C6C3C98E8AE3C944DA66D12406)；
[综述](https://arxiv.org/pdf/1906.00500)）。文本生成分三段六步：

| 段 | 步 | 干什么 |
|---|---|---|
| 文档规划 | 内容确定 | **说什么**：从数据里挑出要讲的信息单元 |
| | 文档结构 | 单元按什么顺序、归哪一节 |
| 微规划 | 词汇化 / 指代 / 聚合 | 单元怎么合并成句、用什么词、怎么指代 |
| 实现 | 表层实现 | 写成最终文字 |

**对我们意味着什么**：精读本质上是 **data-to-text** —— 把一篇论文里的信息单元按范式重新写一遍。
现在的做法是把「说什么」和「怎么说」揉在一次调用里让模型同时干，所以每一步都需要最强的模型。
按这个架构拆开：**内容确定 + 文档结构是抽取和分类（脚本 + 小模型能做）；只有最后「写成中文段落」才是写作**。
写作那一步拿到的是已经选好、排好序的单元清单，任务变成「照清单成文」，难度大幅下降 —— 这正是清单先行奏效的原因，只是现在清单里只有数字。

## 三、「最小单元」在文献这个领域长什么样（四条线的定义）

用户问的「能拆到多小、最小的没联系的单元」，学界在四个方向上各自定义过：

| 线 | 单元 | 出处 |
|---|---|---|
| 事实核查 | **原子事实（atomic fact）**：一句话拆成若干条各自可独立验证的最小陈述，逐条对证据判真假 | FActScore（[decompose-then-verify](https://www.emergentmind.com/topics/factscore-113e12f4-d246-433f-8289-063e105dc511)）；后续 [DnDScore](https://arxiv.org/pdf/2412.13175)、[Optimizing Decomposition](https://arxiv.org/pdf/2503.15354) 讨论怎么拆才最利于验证 |
| 摘要评价 | **内容单元（SCU）**：一份摘要拆成「一个事实一条」的短句；候选摘要覆盖了几条就得几分；可用 NLI 小模型自动判 | Pyramid 方法（[SCU 综述 2024](https://arxiv.org/abs/2404.01701)），Lite³Pyramid 用语义三元组近似 |
| 材料合成 | **合成动作（action）**：一步 = 动作 + 物料 + 量 + 条件 + 顺序，串成动作图；ULSA 给了统一动作词表 | Kononova 等 [文本挖掘 2 万条无机合成配方](https://www.nature.com/articles/s41597-019-0224-1)；[ULSA](https://arxiv.org/pdf/2201.09329) |
| 化学信息抽取 | **性质元组**：(化合物 / 样品, 性质, 数值, 单位, 条件)，逐句抽 | ChemDataExtractor（见 [材料文本挖掘论文集](https://github.com/hhaoyan/awesome-textmining-materials-science)）|

另外，专用小验证器的证据：Bespoke-MiniCheck-7B 这种 7B 级的事实核查模型在聚合基准上达到 SOTA（[VeriFastScore](https://arxiv.org/pdf/2505.16973) 引述）——
**「这句原文支不支持」这种判断，7B 够用是有实证的**；我们本地 T3 判得差，说明问题在给它的材料和一批的量，不在模型档位。

**对我们意味着什么**：一篇文献的**基本单元不是「栏目」**，是下面这些（每一类都能单独抽、单独验、单独存）：

1. **实体**：材料 / 样品编号 / 缩写与全称（我们已有术语表，T0）
2. **性质事实**：(样品, 性质, 值, 单位, 条件, 出处位置)（我们已有表格扫描 + chunk_pass，T0 + T1）
3. **合成动作**：(动作, 物料, 量, 条件, 顺序, 目标产物)（**没有**，现在让模型直接写成段落）
4. **图面板单元**：(图号, 子图, 画的是什么, 关键数值)（**没有**，藏在索引段里）
5. **主张**：作者说这项工作做到了什么、机理是什么（**没有**，藏在导读/总之里）
6. **角色关系**：组分 → 作用（**没有**，Q1 让模型现推）
7. **因果关系**：结构/设计 → 性能（**没有**，Q2 让模型现推）

精读的每一栏都是这些单元的组合：导读 = 主张 + 关键性质事实；实验 = 实体 + 合成动作 + 表征方法；
Q1 = 角色关系；每图两段 = 图面板单元 + 该图的性质事实 + 相关主张；Q2 = 因果关系；总之 = 主张。
**单元之间的依赖**：3、4 只依赖原文；5 依赖 2、4（主张要有数据撑）；6、7 依赖 1、2、5。

## 四、便宜的先上、验证器把关（LLM 级联）

来源：FrugalGPT（[arXiv 2305.05176](https://arxiv.org/abs/2305.05176)）。三招：改提示词、近似（缓存/微调）、**级联**——
先问最便宜的模型，用一个**打分器**判答案够不够好，不够才升级到下一档；同质量下成本降 50–98%。打分器本身是个很小的模型（DistilBERT）。

**对我们意味着什么**：我们的 T0 把关（数字在不在原文、格式合形、清单覆盖）就是打分器的雏形；加上一个小 NLI 判「支不支持」，
就能做成「T2 先写 → 打分 → 不过再 T3」，而不是一律 T3。

## 五、工作流的五种形状（Anthropic）

来源：Anthropic *Building Effective Agents*（[模式参考](https://buildingeffectiveagents.com/patterns/)）：
提示链（每步带门控）、路由（先分类再走专用支路）、并行、编排者-工人、评估者-优化者。可组合。

**对我们意味着什么**：精读已经是「提示链 + 评估者-优化者」；缺的是**路由**（先判论文类型再走不同支路）和
把「工人」拆到单元级（一个工人只产一种单元）。

## 六、拆解方法：先建单元清单与依赖图，再定模型（这是用户要的顺序）

综合上面五条，正确的做法不是「感觉这个大小行就试」，而是：

1. **从范文反推单元**：随机取 20 篇高分子学人范文，按第三节的七类把每一句拆成单元（SCU 的做法；先让模型拆、我复核）。
   产出：每篇每类多少个单元、单元的平均长度、哪些单元在原文哪个位置。这就是「基本单元长什么样」的实测答案。
2. **画依赖图**：哪类单元只依赖原文（可并行、可用最小模型）、哪类依赖别的单元（必须排在后面）。
3. **给每类单元定「抽取形状」**：输入窗口多大才够（由单元在原文里的位置分布算，不猜）、输出是封闭标签还是自由文本。
4. **再定档**：封闭标签 + 小窗口 → T1/T2；自由文本 + 需综合 → T3；每一类在同一批样本上量过才定。
5. **写作只在最后一步**：拿单元清单成文（NLG 的「实现」），T3；但因为「说什么」已经定了，可以试 T2。
