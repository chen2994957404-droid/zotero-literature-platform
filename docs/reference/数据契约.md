# 数据契约 · Data Contract

> 这份文档定义 `data/` 里数据的**格式约定**（R6 窗起分五层：
> `raw/` 解析产物 · `curated/` 精读产物 · `serving/` 对比表与向量库 ·
> `state/` 索引 · `logs/`）。这是整个系统的地基：
> 任何工具（现在的精读脚本、未来的向量化、换的新工具）只要遵守这份契约读写数据，
> 就能无缝协作。数据不变，工具随便换、随便升级。

---

## 核心原则

**以 Zotero 文献条目的 key 为单元组织数据。** 每篇文献一个文件夹，文件夹名 = Zotero 里该文献的 item key（8位字母数字，如 `2T6H4S3D`）。这样本地数据和 Zotero 库天然一一对应，永不错位。

---

## 目录结构

```
data/
├── library/                      # 【核心数据区】按文献归档
│   └── <ZoteroItemKey>/          # 一篇文献一个文件夹
│       ├── parsed/               # MineRU 解析结果（原始产物）
│       │   ├── full.md           # ★解析出的全文 Markdown（向量化的主要文本来源）
│       │   ├── layout.json       # ★页面布局+图坐标（精读裁图靠它）
│       │   ├── *_origin.pdf      # 原始 PDF 副本
│       │   ├── *_content_list.json    # 内容块列表
│       │   ├── *_model.json           # 模型识别结果
│       │   └── images/           # 提取的图片（哈希命名的 jpg）
│       ├── summary.html          # ★图文精读成果（带内嵌base64图，可独立打开）
│       └── meta.json             # ★元数据（标题/DOI/日期/生成信息）
├── structured/                   # 【结构化抽取产物】见 结构化抽取说明.md
│   ├── <ZoteroItemKey>.json      # 每篇的对齐字段（source=coarse粗层/无=精层）
│   └── compare.md                # ★全库横向对比表（找idea的载体）
├── logs/                         # 运行日志
└── _incoming/                    # 临时处理区（可清空）
```

标 ★ 的是**下游工具应该依赖的稳定文件**，其余是中间产物。

---

## 关键文件格式

### meta.json（每篇必有的元数据）
```json
{
  "key": "2T6H4S3D",
  "title": "文献标题",
  "DOI": "10.xxxx/xxxxx",
  "date": "2026",
  "model": "deepseek-v4-flash",
  "time": "2026-07-23 16:43"
}
```
- `key` 与文件夹名一致，是文献的唯一标识。
- 向量化/检索时，用它给每个向量块附带来源信息。

### full.md（向量化的主要文本来源）
- MineRU 解析出的全文 Markdown，英文原文。
- 图片以 `![](images/xxx.jpg)` 标记（向量化时通常忽略图片标记，只取文字）。

### summary.html（精读成果）
- 自包含 HTML，图片已内嵌为 base64，可脱离目录独立打开。
- 结构：`<h2 class="section">` 分栏目（导读/引言/实验/讨论/总结/文献信息）。
- 如需从中提取纯中文文本（如给向量库存中文摘要版），去掉 `<img>` 和标签即可。

## 契约保证（下游工具可以依赖的约定）

1. **文件夹名 = Zotero item key**，一定是 8 位字母数字。
2. **每个已处理文献一定有** `parsed/full.md`、`summary.html`、`meta.json` 三个核心文件。
3. **文件路径稳定**：不随系统升级改变。工具按 `library/<key>/full.md` 这样的固定路径读即可。
4. **只增不改**：一篇文献处理好后，其数据视为只读资产。重新精读会覆盖 summary.html，但 key 和路径不变。

---

## 这对"换工具/升级"意味着什么

- **换向量库**（Chroma→其他）：读同样的 `library/*/full.md` 和 `meta.json` 重新建索引即可，原始数据零改动。
- **换 embedding 模型**：重新向量化一遍，原始数据不动。
- **换解析工具**（MineRU→其他）：只要新工具也往 `parsed/` 里产出 `full.md` + 图坐标信息，下游精读/向量化不用改。
- **系统坏了重装**：`library/` 是核心资产，备份它就等于备份了所有成果（配合 `换设备重装指南.md`）。

## 数据分层：什么不可再生、什么可随时重建（建库最该想清楚的事）

用户问题（2026-07-25）：向量化跟模型能力强相关，以后有更好的模型，能不能像积木一样换？
还是说这一层是天花板、没办法？

**答案：向量化恰恰是最容易换的一层。** 因为要区分"原始资产"和"派生物"：

```
原始文本/PDF (公理层)  →  向量索引 (派生层)  →  检索问答 (应用层)
  不可再生·永久保留         可随时重建·可丢弃
```

| 数据 | 可否重建 | 成本 | 策略 |
|------|---------|------|------|
| **原始 PDF / full.md / Zotero 原文** | **不可再生** | — | **永久保留 + 备份**（核心资产）|
| 向量库（89.6MB, 9105块） | 可重建 | 本地 bge-m3 免费、几十分钟 | 随便丢，换模型就重跑 |
| 结构化抽取 JSON | 可重建 | 几块钱 DeepSeek | 带版本标记，增量重抽 |
| 精读 summary.html | 可重建 | 几分钱/篇 | 可重跑 |
| **用户的标签/笔记/判断** | **不可重建** | — | **最该保护**（是人的智力投入，模型算不出）|

**硬约束（不影响结论）**：不同 embedding 模型的向量在数学上不兼容（bge-m3 的 1024 维
与别的模型无法比较），所以换模型必须**全量重跑**。但重跑是本地免费的，故不构成障碍。

**结论**：向量层不是天花板，是"最不值钱也最容易换"的中间层——这是优点。
真正要小心守护的是①原始资料 ②用户自己的判断/标注（Zotero 标签、笔记）。
后者建议纳入备份策略。

## 可增量再提取原则（回答"以后有更好的方法，要重来吗"）

用户问题（2026-07-24）：信息库建好后，若发现更彻底的提取方法，能在原基础上再提取还是必须重来？

**核心答案：能增量，不用推倒重来——因为保留了"原料"。**

用第一性原理看：
- **原始正文 full.md = 公理**（不可再分的原始事实，永久保留，只增不改）。
- **提取结果（structured JSON）= 定理**（从公理推导出的，可随方法进步重新推导）。
- **定理可以重推，只要公理还在。** 我们永久保留 full.md，所以任何新提取方法，
  最坏也只是"拿现成 full.md 重跑一遍新方法"——不用重下载、重解析 PDF（那些重活）。

**为什么是"回原文重抽"而非"改旧结果"**：提取是信息压缩，旧结果丢了原文信息。
旧方法抽成 N/A 的，新方法要救回，必须回到 full.md 去抽，不能在"N/A"上改。

**如何实现"增量"（只重抽需升级的，不全部重来）——靠版本/来源标记**：
1. 每条抽取记录标 `source`（coarse粗层/精层）、`schema_ver`、`model`、抽取时间。
2. 有新方法时，只对"旧版本"的重抽，已是新版本的跳过（如精层保护机制 #16）。
3. **字段级增量**：JSON 是字段化的，可只对某几个字段用新方法重抽、其他保留。

**结论**：只要守住"full.md 永久保留 + 结果带版本标记"，就能随方法进步**增量升级数据**，
永远不必推倒重来。这是本平台数据资产可持续的根本保证。

## 维护建议

- **library/ 定期备份**（它是不可再生的成果沉淀，尤其你认真读过的）。
- 早期文献如缺 `meta.json`，可用 `scripts/backfill_meta.py` 补齐（保证结构一致）。
- 新增字段时，往 meta.json 里加即可，老工具读不到新字段也不会坏（向后兼容）。
