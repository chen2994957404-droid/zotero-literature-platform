# 架构宪法 · 第一性原理构筑法

> **这是平台的最高纲领,凌驾于所有其他文档之上。任何 LLM/人接手,先读这一份。**
> 它定义"这个系统该如何被构筑与维护"的根本逻辑。具体怎么做(模块地图、数据契约)
> 都必须服从本宪法。

---

## 序言 · 哲学根基:拆解以理解，组合以创造

平台主导者的洞察（2026-07-24）：

> 人类认识世界，是不是就是把世界拆成一个个可以定义、完全理解的最小单元；
> 而创造，就是用这些小单元去组合？

这触到了贯穿数学、物理、哲学的同一个母题，也是本平台的根基：

**这个思想的多张脸（都是同构的）：**
- **线性代数**：任何向量 = 一组基向量 × 系数。基是最小单元，系数是组合方式。
  → 对应本平台：公理是基，推导取系数组合。
- **傅里叶变换**：任何复杂信号 = 简单正弦波的叠加，且分解唯一完备。
  → 复杂 = 纯粹单元的组合，这是"世界可拆解"最美的证明。
- **还原论**：整体拆成部分理解（分子→原子→夸克），找不可再分的最小单元。
- **欧几里得**：5 条公理推出整个几何。**元素周期表**：基本单元解释万物构成。

**但认识要完整，必须补上另一半——组合会"涌现"：**
- 还原论有边界。20 世纪科学发现"涌现（emergence）"：整体有部分完全没有的性质。
  单个水分子没有"湿"，聚起来"湿"涌现；单个神经元不思考，860 亿个组合出意识。
- **拆解告诉你"由什么构成"，但不总能预测"组合会产生什么"。**

**这对本平台的根本指导：**
- **公理层（拆解/还原）** = 把能力拆成最小、可完全理解的单元。地基，已做对。
- **组合层（涌现/创造）** = 积木组合会涌现出单个积木没有的能力。
  例：定位→解析→抽取→找空白→知识图谱，组合起来**涌现出"发现研究 idea"的能力**
  ——这能力不在任何一块积木里，是组合的产物。
- 所以"拆成单元"和"用单元创造"不是一回事：**拆解为理解，组合为涌现。**
  地基（还原/公理）砌好后，真正的探索是"组合会涌现出什么"——即"编排层"（见对标报告）。

一句话：**我们用还原论造干净的砖，用涌现论期待组合的奇迹。** 两者缺一不可。

## 一、核心理念:像数学一样构筑

用户(平台主导者,非程序员)提出的立身之本:

> 像数学那样,从最根本、不能再细化的通识(如 1+1=2 的公理)出发,
> 一步一步往上,构筑一个**绝对有序的网络**。

翻译成工程语言:
- 数学:公理 → 由公理组合成定理 → 定理组合成更大的定理。每步可追溯、无循环。
- 本平台:**原子能力(公理)** → 组合成**功能(定理)** → 功能编排成**工作流(大定理)**。

一切复杂,都是基础的有序组合。LLM 再进化,本质也是在组合调用这些稳定的基础件。
基础件越纯粹、依赖越有序,系统越经得起时间和 LLM 换代。

## 二、三条铁律(不可违背)

### 铁律 1:识别并沉淀"公理层"——不可再分的原子能力
每个原子能力只做一件不能再拆的事,不依赖任何上层。例:
- `定位文献正文PDF`(Zotero 里给 key 找到正文 PDF)——公理
- `PDF→文本`(解析)——公理
- `文本→向量`——公理
- `LLM 翻译重组`——公理

判据:如果一个能力还能被拆成"先做A再做B",它就不是公理,是定理。

### 铁律 2:严格单向依赖,永不循环
上层可调下层,下层**永远不知道**上层存在。
- 允许:精读 → 解析 → 定位PDF
- 禁止:任何反向或循环依赖(像定理不能循环论证)。
这保证整张依赖网"绝对有序",改任一层不会波及其上游。

### 铁律 3:每层可独立验证
每个模块自带 `selftest.py`,能脱离其他部分独立验证正确性
(像每条定理可独立证明)。LLM 改动时逐层验证,牵一发不动全身。

## 三、用第一性原理重看现有的"线"

现有的"精读线/向量线/抽取线"其实都不是公理,是**定理**——是原子能力的编排:

```
精读(定理) = 定位PDF → 解析 → 裁图 → LLM翻译重组 → 渲染HTML → 写回Zotero
向量问答(定理) = 取全文 → 切块 → 向量化 → 存库 →（问答: 检索 → LLM综合）
结构化抽取(定理) = 取正文 → LLM按schema抽取 → 汇成对比表
```

竖着看会发现:**多条定理共用同一批公理**(定位PDF、解析、取全文、LLM调用)。
这正是"基础件拼装"的意义——公理写一次,被多个定理复用,不重复。

### 【首要判据】按"稳定性"决定自己做还是用现成（比按复杂度更本质）

用户洞察（2026-07-25）：
> 把工作分到不可再分后——**稳定存在、后面一直需要的部分自己做；还在发展的东西
> 就用现成的合适的，或稍微改一下。**

这比"按复杂度分"更准。因为复杂度会误判：有的复杂但稳定（裁图坐标换算，数学对了十年不改），
有的简单但天天变（LLM API 格式）。按稳定性分，逻辑是**投入回报**：
- **稳定的** → 一次做对用十年 → 自己做值得，且必须自己掌控（是地基）。
- **发展中的** → 自己做完很快过时 → 用现成的，让别人替你跟进更新。

**实操口诀**：
- "这东西十年后还会是这样吗？" → 会 → **自己做**。
- "一年内会不会被更好的取代？" → 会 → **用现成的，但包一层自己的接口**。

**我们的实践验证**：

| 部件 | 稳定 / 发展中 | 做法 |
|------|--------------|------|
| 裁图坐标换算、Zotero 路径约定、文本切块、数据契约 | 稳定（格式/数学） | 自己写 ✓ |
| MineRU 解析、DeepSeek、bge-m3、视觉模型 | 快速发展（几个月换代） | 用现成 ✓ |
| 知识图谱方法 | 论文里仍在发展 | copy 现成骨架 ✓ |

**最高形态：把变化隔离在稳定接口背后**（llm_client 就是范例）
- 外层 = 我们自己的稳定接口（`chat`/`chat_json`，多年不变）
- 内层 = 快速变化的第三方（已换过 DeepSeek → Ollama → 硅基流动三家）
- 效果：**模型天天换，只改内层几行，上层所有代码一动不动。**
这就是"稳定的自己做（接口）+ 发展的用现成（实现）"的完美结合，应作为默认模式。

---

### 分层复杂度策略（自己写 vs copy 成熟代码）—— 次要判据，服从上面的稳定性判据

用户洞察（2026-07-24）：到组合层，做成好工具的复杂度会指数上升，此时应
"copy 一部分成熟代码做基准，再在其上改"。这是对的，且不违背宪法。判断标准：

| 层 | 复杂度 | 策略 |
|----|--------|------|
| **公理层**（原子能力，如 zotero_client/pdf_parse/llm_client） | 低、线性、一人可完全理解 | **自己写**，完全掌控，是核心资产 |
| **组合层**（知识图谱/编排/关系推理） | **高、指数**，各部分纠缠，是别人做了多年的成熟领域 | **copy 成熟骨架 / 依赖极稳定的底层库**（如 NetworkX 图论），在其上改 |
| **界面层**（可视化/交互） | 高 | 优先用成熟方案，别自己造 |

**copy 的度**（延续"选择性 copy"智慧）：
- copy 它的**骨架/机制**（如"三元组怎么存图、怎么查询"），消化成我们自己的代码；
- **不** copy 它绑定的重依赖和抽象负担；
- 只依赖**极稳定极通用**的底层库（NetworkX 这种做了十几年、几乎不变的），
  花哨框架不碰。
- 原则不变：拿能力/骨架，不拿负担；保持可理解性。

**首个适用对象**：知识图谱（组合层）。届时 copy MatKG 等项目的"实体-关系-存图-查询"
骨架，消化成自己的、依赖 NetworkX，而非从零硬写或套厚框架。

## 四、公理层清单(持续沉淀,modules/ 下逐个建成基础件)

| 公理能力 | 现状 | 基础件 |
|---------|------|--------|
| Zotero 定位/读写 | ✅ 已沉淀 | modules/zotero_client |
| PDF → 文本+图坐标 | ✅ 已沉淀 | modules/pdf_parse |
| LLM 调用（云/本地） | ✅ 已沉淀 | modules/llm_client |
| 文本 → 向量 + 预处理 | ✅ 已沉淀 | modules/embed |
| 裁图（PDF按坐标） | ✅ 已沉淀 | modules/figure_crop |

**原则**:不为沉淀而沉淀。每次因需求动到某块,顺手把它涉及的公理理成基础件,
逐步逼近"全系统由干净公理组合而成"。别一次性大重构(风险高)。

## 五、精读的正确形态(以此为范例)

精读是定理,不该往里堆功能(图表数字化、对比矩阵等都是**别的定理**,不属于精读)。
完善精读 = 让它依赖的公理都变干净 + 精读自己只负责"按顺序编排公理",变薄变清晰。

诱人但不属于精读的功能(来自调研 literature-review-with-LLM 等成熟项目),
归入"未来独立定理",各自作为独立基础件按需构筑,绝不塞进精读:
- 图表数字化(曲线图→数据点)= 独立定理
- 多文献对比矩阵 / 研究空白账本 = 属"找idea"线(未来知识图谱方向)
- 候选文献检索(arXiv/Semantic Scholar)= 独立定理

## 六、从成熟项目吸收的判据(两把尺子)

调研外部项目(如 literature-review-with-LLM)时:
- **架构/代码更优的** → 吸收。例:写回文件前"预览+备份"的安全机制;
  provider(模型)配置化而非写死。
- **功能性的** → 先归位到它该属于的定理,绝不因为"有用"就塞进现有模块。
  哪怕有用,也可能该是一个独立基础件。守住单一职责。

## 七、为什么要这样构筑(立意,不可忘)

平台主导者不懂开发。这套第一性原理架构的**根本目的**,是让他能真正掌控:

> 后期的维护与学习,就是**优化公理**(让原子能力更纯粹可靠)+
> **优化公理到定理的推导**(公理怎么组合成需要的功能)。这是设计的核心,要坚持。

为什么这让"不懂开发的人也能做有用的 vibe coding":
- 普通 vibe coding = 丢个想法、AI 生成一坨代码、能跑就行、坏了主导者看不懂也改不动
  = 把黑箱交给运气。
- 本平台 = 系统是一张**主导者看得懂逻辑的有序网络**。他不碰代码,但能在两个层面参与:
  - **公理层**:感知某个基础能力好不好用(如"定位PDF老找错")→ 提出来。
  - **推导层**:定义公理怎么组合成他要的功能(如"精读先给方法再给结论")
    → 这是逻辑和需求,不是代码,他完全能主导。
- 于是分工清晰:**主导者掌控意图与结构,LLM 掌控实现**。逻辑可谈,代码托付。
  这才是 layperson 能真正掌控的 vibe coding。

**因此:任何 LLM 维护本平台时,不仅要写对代码,更要维持这张网络的"可理解性"——
让非程序员主导者始终能在公理层和推导层与你对话。牺牲可理解性换来的"聪明"实现,违背本宪法。**

## 八、给接手 LLM 的最高指令

1. 先读本宪法,理解"公理→定理→工作流"的构筑逻辑。
2. 任何改动前问自己:我动的是公理还是定理?会不会制造循环依赖?
3. 新能力先判断:它是公理(沉淀进 modules/)还是定理(编排现有公理)?
4. 改完跑相关 selftest;记 变更记录 / 踩坑记录 / 待办与需求。
5. 不为架构而架构——顺手沉淀,别大重构。可用永远优先于完美。
