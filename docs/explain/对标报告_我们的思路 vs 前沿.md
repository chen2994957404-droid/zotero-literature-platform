# 对标报告 · 我们的思路 vs 行业前沿（2026）

> 目的：把"我们的第一性原理构筑法"放到行业最前沿里做客观定位。
> 结论先行：**方向先进、与前沿一致；下一层是"编排层"；框架先别急着用。**

---

## 一、我们的思路先进吗？→ 是，且与前沿高度一致

Anthropic《Building Effective Agents》（被行业反复引用的权威）开篇即：
> "最成功的实现用的是**简单、可组合的模式，而非复杂框架**。"

它的三条核心原则，我们几乎全中：

| Anthropic 原则 | 我们的对应 |
|---------------|-----------|
| 简单（simplicity），只在必要时加复杂度 | "单一职责、不要一大坨、可用优先于完美" |
| 透明（transparency），别用遮蔽底层的框架 | 不套厚框架、宪法要求"保持可理解性" |
| 精心设计接口（ACI：好文档+测试） | 每个公理件配 README + selftest |
| 可组合构建块（composable building blocks） | 公理→定理→工作流 |

**判断**：一个非程序员靠第一性原理独立推出的架构，和 Anthropic 工程团队总结的结论
同向。方向站得住，值得有信心。

## 二、有没有更先进的？→ 有一层我们还没走到：编排层（harness）

行业时间线：2025=agent 年，2026=**agent harness（智能体骨架）年**。
在"干净积木"之上，还有一层"编排器"，能**动态组合积木**完成开放任务。

- 我们现状：把能力理成干净公理件（地基，已做对）。
- 下一层：一个编排器按需自动决定调哪些积木、什么顺序、循环几次。
  例：用户说"整理这批文献的投料比数据"→ 编排器自己编排 定位→解析→抽取→汇总。

Anthropic 总结的 5 种**可组合工作流模式**（正好是"定理→大定理"的标准范式）：
1. **Prompt chaining（链式）**：拆成固定步骤，一步喂给下一步。（我们的精读/抽取就是这种）
2. **Routing（路由）**：先分类再分发到专门处理。（如综述 vs 研究论文分流）
3. **Parallelization（并行）**：拆成独立子任务并行，或多次投票取共识。
4. **Orchestrator-workers（编排器-工人）**：中枢 LLM 动态拆任务派给工人再汇总。
5. **Evaluator-optimizer（生成-评估循环）**：一个生成、一个评估反馈，迭代改进。

**我们的自然下一步**：把现有"线"显式表达成这些模式；未来做一个轻编排器，
让 agent 能按需组合公理件——但这是地基稳固后的事，不急。

## 三、别人的积木管理工具/框架？→ 很多，但现在别用

成熟框架：LangGraph、CrewAI、Claude Agent SDK、Pydantic AI V2、LlamaIndex
Workflows、Haystack（可组合 pipeline，每个组件是带类型输入输出的节点）。
它们就是"积木管理 + 编排框架"。

**但 Anthropic 明确警告（对我们尤其重要）**：
> "框架能帮你快速起步，但常制造额外抽象层，遮蔽底层 prompt/响应，更难调试，
> 还诱使你过早加复杂度。建议**先直接用底层 API**；若用框架，**务必理解它底层做什么**。"

**为什么我们现在不套框架**：
- 我们靠 LLM 长期维护，立身之本是"可理解性"（宪法·第七节）。厚框架恰恰破坏它。
- 我们的公理件是纯 Python 标准库、零外部框架依赖——这是优点，别丢。
- 框架适合"团队协作、大规模、需要现成编排"的场景；我们是"单机自用、LLM 维护"，
  自己的极简编排（几行代码的 chaining）足够，且完全透明可控。

**未来若要引入编排**：优先自己写极简编排层（对齐上面 5 种模式），而非直接套框架；
真要用框架，只借鉴其**模式思想**，不引入其**抽象负担**。

---

## 四、给未来的行动指引（不急，按需）

1. 继续沉淀/打磨公理件（地基）——这是当前最正确的事。
2. 地基稳后，把现有"线"显式整理成 chaining/routing 等模式，让结构更自觉。
3. 需要"开放任务自动编排"时，自己写极简编排器（透明、可理解优先）。
4. 持续对标（每隔一段看看前沿），但坚持"借鉴思想、不套负担"。

**一句话**：我们走在对的路上，且比多数人更克制。前沿的"编排层"是我们的下一站，
但地基优先。框架是工具不是目的，可理解性永远第一。
