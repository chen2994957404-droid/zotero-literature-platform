# 架构宪法 · 分级版

> 本文件是平台的正本纲领。**2026-09-07 重写**：旧版 288 行的推导与哲学原文整篇存进
> `架构宪法_v1_历史存档.md`（一个字没删），这里只留**会改变行为**的部分。

## 怎么用这份文件（先读这一节）

每条规矩带一个标记，**标记决定你能不能推翻它**：

| 标记 | 含义 | 你该怎么对待 |
|------|------|------------|
| 【事实】 | 这个项目的客观状态 | 不可推翻。只有实测发现世界变了才改，并当场更新本文件 |
| 【硬约束】 | 有守卫强制，或涉及花钱/不可逆/用户信任 | 不可推翻。要改先跟用户谈 |
| 【启发式】 | 当时的经验判断 | **可以推翻。** 遇到反例**有义务说出来并给证据**，不许闷头照办 |

**为什么要分级**（2026-09-07 立，用户洞察）：
> 那些旧宪法是不是相当于在你的思考之上，只要稍微合理你也不会推翻它，
> 我怕它反而会限制大模型的思维。

这个担心是真的。写进本文件的话会作为用户指令进入每次会话，优先级高于模型自身判断 ——
**只要看起来不离谱，模型就会照办，不会质疑。** 分级是为了把「不许质疑」的范围
缩到真正该锁死的那一小块，其余全部交还给你自己的判断。

**推论**：本文件里凡是模型本来就懂的通用方法论（高内聚低耦合、单向依赖、
先做最简单能跑的版本），**不写**。写了只会把一个能灵活应用的概念，
锁死成当时想到的那一种用法。哲学论证也不写，全在 v1 存档里。

## 一、【硬约束】零号判据：先看真实世界，别用记忆代替调研

用户原话（2026-08-09）：
> **你下意识回答我的往往还是预训练的结果，我们还是要主动去看真实实时的世界是怎么样。**

<!-- 摘:零号判据 开始 · 本段是全项目唯一的源，AGENTS.md 与 research-first skill 由生成器抄过去 -->
- 外部世界现状的断言（有无某功能、定价、限额、版本、行业惯例）→ **必须查**
- 具体数字 → 查到出处才说，查不到就明说查不到
- 外部 API 行为 → 真实调用实测，不信文档也不信记忆

**现场例证（这是本条真正起作用的部分，不许抽象掉）**：我曾断言「MineRU 的 token
通常两周过期」。查证后官方**根本没给任何天数** —— 那个「两周」是我编的，
一个听起来精确、实则无据的数字。

**自查方法**：说完一句判断，问自己「这是**刚查到的**，还是我**本来就『知道』的**？」
后者一律打问号。

**唯一停止判据**：这次调研能不能改变我接下来的做法？能就查，不能就别查。
<!-- 摘:零号判据 结束 -->

四步调研法在 `research-first` skill，不在这里重复。

## 二、【硬约束】可理解性条款

平台主导者不懂开发。**牺牲可理解性换来的「聪明」实现，违反本宪法。**

他不碰代码，但必须能在两个层面参与：感知某个基础能力好不好用（「定位 PDF 老找错」）、
定义能力怎么组合成他要的功能（「精读先给方法再给结论」）。这是逻辑和需求，不是代码。
**主导者掌控意图与结构，LLM 掌控实现** —— 这是「不懂开发的人也能做 vibe coding」
的全部前提，塌了这条，整个平台就退回成一个看不懂也改不动的黑箱。

## 三、【硬约束】构筑逻辑：公理 → 定理 → 工作流

原子能力（公理，住 `shared/`）组合成功能（定理，住 `tools/`）编排成工作流。
判据：**一个能力如果还能拆成「先做 A 再做 B」，它就不是公理，是定理。**

五层依赖与四条硬规则写在 `AGENTS.md`，由 `tests/test_architecture.py` 强制。
本文件不重复 —— 重复的规矩必然漂移。

每块自带 `selftest.py`，可脱离其余部分独立验证。

## 四、【硬约束】核心归属：数据库是公共账本，Zotero 是个人书架

用户拍板（2026-09-07）。起因是他自己的判断：

> 数据库应该是一个更庞大的集群，包含 Zotero 里的内容……
> Zotero 更多的是代表我个人，而数据库代表整个大方向。

**平台的核心是「证据库」** —— 每一条带出处的数字、样品、曲线。
Zotero 不是核心，它是**若干来源里最重要的那一个**，同时是精读成果的展示面。

由此三条：

1. **文献的身份证与来源无关**（`shared.kernel.paths.check_key`）。
   Zotero 编号退化成一个属性：「这篇在他自己的库里」。
   **跨来源认同一篇靠 DOI**，不靠 id。
2. **数据库不往 Zotero 里塞东西来"存"**。PDF、全文、解析产物的正本在 `data/raw/`；
   推进 Zotero 的只有「他要读的那几篇 + 精读报告」，那是**给人看的副本，不是真相**。
   （这条同时解掉了 Zotero 同步容量的天花板：库长到十万篇，他的 Zotero 里还是几百篇。）
3. **写入口只有一个**：B 机上的流水线。别的设备、别的来源、包括他在 Zotero 里的操作，
   都只是**投稿**（打标签 = 提交一篇种子），由流水线决定收不收。

**这条为什么是硬约束**：它是用户的领域判断，不是技术选择。要改先跟他谈。

## 五、【启发式】按稳定性决定自己做还是用现成

用户洞察（2026-07-25）：稳定存在、后面一直需要的部分自己做；还在发展的东西用现成的。

比按复杂度分更准：有的复杂但稳定（裁图坐标换算，数学对了十年不改），
有的简单但天天变（LLM API 格式）。

- 「十年后还会是这样吗」→ 会 → 自己做
- 「一年内会不会被更好的取代」→ 会 → 用现成的，**但包一层自己的接口**

**最高形态**：`llm_client` —— 外层是我们自己多年不变的 `chat`/`chat_json`，
内层已换过 DeepSeek → Ollama → 硅基流动三家，上层代码一行没动。默认照这个来。

## 六、【启发式】组合层可以 copy 成熟骨架

公理层自己写（低复杂度、完全掌控、是核心资产）；组合层（知识图谱/关系推理）
复杂度指数上升且别人做了多年 → copy 骨架、消化成自己的代码，
只依赖极稳定的底层库（NetworkX 这种），不套花哨框架。**拿能力，不拿负担。**

## 七、【启发式】不为架构而架构 —— ⚠ 本条有已知副作用

原文是「顺手沉淀别大重构，可用永远优先于完美」。

**⚠ 2026-09-07 记：我拿这条合理化过「不修根因」。** 最明显的例子 ——
精层向量只有 276 块、精读产出的高质量全文基本没进库，这个问题挂了很久没动，
这条规矩给了我不动它的理由。

**所以本条附带一个反向义务**：引用它推迟一件事时，必须同时说出
「我正在推迟的是什么、它的代价是什么」，写进 `docs/待办与需求.md`。
只说「可用优先于完美」就跳过的，视为违反本条。

## 八、已知待推翻项（活的靶子，欢迎证伪）

下面几条是现行规矩，但**已经有理由怀疑它们**。谁有证据就来推翻，改完就从这里划掉：

1. **「提示词只增不改」**（`AGENTS.md`）—— 直接后果是提示词只会越来越长，
   而且加进去的每一条**从没被证伪过**。待做：用比武台做一次消融，
   删掉某段约束看输出变不变。
2. **【零号判据】同时住在三处**（本文件 / `AGENTS.md` / `research-first` skill）——
   改一处另两处就漂移。跟「别落第三份 JSON」是同一个病，待收敛。
3. **「每个改动 Git commit」与「改完跑生成器」没规定先后** ——
   实操中经常先 commit 后跑生成器，顺序是错的。

## 九、给接手 LLM 的最高指令

0. 先看真实世界，别用记忆代替调研（第一节）。**听起来很具体的数字最像事实，也最可能是你编的。**
1. 动手前问自己：我动的是公理还是定理？会不会制造循环依赖？
2. 新能力先判断：公理（沉淀进 `shared/`）还是定理（编排现有公理，住 `tools/`）？
3. 改完跑相关 selftest；记 变更记录 / 踩坑记录 / 待办与需求。
4. **看到标着【启发式】的规矩不对，就说出来并给证据** —— 沉默照办才是违规。
