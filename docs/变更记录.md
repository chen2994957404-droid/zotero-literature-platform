**背景**：用户在本对话用平台辅助解决合成问题（聚联硼硅氧烷封端程度/摩尔投料比），
过程中给一篇目标文献 CABSSMLA 打「待精读」，暴露并修复了两个问题。

### 改动 1：修复 find_pdf 误选补充材料（SI）去精读
- **文件**：`scripts/zotero_watcher.py`（find_pdf 函数）
- **问题**：Springer/Nature 系 SI 命名 `..._MOESM1_ESM.pdf` 逃逸了 SUPP_PAT 正则，
  且该 SI 恰好比正文大，被误选去精读。用户在 Zotero 改附件 title 为 "SI" 无效，
  因 find_pdf 读的是磁盘 filename 而非 title。
- **修法**：① SUPP_PAT 增加 `moesm|_esm\b|electronic.?supplementary`；
  ② 同时把附件 Zotero title 纳入判断（title 命中正则 或 title=="SI" 即判 SI），
  尊重用户手动标注。零副作用（只会让更多 SI 被正确排除）。
- **验证**：直接调 find_pdf("CABSSMLA") → 正确选中正文 IL4MTXUJ。✓
- **关联**：踩坑记录 #15。

### 认知 2：deepread_v4 的密钥注入机制（未改代码，仅记录踩坑）
- `deepread_v4.py` 的 DeepSeek key 靠命令行第5参数传入，**不读环境变量**，
  且唯独它没有硬编码 fallback key。上游 watcher 从环境变量 `DEEPSEEK_KEY` 读，
  读不到就传空 → 精读 401。
- **正确启动**：在同一 PowerShell 会话 `$env:DEEPSEEK_KEY="..."` 后再起 watcher，
  确保环境变量继承到 python 子进程。用 `Start-Process cmd /c 启动Zotero闭环.bat`
  时 set 的变量可能传不到子进程。
- **潜在改进建议（留给设计侧决定）**：可让 watcher 或 deepread 也支持从
  `.env` 文件或统一配置读 key，避免每次靠环境变量继承。

### 运维观察 3：watcher 会卡死 + 非自启
- watcher 是普通后台进程，**非开机自启服务**；且观察到进程会卡死（日志十分钟无轮询痕迹），
  卡死后需杀掉重启。
- **潜在改进建议（留给设计侧）**：给 watcher 加轮询心跳日志/看门狗，
  或做成真正的自启服务（任务计划），避免静默卡死。

### 数据操作 4：CABSSMLA 用正文重跑
- 删除了基于 SI 的旧结果（library/CABSSMLA 目录 + structured/CABSSMLA.json），
  标签重置「待精读」，用修复后的 find_pdf 重新用正文精读。

### 结果 5：CABSSMLA 正文精读成功
- 修复后重跑，find_pdf 正确选中正文（IL4MTXUJ），MineRU 解析正文、7张正文图、DeepSeek 精读 9112 字、summary.html 6.2MB 生成。对照之前误选 SI（14张SI附图）已纠正。

## 2026-07-24 · 新增 extract_batch.py（精层批量抽取，补自动 MineRU 衔接）

**背景**：extract_structured.py 缺 full.md 时直接跳过，不会自动解析。精读线的 watcher
虽有「有则复用、无则调 MineRU」逻辑，但精抽脚本没接上。补这一环。

**新脚本 scripts/extract_batch.py**：
- 对给定 key 列表：ensure_fullmd(key) → 有 full.md 复用；无则 find_pdf 定位本地正文 PDF
  （复刻 zotero_watcher.find_pdf 稳定逻辑，含 #15 的 SI 排除补丁）→ mineru_parse 落地
  到 library/<key>/parsed/ → 再走 extract_structured 的精层抽取（DeepSeek pro）。
- 解析结果与精读线共享同一 full.md（数据契约），谁先跑谁生成，另一方复用，不重复解析。
- 产物 source 无标记=精层，受 #16 保护，--rebuild 不会覆盖。
- 用法：python extract_batch.py KEY1 KEY2 / --file keys.txt

**模型选择**：精抽是「输入重、输出轻」的活（输出仅十几字段的 JSON），
用 deepseek-v4-pro——pro/flash 主要差在输出价，输出轻则 pro 几乎不增成本却更准。
（对照：精读线输出 9000 字长文，用 flash 省钱。原则：输出少上 pro，输出多上 flash。）

**首次应用**：PBS 方向 12 篇精抽（探针 5NIJVLMA 链路验证通过：
粗层 N/A → 精层抽出「内部损伤减少65%、损伤面积减少70%」等定量数值）。
MineRU 每日 500 篇免费额度，解析零成本；仅 DeepSeek 精抽花费几元。

## 2026-08-09 · 查询扩展：解决「搜不全面」的根本问题

**用户反馈**：「我在试我的平台的时候感觉还是有点局限不太全面」，

**调研结论**（PaperPilot / PaSa / SPAR 等前沿工作的共同设计）：
1. **查询分解与扩展** —— 把研究问题拆成领域概念、术语变体、约束，
   生成多个适配数据库的查询串，**而不是拿用户原话直接搜**
2. **引用图扩展** —— 前驱/后继/同辈/基准/综述 五个方向遍历引用网络
3. **多轮迭代** —— 保持状态、累积已用查询、用已得结果指导下一轮
4. **重排与集合运算** —— 多源结果做交并差后统一打分
5. 结果排序 ← 我们已有（且 lib_match 比通用工具更贴合本用户）

值得注意：那篇论文的对比表里，连 Elicit 这类商业工具在**引用图扩展**上也标为不支持。

**诊断**：用户「不全面」的主因是**术语覆盖**。材料领域同一事物有大量别名
（polyborosiloxane / PBS / borosiloxane elastomer / shear stiffening gel / silly putty…），
单一检索式必然漏掉用其他叫法写的那批。

**新增第 14 块公理件 `pipelines/query_expand`**：
- `survey` 模式求全（术语变体/同义词/上下位概念）；`problem` 模式求准（现象/机理/解法/指标/体系）
- 两条硬约束：第一个检索式永远是原式（防扩展跑偏丢掉本意）；LLM 不可用时降级不失效
- 顺带消除了 ask_world 里重复实现的中译英逻辑

**discover.py 改为多式检索**：合并去重 + **各式新增贡献统计**。
后者直接回答「搜得够不够」——最后两式几乎无新增即判定「基本搜到底」，
反之提示「可能还没搜全，可加 --扩展 8」。这是系统综述里判断停止的标准做法。

**实测效果**：
- 「polyborosiloxane shear stiffening」：单查询约 20 篇 → 4 式合并 **45 篇**，

**验证**：query_expand 自测 5/5；两种模式各用真实问题实测；体检 12 项全绿（14 块积木）。

## 2026-08-09 · 宪法新增【零号判据】：先看真实世界，别用记忆代替调研

  「有效期需关注平台通知，过期后重新获取」，**没有任何具体天数**。

  这个结论任何一方的记忆里都得不出，只能测出来。

**自查方法**（已写进最高指令）：说完一句判断，问自己 ——
这是**刚查到的**，还是我**本来就"知道"的**？后者一律打问号。

1. 把 discover 的整条流程抽成 `run_discovery()` —— **命令行与面板共用同一份逻辑**。

## 2026-08-09 · 精读质量评测集：把主观判断变成系统能自动算的标准

**背景**：用户问「用 LLM 用得牛的人怎么用、我在哪个阶段」。
查证后（Gartner「context engineering is in, prompt engineering is out」、
规格驱动开发的 CLAUDE.md 实践）给出的判断是：他在上下文工程与系统化上做得扎实，
**最大的缺口是没有评测集** —— 所有自动检查都在验「能不能跑」，没有一项验「好不好」。

**用户的方案演进（他自己迭代出了更好的设计）**：
1. 最初想法：加「看完了」「正在看」标签 + 质量评价标签，评价用完自动消失
2. 我指出的风险：**三个维度不能混进同一个互斥状态机** ——
   若「读完」覆盖「全文精读」，系统会以为没精读过而重跑（花钱）
3. **他随即提出更好的**：「或者以另一个窗口的形式……那个窗口就可以塞下一个
   比较完美合适的评价体系，而不是只能局限标签」

最终设计正是第 3 条：**标签只做触发，面板做评价界面**。

```
Zotero 里只打：在读 / 读完        ← 干净，就两个，系统只读不改
控制面板「精读评价」：            ← 完整评价体系
   自动列出「读完但未评价」的 → 可直接打开精读 → 就地评价
```
评价**不回写 Zotero**，存本地 `workflow_data/evalset.json`。

**新增第 16 块公理件 `adapters/evalset`**：
- `snapshot()` 算客观指标：字数、图数、**数值密度**、章节完整性
- `save()` 记录评分时**连同当时的客观快照** —— 这是关键：
  没有快照，评分只是孤立分数；有了快照，才能回答「什么客观特征对应用户认为的好」
- `stats()` 对比好/差两组的客观指标差异，并判断样本是否够做校准

**面板新增「精读评价」卡片**：待评队列、二元评价 + 6 类可选差评原因 + 备注，
并提供 `/summary?key=` 直接在浏览器打开本地精读（带路径穿越防护）。

**实测**：给一篇已精读文献打「读完」→ 出现在待评队列（含快照 10508字/5图/27数值/6章节）
→ 提交评价 → 从队列消失、评测集 +1 → 确认「全文精读」标签**未被覆盖**（两标签共存）
→ 清理测试数据还原现场。非法评分被拒、路径穿越被拦截。体检 13 项全绿（16 块积木）。

**过程中的一个自我教训**：改完 panel.py 直接重启，导致面板启动失败
（在 `b''` 字节串里写了中文）。**这个错体检的语法检查本来就能抓到，我没跑就重启了。**
写了检查却不用，等于没有。

## 2026-08-26 · 架构重构 v2 · 阶段 1 完成（core/log + core/errors）

### core/log.py —— 统一日志

改造前同一件事有三种写法：`zotero_watcher` **把内置 print 整个换掉**、
`watchdog` 和 `auto_sync` 各自写一个 `def log(msg)`。
劫持 print 尤其糟：读代码的人看到 `print('...')` 会以为只是打屏，实际在写文件；
而且这个 hack 无法 import 复用，只能复制粘贴。

三者还共有一个真问题：**没有任何一个会轮转**。`zotero_watcher` 是常驻服务，
日志只会一直长下去。

- 底层用标准库 `logging` + `RotatingFileHandler`（5MB × 3 份）——
  轮转这种稳定又琐碎的活用现成的，符合宪法【首要判据】
- 对外只暴露一个**像 print 一样的可调用对象**，所以 watcher 里几十处
  `print(...)` 调用**一行都不用改**，只把名字绑过去：
  `print = get_logger('zotero_watcher')`
- 三处调用点全部改用它，删掉各自的私有实现和已死的日志常量

### core/errors.py —— 异常分类

改造前一个步骤失败了，调用方没办法知道该怎么办：watcher 拉子进程只拿得到
退出码和一坨 stdout，积木抛的多是裸 Exception。
于是「MineRU 这一秒过载了」和「你传的 key 根本不合法」走同一条路。

分类维度刻意**不是「哪里出的错」，而是「该拿它怎么办」**：

| 类 | 该怎么办 |
|---|---|
| `BadInputError` | 调用方传错了，重试没用 |
| `ConfigError` | 用户没配好，让他去控制面板 |
| `DataError` | 我们自己的数据坏了，要人来看 |
| `ExternalServiceError`（含 `ServiceUnavailable`/`RateLimited`） | **可以重试** |
| `AuthError` | 密钥问题，重试一万次也不会好 |

调用方只需要 `errors.is_retryable(e)` 一个函数。
保守策略：不认识的异常一律不重试 —— 宁可让失败暴露，也不要对着一个
永远不会成功的调用反复烧钱。

已采用：`core.paths.BadKeyError` 归入 `BadInputError`（同时仍是 ValueError，
旧代码 `except ValueError` 照样接得住）。各 adapters 在阶段 2 逐个改造。

## 2026-08-28 · 数据库方向③：structured → SQLite 查询库（pipelines/paper_db）

`compare.md` 是给人竖着看的一张表：不能筛、不能分组，
而且 `key_properties` 存的是 `'tensile strength: 12 MPa'` 这种人话 —— **机器比不了大小**。
于是「含硼、拉伸强度 > 10 MPa 的体系按动态键类型分组」这类问题永远答不了。

**新增 `pipelines/paper_db`**（SQLite，标准库，零新依赖）：

- `papers` 表：一篇一行，schema 每个字段一列 + `tier` / `source` / `si_used` /
  `schema_ver` / `is_review`
- `properties` 表：一条性能一行（`name` / `value` / `value_max` / `unit` / `cmp` / `raw`），
  由新增的纯逻辑 `domain.schema.parse_property()` 拆出来：
  `'Mn: 3.2×10^4 g/mol'` → 32000 g/mol；`'225–300 °C'` → 225~300；`'>20 times'` → cmp='>'
- **不做单位换算**：MPa 与 kPa 混着时宁可让人看见，查询按「名字 + 单位」一起筛
- `find()` 把常用筛法包好（关键词 / 档次 / 某字段真有值 / 某性能比大小），
  一次性分析直接 `query()` 写 SQL
- 命令行 `python 数据抽取/查询库.py --rebuild | --stats | --props X | --find X | --sql "..."`；
  抽取 CLI 跑完会自动 rebuild

**与 core/jobs 同一条约定：库是索引，不是真相。**真相是 `structured/<key>.json`，
所以只有整库重建、没有增量（省掉一整类「库和文件不同步」的 bug），
`query()` 也只接受 SELECT / WITH —— 不许有第二个真相来源。

在编程端唯一的金样本上实跑：1 篇 → 13 条性能数值，
`--find hydrogel --prop "fracture energy" --min 500` 能筛出来。
**真正的价值要等主力机重建**（175 条，含 `--si-pending` 重抽之后）。

验证：`pipelines/paper_db` 自测 7/7、`domain/schema` 14/14；pytest 195 全绿；离线体检 10/10。

## 2026-08-28 · 面板能看见「密钥被环境变量盖住」了（踩坑 #69）

今天的 401 不是密钥丢了，是三把旧密钥躺在**环境变量**里，

- `core.config.env_shadow(name)`：环境变量里那把的末 4 位、凭据库里那把的末 4 位、

- `core.config.clear_env_key(name)`：删掉用户级（HKCU）环境变量；
  系统级（HKLM）只报告不擅动；删完提示要重启服务（进程环境是启动时拷贝的）
- 面板：被盖住的密钥下面出现红条「你在这里填的新密钥被它盖住了」+
  「清除这个环境变量」按钮；`where` 显示为「⚠ 环境变量」而不再是灰色小字
- `core/config` 自测 +1 条（8/8）

**顺带修正一条我自己的错误结论**：上午我从 SSH 会话查环境变量、得出「环境变量是干净的」，
据此排除了这个原因。实际上 sshd 服务进程的环境是它启动时拷贝的，
用户后来 setx 的变量它看不见。**隔着一个会话查环境变量，查到的不是用户那份。**

## 2026-08-28 · 公众号种子 → DOI 对齐实测：**通了，91% 直接命中**

**背景**：方向层（"认清领域过去/现在/未来"）打算用「高分子学人」公众号推送当种子集 ——
它是有品味的人筛过的正样本。整条链的入口卡在一件事上：
**中文导读文章能不能自动对回原始论文的 DOI**。不通则整条路线作废，所以先测这个。

**样本**：主力机上已下载的 2026 年 6~8 月共 **228 篇** md（工具 `qiye45/wechatDownload`，
只勾 md、关图片；1695 篇全量还没下）。

**结果**（`adapters/openalex` 批量核对，40 个 DOI 一次请求）：

| | 篇数 | 占比 |
|---|---|---|
| 正文里直接抓到 DOI | 220 / 228 | 96.5% |
| 其中 **OpenAlex 真能查到** | **208 / 228** | **91.2%** |
| 靠英文标题再捞回（有噪声，需相似度阈值） | +6~9 | → ~94% |
| 根本不是论文推送（会议邀请×3、招聘×1、报到通知×1、营销号×1） | 6 | 2.6% |

**扣掉非论文推送后，真实对齐率 ≈ 97%。** 结论：**这条路通，可以往下建。**

**几条一并测出来的事实**：

- **DOI 里有非断行连字符**（U+2011），不换成 `-` 会白丢 3 篇 —— 提取时必须归一化
- **命中的 211 篇里 192 篇是 2026 年发表**：公众号给的是**当下切面，不是历史**。
  "过去"只能靠 `adapters/snowball` 后向雪球补 —— 两者分工由此确定
- **期刊分布**（前几名）：AFM 33 / AM 30 / Nat Commun 26 / CEJ 19 / Angew 10 / ACS SusChemEng 10。
  确认了公众号的取向：偏大刊、偏正面结果 —— 只能用来学"什么算好文章"，
  不能直接当领域地图（会只有山峰没有沼泽）
- 228 篇 ≈ 3 个月 → 1695 篇 ≈ 22 个月，全量种子集预计 **1450~1550 篇可对齐论文**

**外部工具调研的硬结论**：`wechat-article-exporter` **已于 2026-07-30 停止维护**
（依赖的公众号后台接口被微信关停）。目前可用的只剩 `wechatDownload` 一条路，
且抓密钥那步必须人工。**因此定下架构原则：公众号只是一次性种子源，
流水线产物只有 DOI + "被推荐过"这个标签，原文提完即弃** ——
既避开 README 的"仅供学习交流"限制，也让方向库不依赖随时会断的微信接口。

**同时修**：`docs/两台机器的分工.md` 里的 SSH 用户名记错（见踩坑 #74），已改为 `Administrator`。

## 2026-08-28 · 方向地图第一版跑通（211 篇种子 → 10 个簇），并发现一个会污染地图的陷阱

**做法**：211 篇已对齐的种子 → 拉全部参考文献 → **文献耦合**（bibliographic coupling，
按「共享参考文献」算 Salton 相似度）→ 标签传播社区发现（只用 numpy，跑 25 次取模块度最高的一次）。
探针在 scratchpad，未入库。

**规模**：9414 篇唯一参考文献 / 10860 条引用边。被引门槛切下来是一条陡峭的幂律：

```
被 >=2 篇种子引用 : 951      被 >=3 : 267      被 >=5 : 51
```

**骨架只有几百篇** —— 这本身就是一个不需要任何模型的重要性排序。

**结果**：模块度 0.398，40 个簇（10 个 >=3 篇）。簇是有意义的，
例如「聚酚/低共熔水凝胶黏合剂」45 篇、「木材/生物基黏合剂」24 篇、
「动态共价网络自修复」22 篇、「硫辛酸超分子」17 篇。

**⚠ 陷阱（本次最有价值的发现）：方法/工具类论文会造出假簇。**
CLUSTER 4（19 篇）把「有机发光」「阴离子传导膜」「原油分馏膜」聚在了一起 ——


（Multiwfn、PBE、DFT-D3、VASP 这类）。否则地图上会长出看不出错的假簇。

顺带一提：这类工具论文**本身是有价值的**（14 篇种子共引 Multiwfn，是全域第二高），
只是不能参与聚类 —— **该进「地基清单」，不该进「相似度计算」**。

**全域地基前几名**（被 >=5 篇种子共同引用，自动浮出，无人工干预）：

## 2026-08-28 · 修「方法类论文造假簇」：三个自动判据全部失败，真正有用的是换算法

接上一条。为了让 CLUSTER 4 那个假簇（有机发光 + 阴离子膜 + 原油分馏，
唯一共同点是都引了 DFT 工具）消失，试了三个**自动识别工具类论文**的判据，**全部失败**。
每个失败的原因不同，都值得记下来，因为它们看起来都很合理。

| 判据 | 想法 | 为什么失败 |
|---|---|---|
| **全球被引 >= 2 万** | 工具论文被引超高 | **轴选错了**。关键的那篇「电子波函数分析工具箱」只有 4688 次，够不着阈值；而 10890 次的聚多巴胺（真地基）差点被误伤 |
| **引用者主题熵高** | 工具被各种主题共引 | **指标饱和**。OpenAlex 给 211 篇种子分了 **69 个细粒度主题**，任何被 7 篇引的文献都横跨 6 个主题，熵一律 0.98。结果把 Leibler vitrimer、Gong 聚两性电解质、Suo 强韧水凝胶全判成了「工具」 |
| **参考文献自己属于语料没有的学科** | 工具是从别的学科借来的 | **OpenAlex 的学科归类噪声太大**。大豆蛋白胶被归到「营养学」、水凝胶电极被归到「神经科学」；而 Multiwfn 归在「Physics and Astronomy」，语料里恰好有极少数种子也在这个学科，没跨过门槛 |

**真正有用的是换算法，不是换判据**：标签传播 → **Louvain（带 resolution）**：

```
标签传播              模块度 0.398 | 簇 10 | 主题纯度 0.30   ← 会塌成 67 篇 / 53 篇的巨块
Louvain res=2.0      模块度 0.346 | 簇 22 | 主题纯度 0.35
Louvain res=2.5 +清单 模块度 0.340 | 簇 23 | 主题纯度 0.39
```

**判据**：
> 簇「塌成巨块」是**算法的分辨率问题**，不是数据脏。
> 先确认算法能给出合适粒度，再去怀疑数据 —— 我把顺序做反了，白跑三轮。

**工具清单最终还是用显式清单**（14 条，人工可审），它比三个自动判据都好（纯度 +0.02）。
但**必须存 OpenAlex ID，不能用标题正则** —— 本次正则就误伤了一篇硫辛酸共聚物论文。
「小、稳定、众所周知」的集合，手工清单胜过任何启发式。

**残留问题（未解决）**：假簇的三篇论文在所有配置下都只散到 2 个簇，没有完全拆开。

**结论：到此为止，不再调参。** 现在是在 211 篇（三个月切面、且黏合剂方向异常密集）上调，
再调下去就是过拟合到这个切面。等 1695 篇全量到位后用同一套代码重跑，届时再看要不要调。

## 2026-08-29 · 实测：方向层的四元组抽取，**本地模型够用**（3060 12G / Qwen3.5-9B）

**背景**：方向层的知识单元是「策略/结构 → 性能 → 应用 → 谁做的」四元组，
要从**摘要**抽（不是全文）。全量约 1 万条摘要，这是整条线唯一的实质成本 ——
所以先测本地模型能不能顶下来。

**环境**：主力机 RTX 3060 12GB · Ollama · `qwen3.5:latest`（9.7B，Q4_K_M，6.14 GB）。
这个模型是 Qwen3.5 小模型系列（2026-03-02 发布）的 9B，
BFCL-V4 函数调用 66.1（上一代 Qwen3-30B 只有 42.4）—— 结构化输出正是它的强项。

**样本**：30 篇真实抗冲击论文摘要（OpenAlex，含剪切硬化胶 / 聚脲防爆 / 弹道 /
仿贝壳 / 能量吸收五个子域），平均 1260 字符。用 Ollama 的 JSON schema 约束输出。

**结果**：

```
成功 30 / 失败 0        平均 3.8 s/篇
按此速度 10000 条摘要 ≈ 10.5 小时（一夜，免费）
```

**质量抽检（关键，不能只看成功率）**：

- 数值抽得准：`内部损伤降低 65% / 33%(10J) / >50%(20J)`、
  `剩余弹道速度降低 24.58%`、`弹道极限提升 27.86%` —— 带条件、带对照
- 策略抽得对：`nacre-like structure[structural]`、
  `polyurea coating position (front/rear face)[structural]`、`self-healing[interface]`
- **不相关论文能自己排除**：混进来一篇「控释肥包膜材料」（聚脲检索带出来的），
  `impact_relevant=False` 正确判定

**发现三个要修的（都是提示词/schema 问题，不是模型能力问题）**：

1. **综述类论文抽不出硬数据**：`strategies` 为空，`performance` 被塞进定性描述
   （"excellent quasi-static mechanical properties"）。
   → schema 要加 `doc_type`（research / review），且 performance.value **必须是数值**，否则丢弃。
2. 探针脚本里 `year` 全是 None —— `adapters.openalex.normalize()` 返回的字段名是
   `year` 而不是 `publication_year`，我在一次性脚本里写错了（只影响探针，不影响正式代码）。
3. Qwen3.5 用 JSON schema 时**推理内容可能混进 message.content 破坏解析**（上游已知问题），
   本次已用 `think:false` 预防，30 篇零失败。**正式实现必须保留这个参数。**

**判据**：
> **「本地小模型不行」这个印象来自图表数字化那次（7B 会编假数据）—— 那是读图。**
> 从文本摘要抽结构化字段是完全不同的任务：输出短、有 schema 约束、原文就在上下文里。
> **任务形状变了，结论就不能沿用。**

**结论**：方向层的全量抽取**用本地模型跑，零 API 成本**。
云端只在质量对照时用（几分钱量级），不进主流程。


### 同日补：30 篇全量体检数字 + schema 该怎么改

用户拍板「不用云端对照，太贵」，改为直接判质量。全 30 篇过一遍：

```
判为抗冲相关         22 / 30      ← 8 篇无关的（控释肥包膜、介电驱动器、人工韧带）正确排除
抽到应用场景         25 / 30
strategies 为空      12 / 30      ← 基本都是综述
performance 条目     43 条
  value 含数字       29 (67%)
  value 是定性描述   14 (33%)     ← schema 要禁掉
每篇平均抽到数值     1.0 条
一条数值都没有的     16 / 30
```

**策略分类没有塌进 other**（这是分类法有效的强信号）：
`structural 21 / composite 10 / interface 9 / molecular 5 / network 5 / processing 5`。

**结论分两半，别混着说**：

- **「谁做了什么 / 用了什么方法 / 用在哪」——够用，可以开工。**
  策略、应用、相关性判定三项质量都好。
- **「性能数值」——摘要天生稀疏，每篇平均只有 1.0 条。**
  这不是模型的问题：大量材料摘要根本不写数字，只写「显著提升」。

**但换个口径看，稀疏不等于不可用**：每篇 1 条 × 1 万篇 ≈ **1 万个数据点**。
做单篇的数值核对不够，做**一个领域的性能分布**绰绰有余 —— 而后者才是方向层要的。
真要做单篇级的数值核对，得上全文，那是**细节层**，用户已明确先不做。

**schema 四处要改**（都从这批数据里看出来的）：

1. 加 `doc_type`（research / review / perspective）—— 综述不该被逼着挤数字，
   但它的 strategies / applications 仍有价值
2. `performance.value` **强制数值模式**；定性说法移到单独的 `claims` 字段
   （不丢信息，但不污染数值层）
3. `metric` 给一份受控词表 + 自由文本兜底 —— 现在混进了
   「optimal coating position」「blast and impact protection」这种非指标
4. **加 `baseline` 字段** —— 实测发现抽到的数字**大多是相对改进而非绝对值**
   （「较未涂覆 CFRP 内部损伤降低 65%」「剩余弹道速度降低 24.58%」）。
   相对值带基准反而比绝对值更有用，schema 应当显式建模，而不是硬塞进 value。

**三条要改的**：

1. **从 `search=` 换成 `filter=title_and_abstract.search:"..."`** ——

3. **用引用网络剪枝**：定一个紧核心（剪切硬化胶 / 聚脲防爆），

**⚠ 暂时改不了：改完要重跑才知道效果，而 filter 查询要花额度，当前额度为 0**
（见踩坑 #77）。**卡在这里，等 API key 或 UTC 午夜。**

### 一、`search()` → `title_and_abstract.search`，质量翻倍

```
                    篇数    综述率   抗冲相关
impact （相关性）    2328     17%      37%
impact2（严格）       700      5%      67%
```

期刊也换了一批人：`Composite Structures` / `Int. J. Impact Engineering` /
`Composites Part B` / `Thin-Walled Structures` —— 抗冲工程真正的阵地。

**根因**：`openalex.search()` 是**相关性排序**，相关性受被引数影响，
于是把大刊综述和高被引泛论文顶上来。`title_and_abstract.search` 是**过滤器**，
词必须真的出现在标题或摘要里。

### 二、⚠ 计划中的第二条修法（按 type 排除综述）**根本不起作用**

试了才发现：OpenAlex 把标题里明写着 "A Review" 的论文也标成 `type: article`。

```
type 分布: [('article', 25)]
标题里带 review 的 2 篇，其中 type 被标成 review 的 0 篇
```

**幸好试了 —— 否则会上线一个什么都不做的过滤器，还以为综述已经排掉了。**
改成：综述**打标签而不是排除**（它们对「策略/应用」有价值，只是不该主导）。

### 三、两个附带修正

- **多词严格 AND 会塌**：`impact stiffening supramolecular elastomer` 只剩 1 篇。
  检索式要写成**术语级的两三个词**，不能沿用为模糊搜索写的长短语。
- **加 `primary_location.source.type:journal`**：不加会混进 SSRN / Zenodo 上的
  预印本（实测 32 篇），它们多是已发表版本的重复，会在引用网络里制造分身。

### 四、按用户重点拆成两条带子

**用户原话**：「抗冲这块应该是两个部分，一个是应用端的是这些工程期刊，
而要做机理发好文章应该还是高分子学人那类期刊，我其实更看重机理那块」
「我一般不会同时问机理和应用端」。

**数据支持拆分**：混合带子里机理侧只占 12%、工程侧 33% ——
**混在一起机理侧会被 3 倍体量的工程侧压死**，聚类出来几乎全是工程簇。

| | `impact_mech`（用户重点） | `impact_eng` |
|---|---|---|
| 问什么 | 什么新机制/新结构能实现什么性能 | 什么方案达到什么防护指标、用在哪 |

## 2026-09-01（傍晚）· 花钱的能力放开三个入口给模型，但每次强制弹窗

用户提的：「没必要把付钱功能完全不让 AI 操控，能不能开个用之前询问我的窗口」。
**他是对的，而且原来那条规则确实太粗。**

### 问题出在判据挑错了维度

原规则「花钱的一律不许当 MCP tool」用的是一个**布尔**（花不花钱），
而真正决定风险的是**代价量级 + 可不可逆**两个连续量。
于是「问一次库（几分钱、不写任何东西）」和「全库向量化（全库作业）」
被当成同一件事 —— 用户日常最常做的事反而最别扭（踩坑 #95）。

### 查证到的事实（不是记忆）

Claude Code 早就支持 `_meta["anthropic/requiresUserInteraction"] = true`：
打上它之后**每次调用都弹权限窗，且不给「不再询问」的选项**，
allow 规则绕不过去，`dontAsk` 模式下直接拒绝而不是偷偷跑。要求 ≥ 2.1.199，
本机 2.1.246。它恰好补上了原规则真正在防的洞 ——
不是「模型会调」，而是「用户点一次『总是允许』之后就再也不问了」。
（Claude Code 也完全支持 MCP elicitation，但那要改 stdio 的消息循环，这次没做。）

### 改成三档

| 档 | 例子 | 怎么暴露 |
|---|---|---|
| 单次、便宜、可重来 | `ask_library` `extract_one` `digitize_figure` | tool + 强制弹窗 |
| 全库作业 | 全库重抽/向量化、建方向图 | prompt（人点）|
| 不可逆写 Zotero | 删条目、批量改名、按 DOI 导入 | prompt（人点）|

**两道闸，缺一不可**：
1. `tool.toml` 的 `agent_tools` 白名单 —— 给人看的那道，加一个是显式动作
2. `confirm=True` → `anthropic/requiresUserInteraction` —— 给运行时的那道

⚠ 第 2 道是 **Claude Code 专有**（`anthropic/` 前缀），换客户端会被忽略。
所以 `role.require_prod` 那道机器角色闸**必须继续留着**，它不依赖任何客户端。

**deepread 故意留空**：精读一篇要跑几分钟，超过 MCP 约 60 秒的上限，当不了同步 tool；
而且用户本来就有更省事的路（在 Zotero 里打标签，常驻服务自动做完）。

### 验红验了三轮才验干净（踩坑 #96）

| 轮 | 漏了什么 | 为什么 |
|---|---|---|
| 一 | pytest 不查「注册了却不在白名单」 | 只写了正方向，**没写反方向** |
| 二 | `check()` 查不出「漏了 confirm」 | 传进 report 时拿**新造的空 server** 去查标记 |
| 三 | `check()` 查不出「白名单写了不存在的入口」 | 那条塞在 `if got.get('tool')` 里，没注册 tool 的走不到 |

### 排查过程本身值得记（踩坑 #97）

撞了三种失败，**每一种我都先误判了一次**，最后靠一个对照实验才分清：
去连一个**必定不存在**的 IP 的 22 端口 —— 它连不上，说明代理没伪造 TCP 握手，
问题在对面不在本机。我此前「路由被 singbox 劫走了」的判断是**错的**，
同网段网关一直通得好好的。

最终结论：ping 不通 + ARP `Unreachable` + TCP 22 偶尔能连上 + 连上又在
打招呼前断 = **B 在睡眠，被网络活动短暂唤醒又睡回去**。

### 诚实说明：「完全所有操作」做不到

**SSH 会话读不到 Windows 凭据库**（公钥登录建的是网络登录会话）。
所以精读、抽取、向量化这些花钱的作业从 SSH 发起，会在第一次调模型时废掉 ——
而且是跑到一半才废。这是技术限制，不是权限问题，改授权没用。

能远程做：拉代码、装包、pytest、离线体检、读日志读数据、重建索引、
改计划任务、重启服务。
不能远程发起：任何调付费 API 的作业。

**可能的绕法**：计划任务的登录会话能读凭据库（watcher 就靠这个跑花钱的活），
所以 `task <已注册任务名>` 也许能绕过去 —— **但这是推断，B 开机后必须实测**，
在那之前不许当结论用。`wake`（网络唤醒）同理，写的时候 B 一直睡着，没验过。

## 2026-09-03（三）· 查清跨网络组网方案 + remote.py 支持多候选地址

### 查证结果（都是查的，不是记忆）

| 方案 | 国内可用性 | 免费额度 | 结论 |
|---|---|---|---|
| Tailscale | 官方 DERP 中继**全在境外**，受干扰、不稳 | — | 要稳就得自建 DERP（买国内云服务器）→ **不合适** |

⚠ 这些是**文章里的说法，不是我实测的**。真正的验证只有装上去跑。

### remote.py 支持多候选地址

`B_HOSTS` 逗号分隔，局域网地址排前面（直连比走中继快），组网虚拟地址兜底。
**记住上次通的那个并优先试** —— 一个连不上的地址要等满 ConnectTimeout，
候选多了每次都从头试会让每条命令白等十几秒。实测：有记忆时 1.8 秒，
无记忆且死地址排前面时 11.7 秒，全不通时把每个地址各自的原因分别列出来。

### 顺手改掉一个「言之凿凿的错判」

`Connection closed` 那条诊断，第一版只写了「机器在睡眠」。
实测发现连一个**根本不存在**的地址也会被这么诊断 —— 真相是本机代理接管了连接。
改成两种可能都列，并给出能分清它们的判据（连一个确定不存在的 IP 试试）。
