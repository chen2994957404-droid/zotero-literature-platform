# 踩坑记录 · Pitfalls & Fixes

⚠ **本文件时间正序、体积很大。要看最新的坑请读文件末尾（tail），不要从头读，会白白吃掉上下文。**

> 这份文档记录搭建过程中遇到的每个问题、根本原因、解法。目的：换设备重装或后期审查时，知道"为什么这么做"，避免重复踩坑。按遇到顺序排列。

---

## 0. 起点：GPT 版为什么完全跑不起来

**现象**：n8n 工作流搭好了但一跑就崩。

**根因**（诊断出三个）：
1. **依赖服务没装**：工作流依赖 MineRU（解析）和 Ollama（总结），但实际只部署了 n8n 一个容器。Ollama 装了没启动且无模型；MineRU 根本没装。
2. **MineRU API 字段全靠猜**：GPT 没查真实 API 文档，节点里注释写着"字段名以官方真实返回为准"——一碰真实响应就对不上报错。还发明了一层不存在的 `task_id` 步骤。
3. **总结流是假演示**：输入写死成固定问题，根本不读解析结果。`test.txt` 是 DeepSeek 凭空答的，与 PDF 无关。

**教训**：API 集成必须先用真实数据实测拿到真实字段，不能靠猜。

## 1. MineRU：PUT 上传 PDF 返回 403 / SignatureDoesNotMatch

**现象**：申请到阿里云 OSS 预签名 URL 后，PUT 上传 PDF 报 403。

**根因**：预签名 URL 是**无 Content-Type** 签发的，但 HTTP 客户端（n8n、urllib）默认会自动加 `Content-Type: application/pdf`，导致签名不匹配。

**解法**：
- n8n：在 httpRequest 节点显式设 `Content-Type` 为空字符串。
- Python：不用 urllib（它强加头），改用 `http.client.HTTPSConnection` 手动 PUT，headers 传空 `{}`。

另注：预签名 URL **短时有效**，申请后要立即上传，隔太久会过期（也报 403）。

## 2. MineRU：轮询字段结构与 GPT 版完全不同

**GPT 版错的**：以为顶层有 `data.state`、`data.full_zip_url`，还要单独查 task_id。

**真实结构**（实测）：
```
GET /extract-results/batch/{batch_id}
→ data.extract_result[0].state  (running/done/failed)
→ data.extract_result[0].full_zip_url
→ data.extract_result[0].err_msg
```
没有 task_id 这一层。删掉 GPT 的节点7/8/9。

## 3. 本地大模型：3060 跑精读版太慢，不实用

**现象**：想用本地 Ollama 省 DeepSeek 额度，实测 qwen3:14b 和 8b 生成一篇精读都要 5 分钟以上。

**根因**：
- qwen3:14b + 16K上下文 超出 3060 的 12GB 显存，13% 溢出到 CPU。
- qwen3:8b 虽 100% GPU，但 3060 算力生成 8000 token 长文本身就慢。

**结论/分工**：精读版这种"要质量+长输出"的活交给 **DeepSeek**（一篇几分钱，2-3分钟，质量高）；本地模型只留给短任务（打标签、分类、向量化）。已在工作流里保留"模型切换开关"（改一个 provider 字段即可切），以后有更强模型可无缝换。

## 4. Ollama：模型"消失"——其实是环境变量指错路径

**现象**：`ollama list` 空的，以为模型没下载。

**根因**：环境变量 `OLLAMA_MODELS` 被设成了空的错误路径 `D:\AI\Models\Ollama`，而模型实际在 `D:\02_AI\models\Ollama\models`。Ollama 启动时读了错误路径所以"失明"。

**解法**：`setx OLLAMA_MODELS "D:\02_AI\models\Ollama\models"`，重启 Ollama。启动脚本里已固化这个设置。

## 5. n8n 容器里没有 Python

**现象**：想在 n8n Code 节点里用 Python 裁图，但 n8n 官方镜像是精简 Node 环境，没 Python。

**解法**：架构分两段——n8n 干它擅长的（MineRU解析、下载、落地文件），把裁图+精读交给宿主机的 Python 守护脚本。两者通过文件目录解耦。（后来 Zotero 闭环直接绕过 n8n，全用宿主机 Python。）

## 6. n8n Code 节点默认禁用 fs 模块

**现象**：Code 节点里 `require('fs')` 报 `Module 'fs' is disallowed`。

**解法**：docker-compose.yml 加环境变量后重启容器：
```
- NODE_FUNCTION_ALLOW_BUILTIN=fs,path
- NODE_FUNCTION_ALLOW_EXTERNAL=*
```

## 7. 图片被 MineRU 打散 / 摘要图混入 / 图没截全（最难的一个）

这是花时间最多的问题，分三个子问题，最终一起解决。

**子问题A：一个大 Figure 被 MineRU 拆成几张碎图。**
根因：学术论文一个 Figure 常是多子图拼成的大图，MineRU 按检测框切，会拆碎。
解法：不用 MineRU 输出的碎 jpg，改成**用坐标从原 PDF 重新裁完整 Figure**。

**子问题B：坐标缩放比例算错，图裁不全。**
根因：一开始用"所有图里最大的x值"当缩放基准（每篇不同、且不是真实基准），Figure 1 碰巧对、其他全错。
解法：读 `layout.json` 里每页的 **`page_size`**（MineRU 给的真实页面尺寸），bbox 与 PDF 是 **1:1 对应**，缩放 = 页面实际宽/page_size宽。这个对所有文献通用，一次调好永久有效。

**子问题C：数据图被漏掉。**
根因：MineRU 把图表类子图标成了 `chart`/`table` 类型，而非 `image`。脚本只收 `image` 就漏了。
解法：合并 `image` + `chart` + `table` 三种视觉块。

**子问题D：有些期刊题注识别不到，导致整篇丢图。**
根因：靠"Figure N 题注"归组时，某些期刊（如 Adv.Mater.）的题注 MineRU 没提取成文字，匹配不到就跳过全部图。
解法：改成**不依赖题注的鲁棒策略**——遍历每页，把视觉块按纵向间隔聚类成 Figure（间隔>页高15%就拆成不同图），题注能识别就用作caption，识别不了按顺序自动编号。这样题注失败也不丢图。

**最终方案**：`deepread_v4.py` 里的裁图逻辑，对不同期刊都通用。

## 8. Zotero：本地 API 只读，不能写

**现象**：Zotero 7 本地 API（localhost:23119）读文献很方便，但 POST 创建笔记报 `Endpoint does not support method` (400)。

**根因**：Zotero 7 本地 API 目前**只读**。

**解法**：读用本地 API（快、稳、不联网），写（回写笔记、改标签）用 **Zotero Web API**（api.zotero.org，需账号 API key，有写权限）。

## 9. Zotero：本地 API 请求被 PowerShell 拒 / curl 中文乱码

**现象1**：PowerShell `Invoke-RestMethod` 请求本地 API 报"连接被关闭"。
**解法**：本地 API 要求请求头带 `Zotero-Allowed-Request: true`。加上就通。

**现象2**：curl 管道读返回的 JSON，中文字符（如"等"）在 Windows 控制台被输出成 `??`，破坏 JSON 解析。
**根因**：curl → Windows 控制台的编码损坏，不是 Zotero 的问题。
**解法**：脚本里用 Python `urllib` 直接请求，不经过 curl 管道，无损。

## 10. Zotero：API 限流 429 + 重复处理

**现象**：watcher 跑起来后频繁 429 Too Many Requests，且同一篇文献被反复处理。

**根因**：
1. 轮询间隔太短（15秒），加上手动查询，触发限流。
2. 处理完没改标签，导致 `待精读` 文献被每轮重复捞出来处理。

**解法**：
- 轮询间隔改 60 秒。
- 处理完通过 Web API 把标签 `待精读` → `已精读`（状态机），不再重复。

## 11. 子进程输出编码错误

**现象**：watcher 用 subprocess 调 deepread 脚本，捕获输出时 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xca`。

**根因**：子进程 stdout 里有 GBK 字符，按 utf-8 解码失败。

**解法**：`subprocess.run(..., encoding='utf-8', errors='replace', env={...PYTHONIOENCODING:'utf-8'})`。

---

## 通用经验

- **Windows 控制台中文乱码**：贯穿始终的干扰。命令里设 `PYTHONIOENCODING=utf-8`、脚本文件用 utf-8、日志用 utf-8 写。看到的乱码多数是显示问题，不是数据问题——用文件工具读或让 Python 直接处理即可确认。
- **MCP 层调用有约60秒超时**：跑长任务（DeepSeek精读、模型下载）会超时，但进程在后台继续。用"发起后轮询文件结果"的方式，别干等。
- **一切外部 API 先用真实数据实测**：这是从 GPT 版失败学到的最重要一条。

## 12. 结构化抽取：性能数值列大面积 N/A —— 根因是 schema 字段太窄

**现象**：粗层抽取后 `compare` 表的 `key_properties`（性能数值）列大面积 N/A。
初判怀疑是「喂给模型的正文被截断」或「MineRU 丢了表格」。

**探针验证**（拿精读过、确定原文有数值的 AZJRUG6P 当基准）：
- full.md 里数值型关键词命中 24 处 → 数据在，MineRU 没丢
- 但 JSON 的 key_properties = N/A → 数据被挡在了抽取环节
- 定位：`key_properties` 字段说明只举力学例子（拉伸强度/自愈合效率），
  而这篇是「合成动力学+表征」论文，核心数据是 GPC 分子量/复数黏度，
  模型严格按 prompt 只找力学量 → 如实填 N/A（模型没错，schema 挡了数据）。

**三种 N/A 要分清**：①文献本身没有（正确）②抽取漏了（缺陷）
③schema 字段没给数据留位置（最隐蔽，本例即此）。

**解法**：放宽 `key_properties` 说明为「任何量化表征结果」，
显式列出力学/分子量/流变黏度/热稳定/电导率/灵敏度等并各给单位示例。
单篇重抽 AZJRUG6P 验证：N/A → 抽出 5 条正确数值（黏度 100,000 cSt、
Mn/Mw、反应后 rPBS Mn/Mw）。改动仅一处 prompt，零副作用。

## 13. 结构化抽取用本地 7B vs 云端 DeepSeek —— 抽取吃精度，7B 不够稳

**背景**：想省 API 费，试把抽取从 DeepSeek 换本地 Ollama。先给
`extract_structured.py` 加 provider 开关（`EXTRACT_PROVIDER=ollama`，
默认仍 deepseek），照搬 deepread 的 localhost:11434 + `format:json`。

**A/B 对比**（同一篇 AZJRUG6P，qwen2.5:7b-instruct vs deepseek-v4-pro）：
- 本地能跑、JSON 合法、字段修复同样生效
- 但质量明显差：DeepSeek 5 条数值全对；本地 4 条含 2 错——
  漏了初始黏度和反应后 Mn/Mw，还把 Mw 值 3.0 错配成「复数黏度 3.0 Pa·s」
  （看着像对、其实张冠李戴，是最危险的脏数据），self_healing 幻觉成 N/A，
  synthesis_conditions/key_properties 结构漂成嵌套字典。

**结论**：
- 向量化能用小模型（bge-m3 只做文本→向量映射，不涉理解）；
  抽取吃推理+精度配单位，7B 不够稳，脏数据混进全库难排查。
- 抽取是一次性成本（全库 177 篇跑一遍即完），DeepSeek 总费用极低，
  买的是数据干净。→ 抽取继续用 DeepSeek，本地模型留给向量化/精读。
- provider 开关已保留：换更大本地模型（如 32B）时设环境变量即可切。

**关联**：向量化 vs 抽取对 LLM 的要求完全不同——前者要 embedding 模型，
后者要长上下文+强指令遵循+结构化输出的生成模型，同一 Ollama 里是两个模型。

## 14. 认知错位：把「本会话新建的东西」当成「用户早先的既有资产」

**现象**：Claude 一路把结构化抽取线（extract_library/extract_structured/compare.md，
本会话 2026-07-24 从零新建）误当成用户早先建好的成熟系统去揣摩，
臆想「full.md 被清理了」「177 篇是 DeepSeek 抽的」等错误来历，反复走偏。

**根因**：
1. 动手前没先通读 docs（架构总览/数据契约/结构化抽取说明），走到哪读到哪。
2. 没记住「哪些是本会话刚产出的」，把新成果当考古对象去猜历史。

**实际状态（订正）**：
- 精读线、向量化问答线 = 用户早先建好的成熟资产。
- 结构化抽取线 = 本会话今天新建，刚跑通粗层（174 篇本地 qwen 免费抽）。
- 粗层零成本（本地 qwen2.5:7b）；精层才花钱（DeepSeek），且只给精选重点文献，
  「全库上 DeepSeek 重抽」本就不符合两级设计意图——之前追问此成本方向本身偏了。

**解法/规则**：
- 接手项目先通读 docs 再动手，别边探边拼。
- 明确区分「本会话产出」vs「既有资产」，前者是刚做的成果不是待考古对象。


## 15. find_pdf 误选补充材料去精读（Springer 的 MOESM/ESM 命名逃逸正则）

**现象**：给 CABSSMLA（A novel shear-stiffening… diboron）打「待精读」，
精读的却是补充材料 SI 而非正文。

**根因（两因素叠加）**：
1. `find_pdf` 的 SUPP_PAT 正则漏了 Springer/Nature 系 SI 的标准命名
   `40843_2023_2581_MOESM1_ESM.pdf`——MOESM(Electronic Supplementary Material)
   一个词都没命中原正则（suppmat|supp|supporting|supplement|-si-|_si_|si.pdf|appendix）。
2. 该 SI 恰好比正文大 9KB（2440 vs 2431 KB），在"非补充材料里选最大"这步 SI 胜出。

**易混淆点**：用户在 Zotero 里把该附件 title 改成了 "SI"，但没生效——
因为 find_pdf 读的是磁盘 filename（MOESM1_ESM.pdf），不是 Zotero 的 title 字段。
Zotero 本身没做正文/SI 判断，纯是脚本正则的漏洞。

**解法（两处，零副作用——只会让更多 SI 被正确排除）**：
1. SUPP_PAT 增加 moesm|_esm\b|electronic.?supplementary，覆盖 Springer/Nature 全系。
2. 同时把附件的 Zotero title 纳入判断（title 命中正则 或 title=="SI" 即判为 SI），
   尊重用户手动标注这一最可靠信号。

## 16. extract_library.py --rebuild 会连精层高质量结果一起覆盖

**现象**：粗层重抽用 `--rebuild` 时，本应「精层优先、已抽过就跳过」的保护失效，
连之前 DeepSeek 精层抽的好结果（如 2T6H4S3D 的 104.6 MPa 力学数据）也被本地 qwen 粗层覆盖降级。

**根因**：脚本里 `--rebuild` 的语义是「无条件重抽全部」，优先级判断只在增量模式生效；
rebuild 时跳过逻辑被绕过，精层记录一并被粗层结果盖掉。

**解法/规则**：
- 跑 `--rebuild` 前必先备份 structured 目录（本次已备份到 structured_bak_before_schema_fix）。
- 重抽完把精层篇（source 字段无 coarse 的、或已知精读过的 key）从备份还原回来。
- 更彻底的修法（待办）：给 --rebuild 加「仍跳过精层 source」的保护，或分离粗/精重抽命令。

## 17. 批量精读 401：deepread key 必须作命令行第5参，且 Start-Process 不继承临时环境变量

**现象**：新写的 deepread_batch.py 跑批量精读，12 篇全 401 Unauthorized，
但同一 key 直接 curl 测试有效。MineRU 解析/裁图都成功，只最后调 DeepSeek 时 401。

**根因（两个叠加，都是应用侧变更记录·认知2 记过的坑，设计侧又踩一次）**：
1. deepread_v4.py 的 key 靠**命令行第5参**传入，不读环境变量。batch 脚本却用
   subprocess env 传 DEEPSEEK_KEY，且误用了未定义的小写变量 key（实际传空）→ deepread 收到空 key。
2. PowerShell `Start-Process` 启动的子进程**不继承当前会话临时 set 的 $env 变量**，
   所以靠 $env:DEEPSEEK_KEY 也传不进去。

**解法**：
- deepread_batch.py 里把 KEY 作为第5个命令行参数传给 deepread_v4.py（不靠 env）。
- 运行时用 `cmd /c "set DEEPSEEK_KEY=xxx&& python ..."` 在同一进程内注入，
  别用 Start-Process + 外部 $env（不继承）。

**教训**：接手前该细读应用侧变更记录里已记的密钥坑——它明确写了「靠第5参、不读环境变量」，
我没照做又踩一次。呼应工单板「deepread 密钥应支持 .env 统一配置」的必要性。

## 15. 图表数字化：本地7B视觉模型会编造"等差数列"假数据（严重）

**现象**：用 qwen2.5vl:7b 数字化一张 FTIR 光谱图，输出的数据点是完美等差数列
（x 均匀+24，y 均匀-2，一路直线降到0），且标 confidence=high。

**根因**：FTIR 光谱本应是起伏的吸收峰，模型根本没真读图，而是编了一个"像数据的规律"
填充。这是视觉模型幻觉最危险的一种——一本正经胡说，还很自信。

**教训**：
- 本地 7B 视觉模型做**精确图表数字化不可靠**，会产生幻觉假数据。之前"找趋势够用"
  的判断过于乐观——连趋势都错（把光谱说成直线）。
- **凡是 LLM/VLM 抽的定量数据，必须能对照原图验证，不能盲信**（尤其 confidence 高时更要警惕）。
- chart_digitize 积木代码/接口是对的，但**当前本地模型下输出不可信**，暂不能用于真实数据采集。

**待解**：需换更强视觉模型（云端 qwen-vl-max / GPT-4o 等）实测，看精度是否够；
或加"多次采样取一致性 + 人工抽检"机制。在验证出可靠模型前，此积木标记为【实验性·勿信输出】。


## 16. 图表数字化：本地7B不可信 vs 云端大模型可信（对照实验决定性结论）

**对照**（同一张 CQSKX3BB 图，实为左FTIR+右TGA两图拼合）：
- 本地 qwen2.5vl:7b：把无Y轴数值的FTIR硬编成等差数列假数据，还 confidence=high（踩坑#15）。
- 硅基流动 Qwen3.6-27B / Qwen3.5-397B：都正确识别"有两个图"，明智地只数字化右边有数值
  刻度的TGA图、拒绝左边FTIR（note说明原因）；读出真实热分解曲线（平台→陡降→再平台），
  且有硼样品残重76% > 无硼66%，物理合理、印证"硼提热稳定性"。397B比27B更细（14点vs8点，
  捕捉到500°C陡降拐点）。

**决定性结论**：
- 图表数字化方法本身正确，之前失败100%是本地7B太弱。
- 大模型的关键能力：①判断图能不能读（拒绝不可读的）②读真实数据③给合理物理曲线。
- **模型分工**：图表数字化用云端大模型（硅基流动 Qwen3.5-397B 精度最高 / 3.6-27B 够用更快）；
  本地7B视觉模型不可用于此任务。

## 26. 弹窗问题的真正根因：任务计划的 -Hidden 对控制台程序无效

**现象**：上次"去掉 cmd 改直接跑 ollama.exe"后，开机仍弹窗（标题变成 ollama.exe 本身）。

**根因（关键认知）**：
- 任务计划的 `-Hidden` 设置**只隐藏任务本身**，不隐藏程序创建的控制台窗口。
- `ollama.exe serve` / `python.exe` 是**控制台程序**，无论怎么启动都会创建控制台窗口。
- 上次修法（去掉 cmd）只是把窗口标题从 cmd 变成 ollama，没解决问题。

**尝试与失败**：先写 VBS 包装器（WScript.Shell.Run(cmd,0,False)）——理论可行，
但实测 ollama 起不来（疑似 VBS 文件的 UTF-8 中文注释编码问题），遂放弃。

**最终解法（已验证）**：任务执行
`powershell.exe -NoProfile -WindowStyle Hidden -Command "Start-Process <exe> -ArgumentList serve -WindowStyle Hidden"`
双层 Hidden：外层隐藏 PowerShell 自己，内层隐藏被启动的控制台程序。
验证：ollama 进程 1 个、有窗口 0 个、服务正常 4 模型。

**同时加固 watchdog**：启动 watcher 时把 `sys.executable` 强制替换为 pythonw.exe
（双保险——即使看门狗本身被 python.exe 拉起，它启动的 watcher 也不会弹窗）。

**四类启动方式的窗口风险速查**：
| 执行程序 | 是否弹窗 |
|---------|---------|
| pythonw.exe | 否（Python GUI 版，推荐） |
| powershell.exe + `-WindowStyle Hidden` | 否 |
| python.exe / ollama.exe / cmd.exe | **是**（控制台程序） |
| GUI 程序（zotero.exe 等） | 否（正常显示自己的界面） |


## 踩坑 #27：DeepSeek V4 思考模式吃光 max_tokens，精读只剩图没有字

**现象**：2026-08 前后多篇精读质量骤降，HBCS74IC 整篇只有 7 张图、零文字；
4SPHXFL8 内容质量其实很好但明显被截断（写到一半戛然而止）。

**排查**：实测 deepseek-v4-flash + 50988 字符输入 + max_tokens=8000 → 返回 0 字符。
A/B 对照：同输入同模型，max_tokens 从 8000 提到 16000 → 输出 13779 字，正常。

**根因**：DeepSeek V4（Flash 与 Pro 都是）**思考模式默认开启**（`thinking.type=enabled`），
模型先生成推理链再生成正文，而**推理链 token 计入 max_tokens 额度**。
我们沿用 V3 时代的 max_tokens=8000，额度被推理链吃光，正文被 finish_reason=length 截断，
极端情况一个字都没输出。脚本又不校验输出长度，静默把「只有图」的空壳写盘并回写 Zotero、
打上「正文精读」标签 —— 于是这篇再也不会被重跑，废品永久留在库里。

**解法（三层）**：
1. `adapters/llm_client`：`chat()` 新增 `thinking` 参数（True/False/None随默认）；
   `_deepseek()` 检测 `finish_reason=='length'` 且正文<200字时直接抛 LLMError，不再静默返回半截。
2. `scripts/deepread_v4.py`：max_tokens 8000→32000 且默认关思考；
   两次尝试策略——先「关思考+32k」（快且省），不足则「开思考+64k」（更强）。
3. 加 `MIN_OK=3000` 底线：正文不足 3000 字直接 sys.exit 失败，**宁可不产出也不产出废品**
   （避免被误标成已精读而不再重跑，这是本坑真正致命的地方）。

**顺带修正**：输入截断从 40000 字符放宽到 150000。V4 上下文 1M token，
一篇正文 3~6 万字符完全放得下，原来的 40000 截断本身就在丢正文后半段（含结论与机理讨论）。

**教训**：换模型代际时，「默认行为」的变化比「参数名」的变化更隐蔽也更致命。
V4 的 API 模型名没变（仍是 deepseek-v4-flash/pro），所以代码「看起来不用改」，
但默认开思考这一条把旧参数配置变成了错误配置。
**推论：任何产出长文本的环节都必须有「输出长度底线校验」，不能信任 LLM 一定给东西。**


## 踩坑 #28：云端 API 的 5xx 抖动没有重试，长批量任务一撞就白跑

**现象**：修复 #27 后验证精读，连续多次调用返回 `HTTP 503 Service Unavailable`，
排查半天以为是自己加的 `thinking` 参数不被接受。

**辨别方法**：**4xx 是我们自己的错，5xx 是对方的错**。
参数写错会返回 400 并带错误说明；503 说明请求本身合法，是服务端过载。
这个判据能省掉大量「怀疑自己代码」的时间。

**解法**：`adapters/llm_client._deepseek()` 加退避重试——
429/500/502/503/504 重试 4 次（间隔 5s/10s/20s），其余 4xx 立即抛 LLMError 附带响应体。
实测退避 3 次后成功（总耗时 87.8s）。

**为什么这条重要**：用户目标是处理几千到几万篇文献。批量任务动辄跑几小时，
期间撞上一次服务端抖动是必然事件。没有重试 = 每次抖动白跑一篇（还要花掉已消耗的 token）。
**推论：所有跨网络的公理件都应内建退避重试，这是批量规模下的生存必需而非锦上添花。**


## 踩坑 #29：改了触发标签名，却要求用户记住新词 —— 打了标签没反应

**现象**：用户打了标签，等了很久精读没启动。日志显示 watcher 一切正常

## 踩坑 #32：子进程中文乱码 —— 长期被误诊为「PowerShell 显示问题」

**现象**：体检报告、日志里的中文长期是乱码。此前一直记为「PowerShell 控制台显示问题，
非数据问题」，用 Read 工具读文件即可 —— **这个诊断是错的**。

**真根因**：Windows 子进程默认按系统区域编码（中文系统 GBK）写 stdout，
而父进程按 UTF-8 解码 → 真的乱码，不是显示问题，数据确实被损坏了。

**发现过程**：给 subproc 写自测时，用 `pythonw`（无控制台）跑一遍，
中文测试直接失败，且自测自己打印中文时抛 `UnicodeEncodeError: 'gbk' codec`。
**是「换个环境再测一遍」把长期误诊揪出来的。**

**解法**：`subproc._env()` 给所有子进程注入 `PYTHONIOENCODING=utf-8` 与 `PYTHONUTF8=1`。
自测脚本自身也用 `TextIOWrapper` 强制 UTF-8 输出（它们可能被 pythonw 拉起）。

**教训**：
1. 「显示问题，不影响数据」这种结论要有证据，否则会掩盖真 bug 很久。
2. **测试要覆盖真实运行环境**。后台服务是 pythonw 跑的，只在有控制台的 python 下测，
   永远发现不了这类问题。


## 踩坑 #33：心跳正常 ≠ 工作正常 —— watcher 静默停摆 19 分钟

**现象**：用户重启电脑后问「有没有什么没跑起来」。查下来：

2. **保活任务不保活**：`auto_sync` 原本检测到 Zotero 没开只是「跳过本轮」，
   没有任何人负责把它拉回来。新增 `_revive()`：探活失败就通过任务计划拉起并复检。
   只拉起、不杀进程，是可逆操作，可以自动做。
   **叫「保活」就该真的保活，只会跳过的检查等于没有。**

3. **心跳设计本身有缺陷**：心跳写在 try 之前，所以「进程活着」和「工作正常」被混为一谈。
   面板新增故障告警栏，直接暴露「最后一条失败晚于最后一条正常」的情况，
   并单独探测 Zotero 给出直白结论。**只看心跳会被骗。**

**验证**：关掉 Zotero → 日志出现「[轮询失败] …（多半是 Zotero 桌面程序没开）」；
拉起后出现「[已恢复] 之前连续失败 1 轮」；auto_sync 实测 7 秒内自动拉起 Zotero；
面板告警栏在故障时出现、正常时消失。

**顺带**：给 ZoteroApp 的登录触发器加了 1 分钟延迟，避免开机时与其他启动项抢资源。

**通用教训：任何「存活指标」都要和「工作指标」区分开。**
心跳只证明循环还在转，不证明循环里的事做成了。


## 踩坑 #34：体检脚本自己在项目里造垃圾，还偷偷调用付费 API

**现象**：用户发现项目根目录反复出现一个叫 `b` 的空文件夹 —— 明明清理过，又回来了。

**根因链**：
1. `mineru_parse.py` **整个脚本写在模块顶层**，没有 `main()`
2. 体检的「运行时导入检查」为了验证脚本能加载，用假参数 `sys.argv=['x','a','b']` 执行它
3. 顶层的 `os.makedirs(OUT_DIR)` 于是用假参数 `'b'` 建了个目录
4. **更严重的是**：该脚本顶层还有真实的 MineRU API 调用 ——
   也就是说**每跑一次体检，都在真的消耗付费 API 额度**（只是失败得很安静）

**解法**：
- `mineru_parse.py` 重构：顶层只留常量与函数定义，所有副作用移进 `parse()` / `main()`
- 体检新增检测：加载脚本后若项目根出现 `a`/`b`/`x` 这类垃圾空目录，
  自动清理并报警 —— 这等于给「脚本必须能被安全 import」这条规范上了自动检查

**教训（两条，第二条更重要）**：
1. **检查工具不该有副作用。** 一个用来验证健康的工具，反过来污染环境甚至花钱，
   是最糟糕的一类 bug —— 因为它伪装成「正常运行」。
2. **能被安全 import 是脚本的基本素养。** 模块顶层只放定义，副作用一律进 main()。
   这不只是风格问题：它决定了这个脚本能否被测试、被复用、被静态检查。


## 踩坑 #35：中文检索式让全球文献召回质量崩塌

**现象**：接入 Sciverse 后，中文提问「聚硼硅氧烷的剪切硬化机理是什么，B-O 键起什么作用」，
召回的证据里 8 条有 6 条跑题 —— 硼硅玻璃辐照、炉渣稳定性、LTCC 陶瓷腐蚀、光催化，

**解法（两层）**：
1. `ask_world.py` 先用 LLM 把中文问题转成**英文检索式**再查（翻译很便宜，收益巨大）
2. 按相关度过滤，阈值 0.60 —— 宁可少给几条，也不要拿跑题片段污染答案

**效果**：同一问题重跑，8 条证据相关度**全部 ≥0.89**，全部对口
（剪切硬化涂层、防弹复合材料、智能抗冲击凝胶）；答案从两句话变成四个层次的机理分析。

**教训**：
1. **检索语言 ≠ 回答语言。** 项目原本就有「机器数据用英文、给用户看的用中文」的约定，
   这次发现它同样适用于**检索式** —— 中间环节一律用英文，只在最终呈现时转中文。
2. **接入新数据源必须用真实问题实测。** 如果只跑英文示例就上线，
   这个坑会等到用户用中文提问时才爆发，而且表现为「答得不好」而非报错，极难归因。


## 踩坑 #36：Sciverse 把补充材料当独立文献返回，9 条重复挤爆结果列表

**现象**：搜「polyborosiloxane dynamic boron-oxygen bond elastomer」，
25 条结果里第 8~16 条是**同一篇文章的 9 个补充材料文件**
（DOI 后缀 .s001~.s009，载体都是 Figshare，标题完全相同、被引全为 0）。
真正有价值的文献被挤到后面。

**根因**：Sciverse 收录了 Figshare 上的 SI 存档，并作为独立记录索引。

**解法**（放在 sciverse 积木层，上层无感）：
- `is_supplementary()`：DOI 匹配 `\.s\d{3,}$`，或载体是 figshare/zenodo 且零被引
- `dedupe()`：按归一标题去重，保留质量最优的一条
  （有真实期刊名 > 被引多 > DOI 短，因为正文 DOI 比 SI 的短）
- 过滤会减少条数，所以**多取一倍再截断**，保证用户要 20 篇就得到 20 篇

**效果**：同一检索从「17 条真文献 + 9 条重复」变为「17 条全是真文献」。

**教训**：**接入新数据源必须看完整的原始返回，不能只看前几条。**
前 7 条完全正常，问题藏在第 8 条之后 —— 只抽查头部就会漏掉。

**顺带自我纠错**：第一版 dedupe 我写了个用占位符维持顺序的绕圈实现，
写完发现自己都要读两遍才能确认对不对，随即重写成「keep best per key + 保持首次出现顺序」
的直白版本。**看不懂的代码就是有 bug 的代码，哪怕现在碰巧是对的。**


## 踩坑 #37：改 stdout 编码的写法有坑，程序跑到一半 print 崩掉

**现象**：`collect.py` 导入文献成功后，打印结果时抛
`ValueError: I/O operation on closed file` —— 事情做完了，却报错退出。
更糟的是用户会以为失败而重跑，**造成重复导入**（实际就发生了，库里多了一条）。

**根因**：我用的写法是
`sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8')`。
这会让原来的 sys.stdout 对象失去最后一个引用被 GC，析构时**关掉底层缓冲**，
于是新包的 wrapper 写不进去了。时机取决于 GC，所以表现为「有时好有时坏」。

**正解**：`sys.stdout.reconfigure(encoding='utf-8', errors='replace')`（Python 3.7+），
不换对象，只改编码。已统一修正 11 个文件。

**顺带修的两处**：
- PowerShell 管道传入的确认输入带 BOM（`\ufeff`），导致「明明输了 y 却被当成取消」。
  已在读输入时剥掉不可见字符。
- `collect.py` 导入前实时查一次库，DOI 已存在就跳过 —— **从源头防重复**，
  比事后清理省事得多（之前全库去重花了不少功夫）。

**教训**：**「功能做完了但收尾时报错」比彻底失败更危险**，
因为用户会重试，而重试会把有副作用的操作再做一遍。
凡是有副作用的流程，收尾阶段的健壮性和主逻辑同样重要。


## 踩坑 #38：只看「跟我的库像不像」不够，雪球一开就被高被引通用文献带偏

**现象**：接入雪球扩展后，候选从 45 篇涨到 182 篇（雪球独贡献 131 篇），
但**排在最前面的全跑题了** —— 被引 1117 的水凝胶综述、被引 363 的摩擦纳米发电机、
被引 483 的高熵合金纳米线，出现在「找聚硼硅氧烷剪切硬化」的结果第一页。

**根因（两层）**：
1. `relevance` 原本只算「与我整个库最近一篇的相似度」。用户库里有水凝胶、有能量收集，
   所以一篇水凝胶综述也能匹到 0.755。
2. **关键词检索的结果天然贴题（是搜出来的），雪球的结果不是** ——
   它只保证「跟种子有引用关系」，而一篇文章的参考文献什么方向都有。
   原设计在只有关键词检索时侥幸成立，雪球一开就崩。

**解法（两步，缺一不可）**：
1. `match_many(topic=...)` 增加「贴题度」：候选 vs **本次检索主题**的相似度。
   最终 relevance = **几何平均**(贴题度 × 近库度)。
   用几何平均而非算术平均：任一边低就明显拉低总分，
   算术平均压不住「跟主题无关但跟库沾边」这种情况。
2. 加**贴题门槛**（默认 0.45）：**高被引不能救一篇跑题的文献**。
   一篇贴题 0.31 的水凝胶综述，被引再多也不该出现在这个检索里。

**效果**：182 篇滤掉 79 篇跨方向的，剩 80 篇全部对口 ——
前五名变成 剪切硬化凝胶 / 抗冲击涂层 / 剪切致密化悬浮液(Nature) /
防弹复合材料 / 剪切硬化流变学。

**教训**：**新增一路数据源，会让原本"侥幸成立"的排序逻辑暴露**。
原来的相关度定义在单一来源下够用，多来源一混就失效。
加数据源时必须重新审视排序假设，不能只看数量涨了就以为成功。

**顺带**：输出里把 relevance 拆成「贴题 x / 近库 y」两个分数展示。
黑箱分数无法判断对错；拆开后一眼就能看出「为什么这篇排在这」，
这次的问题也正是拆开后才定位到的。


## 踩坑 #39：用户搜「PBS」，一次暴露三个 bug（缩写歧义 / 漏导入 / 阈值杀光结果）

用户在面板上搜「PBS」，一条真实使用就翻出三个问题，值得逐个记。

### bug 1：崩溃 —— `re` 用了但没导入

`discover.py` 的 `_key()` 里用 `re.sub`，而文件顶部没有 `import re`。
**语法检查和运行时导入检查都发现不了**：语法完全合法，模块也 import 得进去，
**只有那个函数被真正调用时才炸**。

解法：体检新增 `c_undefined_names()` —— 用 ast 收集每个文件「导入了什么」
与「用了哪些 模块.属性」，交叉核对常见标准库名。
已验证：故意造一个同样的错误，检查立刻报 `_tmp_bugtest.py:4 用了 re 但没导入`。

### bug 2：缩写歧义 —— 「PBS」被理解成铅锡焊料 / 钪钽酸铅

查询扩展把「PBS」扩成了 `Pb-Sn solder alloy`、`lead-free solder microstructure`；
复现时又变成 `lead scandium tantalate ferroelectric`。
**两次猜的还不一样 —— 说明纯靠猜是不稳定的。**

**讽刺之处**：我几轮前亲口说过「同样搜 PBS，材料人指聚硼硅氧烷、化工人指聚丁二酸丁二醇酯、
生物人指磷酸盐缓冲液，所以 API 层做术语扩展只会帮倒忙」——
**然后我自己写的扩展模块犯了同一个错。**

解法：`expand(context=...)` 接收领域上下文，由 `discover` 从**用户自己的库**里
取最相关的 5 篇标题传入。这正是本平台独有的信息 —— API 层和通用工具都拿不到。

效果对照（同一个「PBS」）：
| 无上下文 | 有上下文 |
|---|---|
| PBS lead scandium tantalate | polyborosiloxane shear thickening |
| lead scandium tantalate ferroelectric | polyborosiloxane hydrolysis |
| PST relaxor ferroelectric | polyborosiloxane nanosheets composite |

顺带修：LLM 偶尔吐出 `PBS" lead-free solder` 这种带引号的，只 strip 两端不够，改为全删。

### bug 3：贴题门槛把结果杀光 —— 「滤掉 144 篇，最终 0 篇」

贴题度是拿**用户原始输入**当基准算的。而「PBS」是三个字母的缩写，
向量本身没有语义，于是所有候选都判成不贴题，一篇不剩。

解法两条：
1. 贴题基准改用**全部扩展式拼起来**（`' ; '.join(queries)`）——
   扩展式集合才完整表达了「他到底想找什么」。雪球选种子同理。
2. **兜底自动放宽**：门槛把结果杀到不足 5 篇时，逐级降到 0.35 / 0.25 / 0，并告知用户。
   **内部阈值永远不该让用户看到「0 篇」** —— 那看起来像「这个方向没文献」，
   实际是我们参数不合适，**是最容易误导人的失败方式**。

**修复后**：搜「PBS」得到 88 篇（新的 75 篇），全部对口。

### 三条通用教训

1. **一次真实使用 > 十次自测。** 我用的测试词都是完整术语（polyborosiloxane…），
   永远碰不到缩写歧义；用户随手一个「PBS」全暴露了。
2. **自己说过的坑，自己也会踩。** 讲道理和落到代码里是两回事，
   凡是识别出的风险要当场问「我这段代码有没有这个问题」。
3. **失败要「响」。** 崩溃反而是好的（立刻发现）；
   「0 篇结果」这种安静的失败最危险，因为它看起来像一个合理答案。


## 踩坑 #40：通配符 `_*.py` 匹配到 `__init__.py`，一次删光全部 16 块积木

**事故经过**：清理我自己留下的临时脚本时，用了
`Get-ChildItem -Filter "_*.py" | Remove-Item` ——
`_*` **同时匹配了 `__init__.py`**，于是 `modules/` 下 16 个积木的入口文件全被删除。
整个公理层瞬间消失。

**恢复**：`git checkout -- modules/`，16 个文件全部还原，验证全部可导入。
**从发现到完全恢复不到一分钟** —— 这是本项目坚持「每个改动都 git commit」的直接回报。
如果没有 Git，这次要重写 16 个模块。

**教训（三条，一条比一条重要）**：

1. **删除类操作的通配符必须先 `ls` 再 `rm`。** 我直接把匹配结果管道给了 Remove-Item，
   连它匹配到了什么都没看一眼。正确做法：先列出来确认，再删。

   都是语言的核心约定。用下划线区分临时文件本身就是个危险的约定，
   应该用明确的 `_tmp` 前缀，且删除时精确匹配。
3. **不要把临时脚本写进项目目录。** 本次的根因是我图省事，把一次性脚本
   丢进了项目文件夹，才需要事后清理。临时文件应该写到系统临时目录，
   **根本不进项目**，也就不需要清理，也就不会有误删。

**配套改进**：`health_check.code_files()` 排除 `_tmp*` 等临时脚本名
（它们常由 PowerShell 生成、带 BOM，会让语法检查报无关的错），
但**明确不排除下划线开头的文件** —— 因为 `__init__.py` 必须被检查。


## 踩坑 #41：qwen3.5 本地聊天「卡死」——中文 system 消息极慢 + 思考模式 + 模型名没对齐

**现象**：llm_client 自测 ollama chat 404；改成 qwen3.5 后调用像卡死（60s+ 无返回）。
用户侧症状：控制面板打不开（另一条线，见变更记录）。

**根因**（三个叠加，逐个实测隔离）：
1. **模型名没对齐**：llm_client 默认 `qwen2.5:7b-instruct`，用户本地已更新成 qwen3.5
   → 404。且 llm_client 用 `os.environ.get('OLLAMA_MODEL')` 直读环境变量，
   **不看 .env**（extract_structured 用的是 config.get_key，能读到）——配置入口不统一。
2. **思考模式没关**：qwen3.5 是思考型模型，`stream:false` 下思考链期间全程静默。
   实测：中文 system 消息 + 默认思考 >90s；关思考后降到 ~44s。
3. **中文 system 消息本身就慢**（与思考无关）：实测对照——
   英文 system 5.8s / 英文 system+中文 user 18.8s / 中文 system 44s+（关了思考）~90s（不关）。

**解法**：
- `llm_client/_cfg()` 改用 `_cfg_get('OLLAMA_MODEL') or 'qwen2.5:7b-instruct'`
  （config 三级读取，.env 生效；`or 默认值` 兼容 config 导入失败的兜底 lambda）。
- `_ollama()` 的 options 固定加 `'think': False`：本地调用一律关思考（同
  `_deepseek` 长文关 thinking 的纪律）。
- `.env` 加 `OLLAMA_MODEL=qwen3.5:latest`（用户本地模型更新后的实际模型名；
  手改前已按面板惯例备份 `.env.bak.20260825`）。
- llm_client 自测的 system 消息改用英文（自测只验链路不验翻译），
  两处 ollama 调用从 90s+ 降到 ~15s 内，3/3 通过。

**教训**：① 模型名这类配置，读取必须统一走 config，不能有的地方读 .env 有的地方读裸环境变量；
② 换本地模型后要实测 chat 速度，思考型模型 + stream:false + 中文 system 是「假卡死」高发组合；
③ 「卡死」先分「真死锁（CPU 不动）」和「慢（CPU 在涨）」——CPU 在涨就不是死锁。

## 踩坑 #43：MCP 服务只把 stdout 设成 UTF-8，忘了 stdin —— 中文搜库全变乱码

**现象**：MCP 工具（`mcp__zotero__*`）用英文关键词搜库正常，用中文搜什么都搜不到，
且不报任何错。

**根因**：`mcp_stdio.py` 的【标准开头】只做了 `sys.stdout.reconfigure(encoding='utf-8')`，
**读进来的那一头没人管**。MCP 协议规定报文是 UTF-8，但 Windows 上 `sys.stdin` 默认
跟随系统代码页（本机 `sys.stdin.encoding == 'gbk'`），于是客户端发来的 UTF-8 被按 GBK 解码：

    发出 "聚硼硅氧烷" → 服务端读到 "鑱氱〖纭呮哀鐑" 之类的乱码 → 拿这个去搜 Zotero → 0 条

英文是 ASCII，UTF-8 与 GBK 编码一致，所以英文一直正常，问题被掩盖了很久。

**解法**：在 `serve()` 读 stdin 之前显式 `sys.stdin.reconfigure(encoding='utf-8')`。

**为什么自测没抓到（这条比 bug 本身更值得记）**：
`MCP服务/selftest.py` 的注释白纸黑字写着「不读真 stdin，手动调 `_handle`」——
它为了好写，**绕开了唯一出问题的那一段**。自测全绿，功能全坏。
**教训：自测如果绕开了真实的输入输出通道，它验证的就不是用户会走的那条路。**
凡是「为了方便测试而跳过的环节」，都要单独问一句：那一段谁来保证？

## 踩坑 #44：默认值选错，让单实例锁在最需要它的时候失效

**现象**：（潜在，尚未在生产触发）踩坑 #30 的双 watcher 有回归风险。

**根因一（默认值反了）**：`proc_lock._pid_alive()` 的注释写着
「判断不了时保守返回 True（宁可拦住，不可放两份进来）」，代码却是：

    return str(pid) in _out(['tasklist', ...], timeout=10, default='')

`tasklist` 超时或失败时 `out()` 返回 `default=''`，而 `pid in ''` == **False**
→「查不到」被当成「进程已死」→ 抢走锁 → 第二个 watcher 起来。
**契约写在注释里，实现却靠一个默认值悄悄推翻了它。** 改成 `default=None` 并显式判空。

**根因二（子串假匹配）**：`str(pid) in 输出` 是裸子串匹配，而 tasklist 输出带内存列
（形如 `45,678 K`），`pid=678` 会假匹配成「活着」。改用 `/FO CSV` 后匹配带引号的完整字段。

**根因三（先删后建的竞争窗口）**：`single_instance()` 原来是
「若锁文件存在就先 `os.remove`，再 `O_EXCL` 创建」。remove 到 create 之间的窗口里，
另一个进程可能刚建好自己的锁而被我们删掉，**两份都以为自己是唯一实例** ——
计划任务与看门狗同时开机启动，正好撞这个窗口。
改成：先抢建；撞到已存在的锁，确认是僵尸后用 `os.rename` 争夺接管权
（同一个源文件只可能被改名成功一次，输的那个拿到 `FileNotFoundError`），天然互斥。

**教训**：`default=` 不是随手填的语法噪声，它就是「失败时的行为」。
在安全/互斥类代码里，默认值必须往「保守」的方向倒。

## 踩坑 #47：「只绑 127.0.0.1」挡得住别的机器，挡不住你自己浏览器里的网页

**现象**：（潜在）控制面板的注释写着「只监听本机，外部访问不到」，据此没做任何请求校验。

**根因**：绑定 127.0.0.1 只能挡住**别的机器**，挡不住**你自己浏览器里打开的任意网页**——
那些页面同样跑在你本机。任何一个你随手打开的网站都能往 `127.0.0.1:8777` 发 POST：
`/api/config`（覆盖密钥）、`/api/restart`（重启服务）、`/api/search`（烧 API 额度）。
攻击者读不到返回内容（跨域），但**写操作照样生效**。此外 Host 头没校验，
DNS 重绑定可以把恶意域名解析到 127.0.0.1 来读 `/api/all`。

**解法**（三道判据，见 `panel.py` 的 `_guard()`）：
1. `Host` 必须是本机+本端口 → 挡 DNS 重绑定
2. 有 `Origin` 时必须是面板自己 → 挡跨站脚本
3. 写操作必须是 `application/json` → HTML 表单发不出这个 Content-Type，
   跨站 fetch 想发它会先触发 CORS 预检，而本服务不应答预检。
   面板自己的 JS 本来就带着它，对正常使用零影响。

**教训**：「本地服务」不等于「私密服务」。浏览器是一个所有网站共享的、能访问 localhost 的执行环境。

## 踩坑 #48：logging 的 Logger 是全局的，同名再取一次会把 handler 挂两遍（2026-08-26）

**现象**：给 `core/log.py` 写单元测试，单独跑每个都过，一起跑就有几个红 ——
日志文件根本没被创建，但 pytest 又确实捕获到了那条日志。

**根因**：`logging.getLogger('platform.xxx')` 返回的是**进程级全局单例**。
我原来的写法是：

```python
if not self._logger.handlers:      # ← 只看「有没有 handler」
    ...挂一个写文件的 handler...
```

于是有两种失败方式：
1. 已经挂着 handler（但指向的是**别的文件**，比如测试里换了临时目录）→ 跳过创建，
   日志写进了旧文件，新文件永远不存在。
2. 反过来，如果判断写成「每次都挂」，同名再取一次就会挂两个 handler，
   **每条日志写两遍** —— 这是 logging 最经典的坑，且极难发现（日志能用，只是重复）。

**解法**：不要按「有没有」判断，要按**「指向的是不是同一个文件」**判断：

```python
want = os.path.normcase(os.path.abspath(paths.log(name)))
for h in list(logger.handlers):
    if isinstance(h, RotatingFileHandler):
        if 同一个文件: have_file = True
        else: h.close(); logger.removeHandler(h)     # 目标变了，旧的没意义
if not have_file: ...挂新的...
```

**推广的教训**：任何「全局注册表 + 按名字取」的 API（logging、多进程锁、
连接池、缓存），判断「要不要初始化」时都不能只看「有没有」，
要看**「现有的那个是不是我要的那个」**。

**顺带**：这个坑是被单元测试逼出来的 —— 生产代码里它会表现为
「日志偶尔写两遍」或「换了日志目录不生效」，几乎不可能靠肉眼发现。
这是「阶段 0 先造安全网」的一个当场兑现的例子。

## 踩坑 #49：「模块能 import 成功」远不等于「代码没问题」（2026-08-26）

**现象**：阶段 1 把 `zotero_watcher` 的日志改成 `core.log` 时，顺手删掉了 `_LOG_DIR`。
当时的验证是「这个脚本能不能加载」——**通过了**。
但函数体深处还留着一行：

```python
heartbeat = os.path.join(_LOG_DIR, 'watcher_heartbeat.txt')
```

**如果就这么上线会怎样**：那行在 watcher 主循环里，负责写心跳。
它一 NameError，watcher 每轮都崩；看门狗收不到心跳就重启它 ——
表现为「服务莫名其妙反复重启」，而根因只是一个删漏的变量名。
排查时几乎不会往「上次重构删漏了一个变量」上想。

**为什么三道检查都没拦住**：
- 语法检查：`_LOG_DIR` 是合法标识符，语法完全正确
- 模块导入检查：那行在函数体内，import 时根本不执行
- 体检的「未导入的模块」检查：它只比对常见标准库名，不看局部变量

**根因**：Python 没有编译期。**函数体里的 NameError 只在那个函数被调用时才炸。**
所以「导入成功」这种验证，对「删改后残留的旧名字」这一整类问题是无效的。

**解法**：加了一条真正的静态检查 `tests/test_no_undefined_names.py` ——
用 ast 收集每个文件里「定义过的名字」和「用到的名字」，做差集。
它当场又抓出 `pipelines/lib_match` 里同类的一个（`sim` 被删了还在用）。

**同一天的第二个变种**（同一个根因的另一张脸）：
阶段 2 把 `modules/` 拆成四环时，批量改写的正则只匹配了**行首**的 import，
于是 `panel.py` 里两处**缩进在函数体内**的 `from modules import evalset` 漏掉了。
同样：模块能 import、语法也过，只有用户点开控制面板的「精读评价」那一栏才会炸。
为此又加了一条守卫：**项目内的 import 必须指向真实存在的包**（连函数体内的一起扫）。

**推广的教训**：
> **验证的强度必须匹配改动的性质。** 改的是「名字」（删变量、改包名、搬文件），
> 就必须用**能看见所有名字**的检查（静态分析），而不是「跑一下看看崩不崩」——
> 因为没被执行到的那条路径，跑一百次也不会崩。

## 踩坑 #50：部署 ≠ 把文件换掉 —— 常驻进程不重启就一直跑旧代码（2026-08-26）

**现象**：主力机 `git pull` + 双击「更新平台.bat」都成功了，
打开控制面板却**看不到新加的「机器角色」设置项**。

**根因**：控制面板是常驻进程，占着 8777 端口，内存里是**更新前**加载的代码。
`控制面板.bat` 每次都新起一个进程，但新进程绑不上被占用的端口，
`HTTPServer((HOST, PORT), Handler)` 抛 OSError 后**静默死掉**
（traceback 只进了 `平台管理/panel_launch.log`，用户看不见），
于是浏览器连上的还是那个跑着旧代码的老进程。

**为什么特别难查**：三件事全都「成功」了 —— pull 成功、体检全绿、面板打得开。
没有任何迹象表明你看到的是旧界面。用户唯一能观察到的现象是
「说好的新功能不见了」，很容易误判成「代码没写对」。

**同一个根因还有第二张脸**：watcher 也是常驻的（计划任务拉起）。
更新代码后不重启，它会一直跑旧逻辑，**而且同样毫无迹象**。
这比面板严重得多 —— 面板只是显示旧界面，watcher 是拿旧逻辑处理真实文献。

**解法**：
1. 「更新平台」不再只是 pull + 体检，而是加了两步：
   **停掉旧面板进程** + **重启 watcher 计划任务**。
   逻辑搬进 `平台管理/更新平台.py`（.bat 只剩瘦包装）——
   顺便解决自更新问题：Python 启动时已把整个文件读进内存，
   所以它可以安全地更新自己，本次用旧逻辑跑完、下次才用新逻辑。
2. **控制面板页面顶部现在显示代码版本**（git 短哈希 + 提交标题 + 工作区是否干净
   + 本面板进程的启动时刻）。「我看到的是不是最新的」从此一眼可辨。

**推广的教训**：
> **只要系统里有常驻进程，「更新代码」和「让新代码生效」就是两件事。**
> 后者必须显式做，而且要在部署脚本里做 —— 指望人记得重启，等于没做。
> 更要命的是这类失败**不会报错**，它只是安静地继续跑旧的。

## 踩坑 #51：把「生成物」放进版本库 = 每次拉取必冲突（2026-08-26）

**现象**：主力机 `git pull` 报

```
error: Pulling is not possible because you have unmerged files.
fatal: Exiting because of an unresolved conflict.
```

仓库卡在合并中间状态，拉不动也推不动。而运行端**没有 Claude Code 来解冲突**，
这是两机分工里最难受的一种故障。

**根因**：版本库里有三类文件是**两台机器都会改写**的：

| 文件 | 谁在改写 |
|---|---|
| `HANDOVER.md` | `交接.py` 生成 —— 而**控制面板上有个按钮**，两台机器的用户都会点 |
| `CLAUDE.md` | `交接.py` 会重写它的「结构」自动区块 |
| `workflow_data/_last_search.json` | 每次「找新文献」都重写 |

于是主力机只要点一次面板上的「生成交接文件」、或者搜一次文献，
就产生了本地改动；编程端那边同样的文件也在提交里被改过 —— **必冲突**。

**这不是 git 用法问题，是设计问题**：
> **进版本库的文件，必须只有一个生产者。**
> 多台机器都会改写的生成物和缓存，根本不该进版本库。

**解法**：
- `HANDOVER.md`、`_last_search.json` 移出版本库（`git rm --cached` + gitignore）。
  两者都可再生，各机本地留一份自己用即可。
- `CLAUDE.md` 留在版本库（大部分是手写内容），但 `交接.py` **只在编程端**
  重写它的结构区块；运行端点按钮只生成 HANDOVER，不碰 CLAUDE.md。
- 加两条守卫（`tests/test_architecture.py`）：
  一条禁止生成物被跟踪；**另一条反过来钉死 `evalset.json` 必须留在版本库** ——
  它是用户一条条打出来的精读评价，不可重建，版本库是它唯一的备份。
  只有前一条的话，下次很容易顺手把它也「清理」掉。

**追加一条根治**（同日）：给 `.gitattributes` 加 `merge=union`。

`踩坑记录.md` / `变更记录.md` / `待办与需求.md` / `.gitignore` 这几个文件，
两台机器都是**往末尾追加**，谁也没改谁的部分 ——
但 git 默认的合并算法看不懂这一点，照样判成冲突。
`merge=union` 的意思是「两边的行都留下」，正是这类文件想要的。

⚠ **只能对纯追加的清单/流水账用 union。代码绝不能用** ——
union 会把两边的行都保留，产出一个语法错误的缝合怪。

#50 是「更新了代码但常驻进程还跑旧的」，这条是「版本库里放了不该放的东西」。
共同点是**都只在两台机器的场景下才暴露**，单机开发时完全看不见。

## 踩坑 #52：PowerShell 的「当前位置」不等于 .NET 的「当前目录」（2026-08-26）

**现象**：给用户的解冲突命令报

```
未能找到路径 "C:\Users\Administrator\docs\踩坑记录.md" 的一部分
```

—— 明明人就站在项目目录里，`[System.IO.File]::ReadAllLines('docs\踩坑记录.md')`
却跑去用户主目录下找。

**根因**：PowerShell 的 `$PWD`（`Set-Location` 改的那个）和宿主 .NET 进程的
`[System.IO.Directory]::GetCurrentDirectory()` **是两个独立的东西**。
`Get-Content` / `Set-Content` 这类 cmdlet 用前者；
`[System.IO.File]` 这类 .NET 静态方法用后者，而后者通常停在进程启动时的目录。

实测证据（本机复现）：

```
PowerShell 当前位置: C:\Users\...\Temp\claude\ct2
.NET 当前目录      : D:\dev\zotero-literature-platform
```

**解法**：在 PowerShell 里调 .NET 文件 API，**路径一律先过 `Resolve-Path`**：

```powershell
$p = (Resolve-Path 'docs\踩坑记录.md').Path      # 先变成绝对路径再交给 .NET
[System.IO.File]::ReadAllLines($p)
```

**为什么还坚持用 .NET 而不是 `Get-Content` / `Set-Content`**：
PowerShell 5.1 的 `Set-Content -Encoding utf8` 会写 **BOM**；
而 `Get-Content` 在文件没有 BOM 时按系统 ANSI（中文 Windows 上是 GBK）读 ——
**中文会直接读坏**。只有 `[System.IO.File]` 配 `UTF8Encoding($false)`
才能做到「按 UTF-8 读、按 UTF-8 无 BOM 写」。

**教训**：**给用户的命令必须先在同样的环境里真跑一遍**，不能凭经验写。
这条命令我第一次给出去就是错的，用户替我踩了。
（这和宪法【零号判据】是同一件事：凭记忆写出来的东西看着对，跑起来才知道。）

## 踩坑 #53：用来修好环境的工具，自己被环境卡死（2026-08-26）

**现象**：主力机双击「更新平台.bat」，直接一行

```
ModuleNotFoundError: No module named 'core'
```

**根因**：主力机**从来没装过这个包**（阶段 0 把项目做成 Python 包时它一直没同步到），
而 `平台管理/更新平台.py` 顶上写着 `from core import paths, role` ——
可它要做的事情之一**正是装包**。自举死锁。

用户拿到的只有一行 ModuleNotFoundError，没有任何可行动的信息。

**同类问题还有一个**：`诊断报告.py` 也在顶层 import 了 `core`。
它是「出问题时才用」的工具 —— 环境坏了才需要它，

1. 这两个脚本改成**引导脚本**：模块顶层只用标准库，`ROOT` 自己从 `__file__` 算；

2. `诊断报告.py` 在包没装好时**照样出报告**，而且第一行就写清病因和修法：
   ```
   ⚠⚠ 项目包没装好，读不到本机配置：ModuleNotFoundError: No module named 'core'
       修法：在项目文件夹里跑一次  python -m pip install -e . --no-deps
   ```
3. 加守卫 `test_引导脚本不许在模块顶层import项目包`，防止复发。

**验证方式**：造一个会抛 ImportError 的假 `core` 包顶掉真的（`PYTHONPATH`），
真跑一遍两个脚本，确认降级路径都对 —— 而不是「看代码觉得没问题」。

**推广的教训**：
> **诊断工具和修复工具，必须比它们要诊断/修复的东西更健壮。**
> 判据很简单：问一句「**这东西在系统坏掉的时候还能用吗？**」
> 答不上来，它就还不是一个合格的诊断工具。

## 踩坑 #54：PowerShell 的输出是 gb2312，按 UTF-8 解码全是乱码（2026-08-26）

**现象**：主力机跑「更新平台」，第 3 步打出

```
ͣ������� PID=7304
```

本该是「停掉旧面板 PID=7304」。

**根因**：中文 Windows 上，PowerShell 写给管道的默认编码是 **gb2312**
（实测 `[Console]::OutputEncoding.WebName` → `gb2312`），
而我们 `subprocess.run(..., encoding='utf-8')` 按 UTF-8 解码。

**影响面比看起来大**：不只是新写的两个脚本 ——
`core/subproc.powershell()` 也一样，而**控制面板重启服务、体检查计划任务**
都走它。也就是说这个乱码一直都在，只是以前没人盯着看。

**解法**：在 PowerShell 脚本最前面把它自己的输出编码切成 UTF-8：

```python
_PS_UTF8 = '[Console]::OutputEncoding=[System.Text.Encoding]::UTF8; '
```

修在 `core/subproc.powershell()` 里，面板和体检自动跟着好；
两个引导脚本不能依赖 core，各内联一份（注释里写明了原因）。

## 踩坑 #55：`pip install -e .` 装完，**当前进程仍然 import 不到**（2026-08-26）

**现象**：「更新平台」第 2 步刚装完包，第 4 步问「本机是什么角色」还是读不到，
于是**跳过了重启服务** —— 而重启服务正是这个脚本存在的理由（见踩坑 #50）。
整条流程"成功"了，却什么也没做成。

**解法**：装完之后主动刷新

```python
importlib.invalidate_caches()
site.main()                      # 重新处理 site-packages 里的 .pth
if ROOT not in sys.path:
    sys.path.insert(0, ROOT)     # 兜底，效果等同 .pth
```

那一行 `sys.path.insert` 是全项目唯一被豁免的一处（引导脚本装包后自救），
用行尾 `# paths-exempt` 标记 —— 架构守卫当场就抓过我一次：
**豁免标记必须写在同一行**，写在上一行的注释块里不算数。

## 踩坑 #57：「固定睡 N 秒再打开」永远只是在赌（2026-08-26）

**现象**：主力机双击「控制面板.bat」，浏览器报
「127.0.0.1 拒绝了我们的连接请求」。但面板其实马上就起来了，刷新一下就好。

**根因**：`控制面板.bat` 是「启动面板 → `timeout /t 2` → 开浏览器」。
那个 2 秒是**猜的**。机器慢一点、首次导入慢一点，浏览器就赶在服务器绑好端口
之前打开了。

**更糟的是另一半**：面板**真的**起不来时，用户什么也看不到。
`panel_launch.py` 老老实实把 traceback 写进了 `平台管理/panel_launch.log`，
但没人知道该去看那个文件 —— **一个没人会去看的日志等于没有日志**。

**解法**：新增 `平台管理/打开面板.py`，`控制面板.bat` 瘦成一行调用。
它做三件事：
1. **轮询到真的连得上为止**（最多 30 秒），而不是睡固定时间
2. 面板已在跑就直接开，并提醒「刚更新过代码的话它跑的还是旧代码」（踩坑 #50）
3. 起不来时**直接把 `panel_launch.log` 的尾巴打在屏幕上**，
   连同常见原因（端口被占、包没装好、代码有错）—— 不让用户去猜、去找文件

**教训**：
> **凡是「等某个东西就绪」，就去查它到底就绪了没有，不要睡一个猜出来的时间。**
> 睡得短了必然偶发失败，睡得长了每次都白等 —— 而轮询两者都不占。

**同一天的第二个教训（给接手 LLM 的）**：

这次修 `更新平台.py` 时，我用 `s.replace(old, new)` 做批量替换却**没加断言**，
锚点因为转义问题没匹配上，替换**静默变成了空操作** ——
我以为改好并推送了，用户跑起来才发现根本没生效（输出里还是旧的「完成。」）。

> **每一次程序化改写，都要断言「它确实改到了」。**
> `assert old in s` 一行的成本，远低于「以为改好了、其实没有」带来的一轮往返。
> 这和踩坑 #49 是同一个母题：**验证要针对改动本身，而不是针对你以为的结果。**

## 踩坑 #58：界面上改得动、保存了、却存不进去（2026-08-27）

**现象**：主力机在控制面板把「机器角色」从 dev 改成 prod、点保存、
刷新之后**又变回 dev**，而且没有任何报错。

**根因**：`panel.action_save_config()` 的白名单只写了两类：

```python
updates = {k: v for k, v in payload.items()
           if k in KEY_NAMES 或 k in MODEL_SETTINGS}     # ← 少了 SITE_SETTINGS
```

页面渲染是三类都渲染的（密钥 / 本机设置 / 模型），**保存时却把「本机设置」
整类静默丢弃**。也就是说 `ZOTERO_STORAGE`、`OLLAMA_MODELS` 这些
一直都存不进去，只是以前用户都直接改 `.env`，没人从面板存过。

**为什么这类 bug 特别毒**：三件事都"正常" —— 输入框能改、点保存有成功提示、
页面也不报错。用户唯一能观察到的现象是「我改的东西没生效」，
而这最容易被归因成「是不是我操作错了」。**静默丢弃比报错危险得多。**

**解法**：
- 白名单补上 `SITE_SETTINGS`
- 顺手把面板那张卡分成三段小标题（密钥 / 本机设置 / 模型）——
  用户反馈「顶上没有本机设置」，其实它混在同一片输入框里找不着
- **机器角色改成下拉框**：它是枚举值，手打就可能拼错，
  而 `role.current()` 对非法值一律按 dev 处理 —— 拼错会**静默降级**，
  又是一个不报错的坑。下拉框从源头消灭它。

**验证方式**：真调一次 `action_save_config`，改一个无害的设置项
（`OLLAMA_HOST`），确认 `.env` 里真的写进去了再还原。
**刻意没拿 ROLE 做写入测试** —— 这台是编程端，把它写成 prod 哪怕一瞬间，
也等于短暂解除了「不许写 Zotero」的保护。

**教训**：
> **「能显示 + 能编辑」不等于「能保存」。** 凡是界面上可改的字段，
> 都要有一条真的走到底、并回读确认的测试 —— 光看页面渲染对了没用。

**现象**：控制面板的「密钥·本机设置·模型」整张卡片只剩两个字：`NaN`。

原来的第一项本来就没有前导 `+`（它是第一项），我却按「后续项」的样子插了进去。

**真正该骂的不是这个手误，而是我没验证**：

## 踩坑 #60：Windows 控制台的编码，在三个地方分别咬人（2026-08-27）

同一个「代码页」问题，换三张脸出现，各要各的解法。前两个是实测复现的。

### ① PowerShell 的**输出**（已记于踩坑 #54）

中文 Windows 上 PowerShell 写给管道的默认编码是 gb2312，
我们按 UTF-8 解码 → `停掉旧面板` 变成 `ͣ�������`。
**解**：脚本开头 `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8; `

### ② `clip` 的**输入**

`clip.exe` 按**当前控制台代码页**读 stdin。我们喂 UTF-8 进去，
出来就是 `鏍囪...` 这种典型的「UTF-8 被当成 GBK 读」的乱码。
用户拿到的诊断报告整份都是乱码，等于白跑一次。

**解**：不用 `clip`，改走 PowerShell —— 先把报告写成 UTF-8 文件（本来就要写），
再让 PowerShell 读回来放进剪贴板，全程 Unicode：

```powershell
Get-Content -LiteralPath '<文件>' -Encoding UTF8 -Raw | Set-Clipboard
```

实测：138 行中文一字不差。

### ③ `.bat` 里的**非 ASCII 字符**

`诊断报告.bat` 里有几行 `echo   ────────────`（U+2500 制表符），
cmd 报

```
'��───────────────────────────────' is not recognized as an internal or external command
```

即使前面已经 `chcp 65001`，cmd 解析批处理文件时对多字节字符仍会失步 ——
它把整行当成了一条命令名。

**解**：**.bat 里只写 ASCII**。所有给人看的中文提示交给 Python 打印 ——
Python 的 stdout 编码我们能控制（标准开头就在做这件事），cmd 的解析器我们控制不了。

**推广的教训**：
> **凡是「文本要跨进程边界」，就要显式说清两边用什么编码。**
> Windows 上默认值到处不一样（控制台 gb2312、文件 UTF-8、剪贴板 UTF-16），
> 靠默认值一定会在某处对不上 —— 而且**乱码不会报错**，只会安静地毁掉输出。

## 踩坑 #61：看门狗一直在杀**正在干活**的 watcher（2026-08-27）

**怎么发现的**：主力机第一次交出完整诊断报告，看门狗日志里一个月重启约 **20 次**，
而且绝大多数是 `心跳已 3xx 秒未更新（>300）` —— **整整齐齐卡在阈值附近**。
真的死机不会长这样。

**根因**（代码里核实，不是猜）：心跳只写在轮询循环的开头。

```python
while True:
    写心跳                    # ← 只有这里写
    for it in 待处理文献:
        process_item(it)      # ← 精读一篇：解析 + 9000 字生成 + 裁图 + 回写
    time.sleep(60)
```

精读期间**一次心跳都不写**，而精读一篇远不止 5 分钟。
于是只要有文献在精读，看门狗几乎必然把它杀掉。

**代价**：被杀那篇已经花掉的 MineRU + DeepSeek 调用作废，下一轮重来再花一次。
系统看起来「能用」，是因为杀了会重试、总有一轮能在 5 分钟内跑完 ——
**这正是它一直没被发现的原因**。

> **更正（同日）**：我当时推测库里那 4 篇「缺核心产物」的文献是被杀出来的半成品。
> 查证后**不成立** —— 它们 `fulltext` / `layout` / `summary` 全都有，只缺 `meta.json`，
> 精读其实做完了。这提醒了两件事：一是**推断要标明是推断**，
> 二是**看到证据要立刻改口**，别让一个顺手的解释固化成事实。

时间线也对得上：08-04 `18:19` 重启 → `18:20`、`18:23` 各完成一篇 → `18:25` 又重启。

**根子上：一个信号回答不了两个问题。** 看门狗想知道的其实是两件事：

| 问题 | 信号 | 谁写 | 超时意味着 |
|---|---|---|---|
| 进程还活着吗？ | `watcher_heartbeat.txt` | **后台线程**，每 30 秒 | 死了/冻住了 |
| 还在往前推进吗？ | `watcher_progress.txt` | 每完成一件实事 | 活着但空转 |

原来的单心跳把两件事混成一个，于是「正在忙」和「已经死了」长得一模一样。

**解法**：新增 `core/heartbeat.py`，后台线程报活 + 显式记进度；
看门狗改看两个信号（报活 300 秒 / 无进展 45 分钟），
判断做成纯函数 `verdict()` 以便直接测。

**验证**（不止跑单元测试）：造了一个真子进程，起后台报活线程后「精读」15 秒
完全不报进展，把报活阈值压到 4 秒观察 ——
全程判定「不动」（**旧逻辑在第一次检查就会杀它**）；
随后杀掉子进程，6 秒内被正确判定为需要重启。

**教训**：
> **一个信号只能回答一个问题。** 当你发现同一个指标既要表示「活着」
> 又要表示「在推进」，那它一定会在某种情况下给出错误答案。
>
> 另外：**「一直能用」不等于「没有 bug」**。这个 bug 存在了至少一个月，
> 每天都在烧钱、留半成品，而表面现象只是「服务偶尔重启」——
> 直到把日志完整看一遍才暴露。**定期真的读一次日志，别只看红绿灯。**

## 踩坑 #62：重启计划任务换不掉 watcher —— 它是**孙子进程**（2026-08-27）

**现象**：「更新平台」明明打印了 `ZoteroLiteratureWatcher 已重启`，
但对比前后两份诊断报告：**看门狗 PID 变了（27512 → 36536），
`zotero_watcher.py` 的 PID 一模一样（12292）**。
也就是说 watcher 从头到尾没被换掉，刚修好的心跳代码**根本没生效**。

**根因**：进程是三层的。

```
计划任务 ZoteroLiteratureWatcher
   └── watchdog.py          ← 停/起任务只换掉这一层
         └── zotero_watcher.py   ← 看门狗 spawn 出去的独立进程，任务管不着
```

看门狗只在「判定它死了」时才重启 watcher。而老 watcher 活得好好的、
心跳照写，新看门狗当然不会动它。于是新代码静静躺在磁盘上，一行没跑。

**这类错误最难发现的地方**：所有输出都是成功的 ——
任务重启成功、体检全绿、心跳正常。**没有任何迹象表明新代码没生效。**

**解法**（两步缺一不可）：
1. 「更新平台」显式杀掉 watcher 进程（按 `*zotero_watcher*` 匹配，并排除自身）
2. **杀完要清掉它的心跳/进度信号文件** —— 否则刚被杀的进程留下的是**新鲜**心跳，
   新看门狗会认为「它还活着」，得等满 300 秒才发现没人干活。
   清掉之后看门狗一上来就判「信号缺失」，当场拉起新代码。

**还加了一条「让它看得见」**：诊断报告现在分别显示两个信号。
旧版 watcher 只写心跳、不写进度 —— 所以**进度信号缺失 = 它还在跑旧代码**，
一眼就能看出来。这次正是因为看不见这一点才漏掉的。

**教训**：
> **「重启了服务」不等于「新代码在跑」。** 只要进程是被别的进程拉起来的，
> 重启它的父亲就换不掉它。部署之后要有一个**能直接观察到版本**的办法 ——
> 靠「我重启过了」来推断，迟早会错。

## 踩坑 #63：面板上改配置，**没点保存就被自动刷新冲回去了**（2026-08-27）

**现象**：控制面板「机器角色」选成 `test`，一会儿又变回 `dev`。
反复几次都一样，看起来像「保存不进去」或「这个值不被接受」。

**排查**：`.env` 的修改时间停在几小时前 —— **说明保存请求根本没带上新值**，
不是写盘失败。后端白名单、`set_keys`、CSRF 守卫全都正常。

**根因**：面板每 15 秒 `load()` 一次刷新状态，而 `load()` 里
把整个配置区 `$('#cfg').innerHTML = ...` **重画一遍**，
重画时每个控件的值都取自「服务器上已存的值」。
于是用户选了 `test`、还没来得及点保存，15 秒内就被刷成 `dev`；
点保存时提交的自然也是 `dev`。

**为什么难查**：三处表现都指向别处 ——
① 看起来像后端拒绝了 `test`（其实后端根本没收到）；
② 真有一个同名的老问题（踩坑 #58「白名单漏了导致存不进去」）在旁边，
   极易先入为主地往那儿想；
③ 15 秒的间隔恰好长到让人以为是自己点错了、短到不容易观察出规律。

**解法**：配置区**只在首次加载和保存之后**重画（`cfgReady` 标志 + `load(true)`），
不参与周期性刷新。状态区（服务、心跳、日志）照旧每 15 秒刷。

**判据（比这个 bug 本身更重要）**：
> **自动刷新只能重画「用户不会在里面输入的区域」。**
> 只要一块界面里有输入框、下拉框，周期性重画就等于在替用户撤销他的操作。

顺带修掉同一族的另一处：面板顶部的角色标签也是前端写死 `prod`/`dev` 两档，
`test` 会被显示成「编程端(dev)」。改为直接用后端给的 `role_label`。

## 踩坑 #64：**问本地 API「我刚传上去的东西在不在」，答案永远是「不在」**（2026-08-27）

**发现方式**：测试端（独立 Zotero 账号）第一次真跑回写链路 —— 上线以来
这一段在编程端从来没跑过，一跑就露。

**现象**：上传 summary 附件成功，紧接着再问一次「这篇有没有 summary 附件」，
`find_existing_summary` 返回 `None`。

**根因**：写走的是 **zotero.org 云端 API**，查走的是 **Zotero 桌面的本地 API**。
本地 API 反映的是桌面端**已经同步下来**的状态，比刚写上去的东西滞后几分钟。
于是「复用已有附件条目」这条防线在同步窗口内失效 —— watcher 会**再传一份**，
产生重复的 summary 附件，正是踩坑 #28 当初要防的东西。

**为什么一直没暴露**：真实使用中，同一篇被重新处理通常隔了很久，
早就同步完了。只有「刚处理完又立刻重跑」才会撞上 —— 而这恰恰是**测试时的常态**。

**解法**：`adapters/zotero_client` 加 `zweb()`（云端只读 GET）与
`find_child_attachment()`：**先问云端，云端不可达再退回本地**。
退化的代价（可能多建一个附件）远小于「整篇精读白做」。

**判据（值得记住的是这一条）**：
> **自己刚写上去的东西，要问权威方，别问缓存/副本。**
> 一个系统里同时存在「权威源」和「本地副本」时，
> 读的用途决定该问谁：给用户看 → 问副本（快）；
> **判断自己的写有没有生效 → 必须问权威源**。

**顺带**：这个洞让适配层第一次需要读云端，于是架构守卫「每个写 Zotero 的地方
都要有机器角色守卫」会误伤它（它只读不写）。做法不是简单加白名单，
而是**加白名单 + 加一条新守卫**：`_READONLY_WEB` 里的文件不许出现
POST/PATCH/PUT/DELETE。开了口子就得有东西守着口子。

## 踩坑 #65：SI 精读的 token 额度是正文线的 1/5，于是「有时成有时败」（2026-08-27）

**现象**：同一篇文献的 SI，上午跑成功了（5223 字），下午重跑却报
「输出被 max_tokens=6000 截断且正文近乎为空」。

**根因**：`si_deepread` 一直用 `max_tokens=6000`，而正文精读线早就是
**32000 起 + 两级重试**（那正是血泪教训第 1 条：**DeepSeek V4 的推理链计入
max_tokens**，给少了会把正文挤没）。SI 这条线从来没跟着改 ——
输入长度一浮动就翻车，看起来像玄学。

**为什么长期没被发现**：SI 通常比正文短，6000 大多数时候够用；
失败时 watcher 只打一行「[SI精读失败]」，正文精读照常产出、标签照常换成
「正文精读」，用户看到的只是**这篇没有 SI 那一节** —— 而他并不知道本该有。

**解法**：给 SI 线同款额度阶梯 `(16000, 32000)` + `MIN_OK=800` 底线，
不达标就加大额度重来，两次都不行才判失败、**不写废品上盘**。

**判据**：
> **同一类调用，别在两条线上用两套参数。**一条线上的血泪教训，
> 要么抽成公共实现，要么至少让参数长得一样 —— 否则修好的那条会掩盖没修的那条。

顺带一提，这个 bug 是被**状态库**送到眼前的：失败被记成 `si_summary/failed`，
下次跑时「上次没成功 → 自动重做」，重做时带上新额度就成了。
在此之前，失败只存在于一行滚过去的日志里。

## 踩坑 #66：主力机的密钥早就失效了，而体检一直是绿的（2026-08-28）

**发现方式**：第一次能从编程端 SSH 进主力机之后，顺手验了一下三把密钥。

**现象**：主力机上
- DeepSeek 密钥 → **HTTP 401，无效**
- Zotero API key → **HTTP 403，无效/已撤销**
- 而 watcher 心跳正常、完整体检 15 通过 0 失败、面板一切正常

**也就是说：这台机器早就精读不了、也回写不了，但所有仪表都显示健康。**
只有等用户下次打「待处理」标签、发现「怎么没反应」，才会暴露 ——
而那时他看到的是一个没有原因的沉默。

**根因**：体检那条「配置加载」只检查 `get_key()` **读不读得到**，
不检查**这把钥匙还能不能开门**。

> **「配置存在」不等于「配置有用」。**
> 一个只查存在性的健康检查，查的是「我们有没有填过」，
> 不是「它现在还好不好使」—— 而后者才是用户关心的唯一问题。

**解法**：三个适配层各加一个**零成本**的有效性探针，体检新增一条「密钥有效性」：
- DeepSeek：`/user/balance`（顺带报余额，快没钱时能提前看见）
- Zotero：`/keys/current`（顺带回答**这把 key 属于哪个账号** ——
  「key 是 A 账号的、配置写的是 B 账号」这种错法症状也是 403，光看密钥查不出来）
- MineRU：拿一个不存在的 batch id 查结果，**401 vs 200 就能区分认证问题**
  （实测确认：有效 token 返回 200 + `task not found or expire`）

**连带发现的第二个坑**：密钥加载顺序是「环境变量 → 凭据库 → .env」，
主力机那两把失效密钥躺在**用户级环境变量**里。
这意味着用户就算在控制面板里重填一遍（写进凭据库），
**也会被环境变量里的死值盖住，且没有任何提示**。清掉环境变量才生效。
→ 已记入待办：面板保存密钥时应检测同名环境变量并警告。

## 踩坑 #67：用户重新打标签，watcher 看得见却一动不动（2026-08-28）

**用户实测撞上的**：一篇文献先只有正文 → 打「待处理」→ 精读成功 → 标签变「正文精读」。
然后**给它补了 SI，再打一次「待处理」—— 一个多小时毫无反应。**

**日志长这样**（最能说明问题的是「看得见」这件事）：

```
10:19:43  [状态] 待处理 → 正文精读        ← 第一次，成功
10:25:44  [心跳] 轮询正常，待处理 1 篇     ← 用户重新打了标签
   ...    [心跳] 轮询正常，待处理 1 篇     ← 持续 75 分钟，一行「[发现]」都没有
```

**根因**：轮询循环里有个 `seen` 集合，**同一个 key 处理过一次就永远跳过**
（直到 watcher 重启）。它想防的是「回写失败 → 标签没换掉 → 每 60 秒重跑一次烧钱」，
但它同时挡掉了**用户重新打标签**这个明确请求 ——
而「先精读正文，后来补 SI，再打一次待处理」正是 `文献精读/CLAUDE.md` 里
写明的核心用法（「已有正文精读 + 有SI → 只补SI，标签升级为全文精读」）。

**为什么所有测试都没发现**：这个 bug 不在任何一步的逻辑里，
而在**「什么时候该调用这些逻辑」**这一层。而那一层当时没有测试 ——
它藏在 `while True:` 循环中间的一个 `continue` 里，
既不是函数、也没有名字，测不着也看不见。

**解法**：把判据提成一个纯函数 `should_process(key, version, seen, now)`，两条判据满足其一：
1. **条目变了**（Zotero 的 `version` 字段每次改动都变）—— 用户改标签就是明确请求
2. **距上次尝试超过 30 分钟** —— 给「上次没做完」一个自愈机会，不必等重启

不怕重跑烧钱：每一步都幂等（`core.jobs` + 产物检查），重跑一篇已完成的只花几百毫秒、
零 API 调用。**幂等做扎实了，「宁可多跑一次」才敢成为默认选择。**

**判据（比这个 bug 本身更值得记）**：
> **去重要按「事情有没有变」，不能按「我做过没有」。**
> 后者会把用户的重新请求当成重复请求 —— 而用户重新提交，
> 恰恰说明他知道有什么变了。

顺带：这也是为什么「调度层」必须有自己的测试。逻辑层测得再全，
只要「什么时候调用它」写在一个匿名的 `continue` 里，就永远没人验证过。


## 踩坑 #68：合成条件全是 N/A，因为抽取从来没打开过补充材料（2026-08-28）

**现象**：175 条结构化记录里，`synthesis_conditions` 精层只有 36% 有值、粗层只有 5%。
而这恰恰是用户最需要的字段 —— 想比较「谁用什么配比做出了什么性能」，比不了。

**一开始的猜测**（错的）：提示词不够严、模型不够强、正文预算截断太狠。
这三条都能自圆其说，也都能改，但改完也不会好 —— 因为料根本不在锅里。

**根因**：`pipelines/extract.extract_one()` 只读 `paths.fulltext(key)`（正文 full.md）。
**论文正文本来就不写投料量** —— 期刊把「多少克、什么配比、多少度多久」全放进补充材料。
平台其实早就把 SI 解析成 `si_parsed/full.md` 了（SI 精读那一步做的），
就摆在同一个文件夹里，抽取从来没去读。

**解法**：抽取时把 SI 一起喂进去（`schema.si_body()` 取合成相关章节 +
配方线索密度最高的段落），自检也照「正文+SI」查。金样本上 4 个 N/A 字段一次全填上了。

**判据（比这个 bug 值钱）**：
> **一个字段大面积是空的，先问「料给全了吗」，再问「提示词/模型行不行」。**
> 前者是零成本的排查（看一眼读了哪些文件），后者是要花钱试的调参。
> 我们差点先做后者。

**连带**：由此才发现对比表把粗层和精层混在一起且看不出区别 ——
空白格分不清「本来没有」还是「没抽到」，于是「有值率」这类元信息
必须印在表里（同日一并做了）。


## 踩坑 #69：面板里填了新密钥，跑起来还是旧的那把（2026-08-28）

**现象**：用户在控制面板里把三把密钥都重填了一遍，DeepSeek 官网上看密钥也是有效的，
可 28 篇重抽全部 401，面板「测一测密钥」三把全红。用户的第一反应很合理 ——
「是不是脚本把我新填的密钥弄掉了」。

**根因**：不是弄掉了，是**被盖住了**。加载顺序写在 `core/config`：

    环境变量 → 系统凭据库 → .env

用户很久以前用 `setx` 往环境变量里塞过三把密钥。后来密钥换了，
新的填进了凭据库，**但环境变量那份排在前面，永远赢**。
从面板远程读到的真相是这样的：

    DEEPSEEK_KEY   | *******7984 | 环境变量     ← 真正在生效的（已作废）
    ZOTERO_API_KEY | *******g7LZ | 环境变量
    MINERU_TOKEN   | *******sio9 | 环境变量
    SCIVERSE_KEY   | *******Q2ps | 系统凭据库   ← 唯一没被盖住的

**为什么排查绕了一圈**：我先从 SSH 会话里查环境变量，`get_key` 返回空，
于是我下了「环境变量是干净的」这个结论 —— **错的**。
sshd 服务进程的环境是它自己启动时拷贝的，用户后来 `setx` 的变量它看不见；
而用户双击 .bat 是从资源管理器起的，环境是新的，拿得到。
**同一台机器上，「哪个进程」不同，环境变量就不同** —— 隔着一个会话查环境变量，
查到的不是用户那份。

**解法**（这条待办 2026-08-28 早上刚记下，当天就咬人了）：
面板现在显式识别遮蔽 —— `core.config.env_shadow(name)` 返回
「环境变量里那把的末 4 位 / 凭据库里那把的末 4 位 / 是不是同一把」，
面板把它画成一条红条：「**你在这里填的新密钥被它盖住了**」，
旁边一个「清除这个环境变量」按钮（`clear_env_key`，删 HKCU\Environment，
系统级只报告不擅动）。删完要重启用到它的服务 ——
**进程的环境变量是启动那一刻拷贝的，改注册表不会追进已经在跑的进程**。

**判据**：
> **配置有优先级时，界面必须显示「现在生效的是哪一份」，而不只是「你填了什么」。**
> 用户看到的是自己填的值，系统用的是另一份 —— 这种界面天生会骗人，
> 而被骗的人一定会先怀疑自己或怀疑脚本，最后才怀疑到「加载顺序」。


## 踩坑 #70：从 SSH 远程启动的后台作业，SSH 一断就死（2026-08-28）

**现象**：在 A 机用 `Start-Process ... -WindowStyle Hidden` 从 SSH 会话里启动主力机上的
批量重抽，日志停在「[1/28]」再不动，回头一看**那个 python 进程根本不在了**。

**根因**：Windows 上 sshd 给每个会话建作业对象（job object），
会话结束时整棵进程树跟着被回收。`Start-Process` 只是不阻塞当前 shell，
**并没有把新进程移出那棵树**。所以远程发起的长任务，SSH 一断就没。

**能远程做什么、不能做什么，到这里就清楚了**：

| | 远程（SSH） | 主力机自己的会话 |
|---|---|---|
| git pull / pytest / 体检 / 读日志 / 重建查询库 | ✅ | ✅ |
| 要密钥的作业 | ❌ 读不到凭据库（踩坑 #66 的连带发现） | ✅ |
| **跑得久的作业** | ❌ **断线即死（本条）** | ✅ 窗口开着就行 |

**解法**：长任务一律走「用户双击一个 .bat」这条路（`docs/两台机器的分工.md` 第四节
本来就这么定的）。`重抽缺SI的文献.bat` 现在会问一句「用云端还是本地模型」，
选完就在自己的窗口里跑，跑多久都不怕。

**判据**：
> **别把「我能远程发起它」当成「它能远程活下来」。**
> 长任务要活，得挂在一个不会被回收的会话上 —— 要么用户自己的窗口，要么计划任务。


## 踩坑 #71：面板的「重启服务」按钮从来没生效过（2026-08-28）

**现象**：密钥换新之后要重启 watcher（进程的密钥是启动时读的），
调面板的 `/api/restart` 返回失败：

    Restart-ScheduledTask : 无法将「Restart-ScheduledTask」项识别为 cmdlet…

**根因**：Windows PowerShell 5.1 的 ScheduledTasks 模块里**没有 `Restart-ScheduledTask`
这个 cmdlet**。只有 `Stop-ScheduledTask` 和 `Start-ScheduledTask`。
面板上那个「重启」按钮从写下的那天起就没工作过 —— 没人发现，
是因为平时重启服务都靠重启机器或双击 .bat，从来没人回头看那个按钮的返回值。

**解法**：改成 `Stop-ScheduledTask -ErrorAction SilentlyContinue` 再 `Start-ScheduledTask`
（Stop 对没在跑的任务会报错，吞掉它，只认 Start 的结果）。

**判据**：
> **按钮返回 False 而界面只弹一句 toast，等于没人会发现它坏了。**
> 凡是「点了就没下文」的动作，要么把失败原因显示出来，要么就别做成按钮。
> 这和踩坑 #66（密钥「读得到」不等于「有用」）是同一类：
> **验证要验到「事情真的发生了」，不能停在「命令发出去了」。**


### 踩坑 #71 续：重启了任务，干活的那个进程根本没换

修好 `Restart-ScheduledTask` 之后，重启依然不生效 —— 因为**计划任务启动的是看门狗，
watcher 是看门狗 spawn 出去的独立进程**。`Stop-ScheduledTask` 停的是看门狗，
watcher 照跑不误（心跳一秒没断），于是它一直揣着启动那一刻读到的旧密钥。

新看门狗起来后也不会动它：看门狗只在「心跳超时/无进展」时才重启 watcher，
而这时候心跳是新鲜的 —— 对崩溃恢复是对的，对「换了配置要重启」是错的。

**解法**：`action_restart` 按 `core.proc_lock.holder('watcher')` 拿到真正干活那个
进程的 PID，连它一起停，再启动任务。

**判据（和上一条同源）**：
> **「重启服务」要重启的是干活的那个进程，不是启动它的那个。**
> 有看门狗/启动器的系统里，这两者天然不是同一个 —— 而按钮的名字会让你以为是。


## 踩坑 #72：同一个 .bat 里，前一条命令好好的，后一条报「找不到指定的路径」（2026-08-28）

**现象**：用户双击「重抽缺SI的文献.bat」，窗口一闪而过说「完成了」，
日志里只有 44 个字节：

    The system cannot find the path specified.

而这个 .bat 的**前半段是好的** —— 它用同样的写法
（`python 数据抽取\extract_structured.py --si-pending --list`）成功列出了 28 篇。
只有标签 `:run` 之后那条几乎一模一样的命令失败。远程复现，稳定重现。

**根因**：`chcp 65001`（UTF-8）+ .bat 里有标签（`:run` / `goto`）。
cmd 执行标签跳转时**按字节偏移重新定位文件指针**，而它对多字节字符的记账在
UTF-8 代码页下是错的 —— 恢复读取的位置落在某个汉字的半截上，
后面那条命令就被截成了残缺的路径。于是同样的命令，在标签之前能跑、之后不能跑。

**为什么排查绕了远**：我先怀疑密钥、怀疑我正在 `git pull` 改文件、怀疑重定向、
怀疑 PATH 里的 python —— 全都单独验过，全都正常。
**决定性的一步是「把前后两条命令的差异缩到只剩标签」**：
前一条能跑、后一条不能跑，而两者唯一的区别就是中间那个 `:run`。

**解法**：中文和交互全部搬进 Python（`数据抽取/重抽向导.py`），
.bat 只剩三行、没有标签、没有 `set /p`：

```bat
chcp 65001 >nul
cd /d "%~dp0"
python 数据抽取\重抽向导.py %1
```

**判据**：
> **.bat 只配当一个「双击入口」，不配当程序。**
> 但凡要分支、要循环、要读用户输入、要拼中文路径 —— 立刻交给 Python。
> cmd 在 UTF-8 下的行为不可靠，而它出错的方式（前半段正常、后半段离奇）
> 极难联想到编码。


## 踩坑 #73：注册表里的旧密钥删掉了，双击出来的程序拿到的还是旧的（2026-08-28）

**现象**：面板显示三把密钥都来自「系统凭据库」、点「测一测」三把全绿、
watcher 重启后日志也写着「DeepSeek 有效，余额 6.45 CNY」。
可用户双击重抽，28 篇**全部 401，而且报的还是那把作废的旧密钥（末位 7984）**。

**根因**：`clear_env_key` 把 `HKCU\Environment` 里的旧值删了，但**没有广播
`WM_SETTINGCHANGE`**。而 `explorer.exe` 的环境是它自己启动那一刻拷贝的 ——
它不知道注册表变了，于是**用户双击出来的每一个程序，继承的都是那份旧环境**。

面板和 watcher 之所以显示正常，是因为它们是我从别处重启的（拿到了干净环境），
而用户双击的窗口是 explorer 的孩子。**同一台机器上，同一把密钥，
「谁启动的」不同，读到的值就不同** —— 这是今天第二次栽在这件事上（前一次是 SSH 会话）。

**解法两层**：
1. `clear_env_key` 删完广播 `WM_SETTINGCHANGE`（explorer 会据此重读环境）
2. `core.config.drop_stale_env()`：跑作业前，**本进程内**丢掉那些「和凭据库对不上」的
   密钥环境变量 —— 两边都有值且不同才丢，所以「用环境变量临时覆盖」这个正当用法不受影响。
   重抽向导与抽取 CLI 都在开跑前调它。
3. 顺带：向导现在**开跑前先验一把密钥**。上一版一头扎进去，
   烧了 28 次失败才发现密钥不对 —— 一次自检 2 秒，能省下 28 次无用调用。

**判据**：
> **环境变量不是「机器上的一个值」，是「每个进程各自的一份快照」。**
> 改了它，必须回答：**哪些进程还揣着旧的？** —— explorer 几乎总在这份名单里，
> 而它恰恰是所有双击操作的父进程。

## 踩坑 #74：SSH 连不上主力机，把「计算机名」当成了「用户名」（2026-08-28）

**现象**：从编程端 SSH 主力机，一直 `Permission denied (publickey,...)`。
公钥明明在、`known_hosts` 对得上、TCP 22 通、主机密钥一致 —— 看起来就是「钥匙被换了」。
于是花了两轮去补 `authorized_keys`、修文件属主与 ACL、重启 sshd，**全部无效**。

**根因**：用的用户名 `吧啦吧啦` 是主力机的**计算机名**，不是账号。真实账号是 `Administrator`。
`docs/两台机器的分工.md` 最初把 `whoami` 的输出 `吧啦吧啦dministrator` 记成了用户名，
之后所有人（包括我）都照着这条错记录连。

**为什么绕了两轮**：`Permission denied (publickey,password,keyboard-interactive)` 这条报错
**对「用户不存在」和「公钥不对」是同一句话** —— 客户端侧根本区分不了，
所以从 A 机怎么看都像密钥问题。

**决定性证据只在服务端日志里**：

```
sshd: Invalid user 吧啦吧啦 from 192.168.123.228
```

`Invalid user` = 账号不存在，与公钥无关。在主力机上一条命令就能看到：

```powershell
Get-WinEvent -LogName OpenSSH/Operational -MaxEvents 12 | Select TimeCreated,Message
```

**解法**：

```bash
ssh -i ~/.ssh/id_ed25519_zotero_b Administrator@192.168.123.216 "<PowerShell 命令>"
```

**判据**：
> **认证失败时，客户端的报错只是「没让你进」，不告诉你「为什么」。**
> 别在客户端侧反复试错 —— **服务端日志是唯一能区分「你是谁不对」和「你的钥匙不对」的地方**，
> 第一轮就该去看它，而不是第三轮。

**顺带两条 Windows/SSH 的实测**（这次一并踩到）：

1. **中文路径的文件没法 scp**：`remote readdir(...): Bad message`。
   Windows 的 sftp-server 处理非 ASCII 文件名会直接失败。
   绕法是在主力机上先 `Compress-Archive` 成一个 **ASCII 名字的 zip**，再 scp 那一个文件。
2. **远程命令里别嵌套双引号**：主力机默认 shell 是 PowerShell，
   `\"` 转义穿过两层 shell 后必炸（`TerminatorExpectedAtEndOfString`）。
   远程命令内部一律用单引号；`&` 也不能用（PowerShell 不认），用 `;` 分隔。

## 踩坑 #75：种子被「太重要」踢出了聚类 —— 主键覆盖把 120 篇降级（2026-08-29）

**现象**：方向地图落库后跑聚类，相似度矩阵只有 **634×634**，而种子明明有 754 篇。
不报错、不缺数据、日志全绿，只是**输入悄悄少了 120 篇**。

**根因**：`works` 表以 OpenAlex id 为主键。build 先插种子（`is_seed=1`），
再插骨干参考文献（`is_seed=0`）。而**种子和参考文献本来就会重叠** ——
一篇种子被其他种子引用 >=3 次，就同时出现在两边。后写的那行把 `is_seed` 覆盖成了 0。

**为什么这个坑特别毒**：被降级的**恰恰是被同行引得最多的那 120 篇**，
也就是这个领域最核心的论文。「越重要越容易被踢出去」，
而且失败形式是安静的 —— 聚类照跑、结果照出、纯度看着还行。

**发现方式**：只有拿真实数据实跑才看得见。自测里的假数据种子和参考文献没有重叠，
**全绿通过**。

**解法**：插参考文献时跳过本身就是种子的（种子那行信息更全，有 topics、
referenced_works、推送日期）。抽成独立函数 `direction_map.ref_rows_for()` 以便离线测试。

**判据**：
> **主键覆盖是一种安静的数据丢失。** 往同一张表写两类语义不同的行时，
> 先问一句：**它们的 id 会不会撞？撞了以后谁赢？**
> 这里「谁赢」的答案原本取决于 executemany 的顺序 —— 没人写下来，也没人测。

**顺带一条测试教训**：第一版补的回归测试只往 edges 表插了一条边，
**根本没走到出 bug 的那段逻辑**，照样全绿。
把出 bug 的代码抽成一个可以单独调用的纯函数，才是能真正测到它的前提。

## 踩坑 #76：批量取用被限流，30% 的数据静默丢失，还把我自己带进了错误的诊断（2026-08-29）

**现象**：建 impact 窄带，骨干参考文献 10370 篇，元数据只落库 7244 篇（**缺 30%**）。
不报错、日志全绿。日志里唯一的线索是进度停止增长：

```
...6400/10370 → 6371
...7200/10370 → 6930
...8000/10370 → 6930      ← 从这里开始再也不涨
...9600/10370 → 6930
```

**根因（我自己写的）**：`adapters/openalex._batch_filter` 里写着

```python
except errors.PlatformError:
    pass          # ← 单批失败不该让整轮作废
```

注释写得像是深思熟虑，实际后果是**限流之后每一批都失败、每一批都被吞掉**。

**为什么会被限流**：`search()` 一直带着 `mailto`（OpenAlex 礼貌池），
而我新加的批量取用**漏了这个参数**。同一个 API、两个入口、两种配额待遇。

**⚠ 排查时我先得出了一个错误结论**，值得记下来：
重查那批缺失 id，返回 0/80，我据此判断「这些 id 在 OpenAlex 里确实查不到」。
**错的** —— 当时仍在限流期内。而单条端点 `/works/W123` 却能正常返回
（62 / 134 / 775 / 1469 / 491 次引用的真实论文），
「批量查不到 + 单条查得到」这个组合把我引向了「批量接口对老 id 有问题」的错误假设。

真正戳破它的是一个对照实验：拿**刚刚单条查成功**的 5 个 id 再做批量查询 ——
照样报限流。**说明问题不在 id，在配额。**

**解法**（都在 `adapters/openalex`）：

1. 批量取用带上 `mailto`（进礼貌池）
2. 撞限流后按 5 / 15 / 45 秒退避重试，而不是靠 `get()` 内部那两次短重试
   （内部重试对付偶发抖动，这里对付「已经被限流了，得真的等一会」）
3. **默认严格：任何一批最终失败就抛异常**，不再静默返回残缺结果。
   要容忍残缺必须显式传 `allow_partial=True`，而且调用方有义务把失败数落进产物

**判据**：
> **静默的部分成功，比明确的失败危险得多。**
> 宁可整个作业失败让人重跑，也不要产出一份看不出问题的残缺数据 ——
> 后者会被下游当成完整数据用下去，而且很可能永远没人发现。
>
> 推论：`except: pass` 旁边写「单批失败不该让整轮作废」这类注释时，
> 要先问一句：**如果每一批都失败呢？**

**同类线索的通用识别方法**：进度日志里「计数停止增长但循环继续」= 静默失败。
所以进度回调值得一直保留累计数，而不只是百分比。

## 踩坑 #77：OpenAlex 从 2026-02 起按量计费，「免费无密钥」这条旧认知已经过期（2026-08-29）

**现象**：接踩坑 #76 修完退避重试之后，**所有**批量查询仍然 429 —— 包括刚刚用单条
端点成功取到的那几个 id。看错误正文才明白它根本不是限流：

```
{"error":"Rate limit exceeded",
 "message":"Insufficient budget. This request costs $0.0001 but you only have $0 remaining"}
```

**现在的真实规则**（查证自官方帮助中心）：

| | 每日额度 | 约等于 |
|---|---|---|
| 无 API key | **$0.10/天** | ~1,000 次 filter 查询 |
| 免费 API key | **$1/天** | ~10,000 次 filter 查询 |

单价：

```
单条 /works/W123      免费，且不限次    ← 关键
list / filter 查询     $0.10 / 1000 次
全文搜索 / 语义搜索     $1    / 1000 次
PDF 内容              $10   / 1000 次
```

额度按 **UTC 午夜**重置。key 在 `openalex.org/settings/api` 免费领，30 秒，
可用 `api_key=` 查询参数或 `Authorization: Bearer` 头传。

本次建 impact 窄带打了约 320 次 filter 请求 —— 无 key 的 $0.10 额度直接见底。

**为什么这个坑值得单独记**：它的表象（429 + "Rate limit exceeded"）
和普通限流**完全一样**，而处置方式截然不同 ——
限流是「等一会再试」，额度耗尽是「等到 UTC 午夜，或者去领个 key，或者换免费端点」。
按限流去做退避重试，等多久都没用。

> **判据：429 别只看状态码，要读响应正文。** 同一个状态码底下可能是完全不同的事。

**解法**（都在 `adapters/openalex`）：

1. `api_key()` 从 `core.config` 读 `OPENALEX_KEY`，`_auth()` 自动挂到每个请求上
2. **429 的报错文案区分两种情况**并直接给出下一步：没配 key 就告诉用户去哪领
3. 新增 `works_singleton()` / `works_by_ids(..., singleton=True)`：
   逐条走免费端点。慢（一条一个请求），但**额度耗尽后它是唯一还能走的通路**
4. `pipelines/direction_map` 新增 `missing_backbone(band)` / `fill_missing(band)` ——
   把「缺没缺」从看不见变成一句话能问出来，并且能免费补齐

**顺带发现**：`wechat_polymer` 那条窄带也缺 11 篇骨干元数据 ——
它是在严格模式上线之前建的。**说明这类静默缺口一旦发生就会一直躺在数据里**，
除非有人专门去查。这正是 `missing_backbone()` 该长期存在的理由。

## 踩坑 #78：一整包代码搬深一层，`__file__` 数上来的 ROOT 会静默指错（2026-08-30）

**现象**：R1 窗把 `core/` 搬成 `shared/kernel/` 之后，`import` 全部成功、
语法检查全过，但 pytest 一收集就炸「缺少必要配置 ZOTERO_USER_ID」——
而 `.env` 明明就在项目根、内容也没动。

**根因**：项目里有 12 处「从 `__file__` 往上数几级找项目根」的写法：

```python
ROOT = os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
```

搬家让这些文件**深了一级**，于是 ROOT 集体指到了 `shared/`。
`config` 于是去 `shared/.env` 找配置（没有），`paths` 于是把数据目录
算成 `shared/workflow_data/`（**并且真的在那儿建了一个空的 logs 目录**）。

> **这是搬家这件事唯一会静默出错的地方。** import 会报错、语法会报错，
> 只有「数上来的层数」不会报错 —— 它只是安静地指向另一个地方。

**解法**：搬完先 `grep -rn "dirname(os.path.dirname" --include="*.py"`，
把每一处按新深度补齐层数，然后**必须实际打印一次**：
`python -c "from shared.kernel import paths; print(paths.ROOT)"`。
搬家之后顺手 `find . -name workflow_data -type d`，清掉指错期间建出来的空目录。

**同一根因的第二处**：`proc_lock/selftest.py` 把 `from core.proc_lock import ...`
写在**字符串里**去起子进程。批量改 import 的正则只匹配行首，漏掉了它，
于是自测里冒出 `ModuleNotFoundError: No module named 'core'`。
**改包名时要连字符串里的 import 一起搜**（`grep "from core"` 而不是 `grep "^from core"`）。

## 踩坑 #80：自动区块的标记里写了生成器自己的路径，生成器一搬家就多出一份（2026-08-30）

## 踩坑 #81：按文件名找脚本 / 找进程的地方，搬家时会静默失效（2026-08-30）

**现象**（R2 窗搬家时逐个揪出来的，三处，都不会报错）：

| 位置 | 它在干什么 | 改名后会怎样 |
|---|---|---|
| `watchdog.find_watcher_pids` | PowerShell `CommandLine -match 'zotero_watcher'` | 永远「找不到 watcher」→ 判死 → 每轮再起一个 |
| `host/deploy/update.py` | `CommandLine -like '*zotero_watcher*'` | 部署时**停不掉旧 watcher**，新代码不生效（这正是 2026-08-27 那次「重启任务换不掉进程」的同型故障）|
| `health_check.c_importable` | `find_script('zotero_watcher')` 满工作流文件夹找 `.py` | 直接报 FAIL「关键脚本找不到」 |

**根因**：这三处都把**文件名**当成了标识符。文件名是位置，不是契约 ——

前两处的失败形态是「什么都没匹配到」，那和「本来就没在跑」长得一模一样。

> **判据：跨进程/跨工具的标识符，要用不会随搬家变化的东西。**
> 模块名（`tools.deepread.watcher`）是契约，文件路径不是。

**解法**：
- 体检改成 `python -c "import tools.deepread.watcher"` —— 按**模块名**验，
  顺带真的把 import 期的 NameError 也验了。
- 两处进程匹配改成两个词一起匹配（`deepread` **且** `watcher`），
  不再依赖某一个具体文件名；`watchdog` 里没有 `watcher` 这个子串，
  所以看门狗不会把自己杀掉。
- **搬家时的自查动作**：`grep -rn` 一遍旧文件名（含 `.bat` 和 PowerShell 字符串），
  别只 grep `import`。这三处一个都不是 import。

## 踩坑 #86：花钱的能力如果暴露成 MCP `tool`，等于把钱包交给模型（2026-08-31）

**现象**：R4 窗要把十个工具都挂上 MCP。照直觉全注册成 `tool` 的话，
模型可以自己调 `deepread`（每篇几毛钱 + 写 Zotero）、自己调 `extract`（全库抽取）。

**根因**：MCP 的三类暴露不是分类学，是**权限边界**：
`tool` = 模型自己调，`resource` = 模型自己读，`prompt` = **人在客户端里点**。

由 `host/mcp/registry.py` 的 `check()` 强制：
**声明了花钱或有副作用的切片，不许注册 `tool` 类**，只能 `prompt`。
现状：只有 `library`（9 个只读查询）与 `paperdb`（4 个只读查询）是 tool。
提示词正文里再统一加一句「先把代价讲给用户听、等他点头」——
那句话由 `shared/kernel/mcp_prompt.card()` 拼，八个工具共用一份，不会各说各话。


## 踩坑 #87：`git rm -r` 删掉一个包之后，结构树里它还在（2026-08-31）

**现象**：R5 窗解散 `shared/adapters/evalset/`，`git rm -r` 成功、
`paths.block_dirs()` 也已经不返回它了，但 `python host/codegen/handover.py`
生成的 CLAUDE.md 结构树里 `adapters` 仍然写着 12 块、仍然列着 `evalset`。

**根因**：两处枚举口径不一样。
- `paths.block_dirs()` 认的是「有 `__init__.py` 的子目录」→ `__init__.py` 已删，正确地不返回它
- `handover.py` 画结构树用的是 `os.listdir` + `isdir`，认的是「目录还在不在」

而 `git rm -r` 只删**被跟踪的文件**：`__pycache__/` 从来不进版本库，
于是那个目录在磁盘上以「只剩一个 pycache」的形态活了下来，结构树照样画它。

**解法**：删包之后要 `rm -rf` 那个目录本身，别只依赖 `git rm`。
删完重跑一次交接生成器确认结构树对了。

**更该记住的**：**同一个概念有两处枚举，就一定会有对不上的那一天。**
`block_dirs()` 是块的权威定义，结构树却自己 listdir —— R7 窗重写守卫时应当合并成一处。

## 踩坑 #88：换用 `paths.summary(key)` 顺手引入了一处会抛异常的新行为（2026-08-31）

**现象**：R5 窗把评测集的 `snapshot()` 从自己拼路径
（`os.path.join(LIBRARY, key, 'summary.html')`）改成走契约层 `paths.summary(key)`，
新写的测试立刻红：`BadKeyError: 不是合法的 Zotero item key: 'KEY1'`。

**根因**：`paths.paper_dir()` 里有 `check_key()` —— 契约层**会校验** key 的形状，
而手拼路径**不会**。原来的 `snapshot('随便什么字符串')` 安静地返回 None，
改完之后变成抛异常。真实 Zotero key 永远是 8 位字母数字，所以生产上看不出区别，
但面板的待评价列表是拿一批条目循环调 `snapshot()` 的 ——
里头混进一个怪 key，整个列表就崩了。

**解法**：`snapshot()` 里显式 `except paths.BadKeyError: return None`，
把「宽容」写成代码而不是靠巧合。

**更该记住的**：**「搬家窗不改行为」这句话里，行为包括异常。**
把手写实现换成公用件，公用件多出来的那点严格就是一次静默的行为变更 ——
搬家时要么保留旧宽容并写注释说明，要么就明确当成一次改进并告知，不能装作没发生。

## 踩坑 #89：数据分层把「建了 A 就等于建了 B」这个隐含保证悄悄拆了（2026-08-31）

**现象**：R6 窗把 `workflow_data/library/<KEY>/` 拆成 `data/raw/<KEY>/`（解析产物）
与 `data/curated/<KEY>/`（精读产物）。改完 **pytest 204 全绿、离线体检 10/0/0**，
但 `tools/ask/selftest.py` 与 `tools/extract/selftest.py` 一跑就
`FileNotFoundError: ...\curated\ZZZZ0003\meta.json`。

**根因**：拆之前 `parsed/` 是 `library/<KEY>/` 的**子目录**，所以
`paths.parsed_dir(key, create=True)` 顺手就把这篇的目录建出来了 ——
后面写 `meta.json` / `summary.html` 直接就能写。这个保证**从来没有人写下来**，
它只是目录嵌套关系的副产品。分成两层之后嵌套没了，保证也就没了，
而所有依赖它的代码一个字都没改，看起来完全正常。

**为什么测试没拦住**：单元测试各自 monkeypatch 临时目录、各自先建好目录，
正好把这个保证绕过去了。只有「真跑一篇」的路径才会踩到。

**解法**：把不变量**钉在唯一知道布局的地方**（`shared/kernel/paths.py`）：
新增 `_open_paper(key)`，`parsed_dir(create=True)` 与 `si_parsed_dir(create=True)`
都调它，一次把两层的目录都建出来。
不在每个写产物的地方各补一句 `makedirs` —— 那样等于把契约又摊回去几十处。

**教训**：**拆目录层级时，先问「原来的嵌套关系替谁做了事」。**
嵌套本身就是一种没写下来的契约：父目录存在、路径同级、相对链接可用。
拆开的那一刻这些全部失效，而且**编译器和离线测试都不会说一个字**。

## 踩坑 #90：为验证守卫「故意违反一次」，还原时用 `git checkout --` 把本窗未暂存的改动一起冲了（2026-08-31）

**现象**：按项目纪律「每加一条守卫，故意违反一次确认它真的会红」，
往 `host/doctor/artifact_gaps.py` 塞了一行违规代码，确认守卫变红后
用 `git checkout -- host/doctor/artifact_gaps.py` 还原 ——
结果这个文件**本窗早先做的真实改动**（产物体积要走 raw + curated 两个目录）
被一起还原回了 HEAD，而且没有任何提示。

**根因**：`git checkout -- <文件>` 是「拿索引里的版本覆盖工作区」。
本窗的改动还没 `git add`，索引里就是 HEAD 那份 —— 于是连同违规行一起被抹平。
守卫确实红了，验证成功；被毁掉的是**验证之外的东西**。

**解法**：验证守卫时**不要用 git 还原**。要么先把违规行原样删回去
（改了什么就反着改回来），要么改在一个临时新建的文件上、验完删掉它。

**教训**：**「故意弄坏再还原」这套动作里，还原那一步才是危险的那一步。**
用一个作用范围比「我刚弄坏的那点东西」更大的命令去还原，
迟早会顺手毁掉旁边的东西。还原的粒度必须和破坏的粒度一样细。
（发现得早只因为紧接着 grep 了一次改动关键字 —— 这个自查值得固化下来。）

## 踩坑 #91：坑号撞车 —— 同一个编号被两条完全不同的记录占着（2026-08-31）

**现象**：R7 窗按工具切 `INCIDENTS.md` 时，汇总脚本报出一条不存在的关联 ——
「#15 find_pdf 误选补充材料」同时咬过 deepread 和 digitize。
可 digitize 根本不碰 find_pdf。

**根因**：总账里 **#15 / #16 / #43 各被用过两次**。
它们是并行记录留下的：那阵子精读线和图表数字化线各写各的，
两边都按「上一条是 14，我写 15」往下编，谁也没看对方写到哪了。
于是同一个号在文件里出现两次，标题完全不同。

**为什么它比看起来严重**：任何「按编号聚合」的东西都会凭空造出关联，
而且看起来是统计出来的结果 —— **生成的假事实比没有更糟**。
本项目里靠编号互相引用的地方很多（skill 的速查表、各工具的 INCIDENTS、变更记录）。

2. 汇总按 **(坑号, 现象)** 合并，不按坑号合并（`host/codegen/incidents.py`）。
3. 撞车的三个号在各工具的 `INCIDENTS.md` 里带上限定语
   （「第一个 15，精读线那条」/「第二组 15/16，图表数字化」）。
4. 以后新增一条**先 `grep "^## " 踩坑记录.md | tail -3` 看真实的最大号**，
   别凭印象往下编。

## 踩坑 #92：守卫「空转」有第二种形态 —— `pytest.skip`（2026-08-31）

**现象**：R7 窗重写架构守卫时才发现，「domain 环不许有 I/O」这条守卫
**从 R1 窗起就一次都没真正跑过**。pytest 报告里那个孤零零的 `s`（skipped）
一直在，六个窗里没人多看一眼。

**根因**：守卫开头写着

```python
if not os.path.isdir(os.path.join(ROOT, 'domain')):
    pytest.skip('domain 环尚未建立')
```

R1 窗把 `domain/` 搬成了 `shared/domain/`，于是这个判断永远为真 —— 永远 skip。
写这行的本意是「阶段性地还没建这一环，先别红」，是善意的；
但环建好之后没人回来删它，它就变成了一个**假装在守的守卫**。

**为什么比踩坑 #83（改名导致空转）更隐蔽**：#83 那种空转，测试是「通过」的，
至少人还能自欺；而 skip 会**在报告里明晃晃地显示一个 `s`**，
所有人都看见了，所有人都以为「哦那是暂时的」。看得见反而更容易被容忍。

**解法**：
1. 把 `skip` 换成**断言目录必须存在**：环没了就该红，因为那说明守卫失去了对象。
2. 同一窗里另外两条也是同类事故：依赖方向守卫的 `RINGS` 与引导脚本守卫的
   `_PROJECT_PKGS` 都还写着 `core/domain/adapters/pipelines` —— 全部空转六个窗。
   凡是能从 `paths.CODE_ROOTS` 之类取到的，**别抄第二份**。
3. 纪律照旧：**每加一条守卫，故意违反一次确认它真的会红。**
   R7 窗六条新守卫逐条验过，其中「工具不许 import 工具」验红时还顺手
   抓到 `_imports_of` 漏掉 `from shared.kernel import paths` 这种最常用写法。

**一句话**：`pytest.skip` 和「守卫空转」是同一件事的两张脸 ——
**报告里每一个 `s`，都要能说清它为什么还在。**


## 踩坑 #93：走子进程绕过 import，不叫「合规」（2026-08-31）

**现象**：R3 窗记了一条待办：`tools/curate/sync.py` 用子进程跑
`tools.ask.vectorize` 与 `tools.extract` —— 「这不构成 import 边（所以硬规则 2
拦不到它），但它确实是一个工具驱动另外两个工具」。
写下这句话的时候其实已经知道不对了，只是守卫没红，就先放着了。

**根因**：守卫检查的是 **import 语句**，而耦合的本质是**依赖关系**。
子进程调用同样让「改 extract 会波及 curate」成立，只是让机器看不见而已。
一旦养成「守卫没红就算过」的习惯，守卫就从「规则的执行者」退化成
「规避的靶子」——人开始绕着它写代码，而不是照着它写。

**解法**（R7 窗）：按规则的**意图**而不是它的**实现**判断，把它挪去
`host/autosync/`。判据与同窗的 watcher 完全相同：REBUILD.md 第一节
定义 host 是「不是能力，是让平台活着的东西」，一个定时跑、串起两个工具、
还顺手救活后台服务的作业正是这个定义；硬规则 4 又明写 host 可以 import 一切。

**推论（比这条坑本身更有用）**：守卫红了当然要改；**守卫没红但你心里发虚的地方，
也要改**。发虚的那一下，就是你已经知道规则的意图被违反了。

## 踩坑 #94：「先复制、核对、再删」的流程，最后一步是死路（2026-09-01）

**现象**：R6 窗搬完数据后想删原目录 `workflow_data/`，跑
`migrate_data.py --apply --remove-old`，直接被拦：`✗ 目标已存在`。
于是原目录多留了一天，根目录里同时躺着两个看起来都像数据的目录。

**根因**：脚本的三步是「复制 → 核对 → 核对全过才删」，而删除**只能**从
这条流水线的末端触发。可 `copy_all()` 一见到目标已存在就 `SystemExit` ——
**第二次运行永远走不到核对和删除**。也就是说：正常搬完一轮之后，
「删原目录」这个唯一的正规入口是死的。

写的时候没想到「第二次运行」这个状态，因为脑子里的流程是「一次跑完」。
但现实里它必然被跑第二次 —— 设计上就是这么要求的（先不删，确认没问题再删）。

**解法**：补上「目标全都已存在 → 跳过复制，直接核对」。
「搬了一半」（部分目标存在）仍然停下来让人处理 —— 那种状态自动继续太危险。

**顺带撞出的第二个问题**：核对方式是「文件数与总字节完全一致」，
但 `logs/` 在搬完之后**还在往新位置继续写**，一天后新位置多了 44 KB，
核对当然不过 —— 而这恰恰证明搬对了。改成：日志目录只要求「文件数一致
且没变小」，别处照旧按字节严格核对。**判据是「这份数据搬完之后还会不会长」。**

**推论**：写「分阶段、可中断」的脚本时，**每个中间状态都要能被第二次运行接住**。
只测「从头跑到尾」这一条路径，等于只测了它永远不会被用到的那一次。



## 踩坑 #95：一条规则同时管着差三个数量级的两件事（2026-09-01）

**现象**：用户说「没必要把付钱功能完全不让 AI 操控，能不能开个确认窗」。
一查才发现，原来那条「花钱的一律不许当 MCP tool」把
**「问一次库（几分钱、不写任何东西）」和「全库向量化（全库作业）」当成了同一件事**。
结果是用户日常最常做的事反而最别扭：想问一句自己的库，得他自己去点提示词。

**根因**：规则的判据挑错了维度。挑的是「花不花钱」（一个布尔），
而真正决定风险的是**代价的量级 + 可不可逆**（两个连续量）。
一个布尔盖住两个数量级的差距，必然要么太松要么太紧 —— 这次是太紧。

**解法**：改成三档。单次/便宜/可重来的可以是 tool（但带强制确认），
全库作业与不可逆写库仍然只能是 prompt。

**顺带查证到的事实**（不是记忆，是查的）：Claude Code 早就支持
`_meta["anthropic/requiresUserInteraction"] = true` —— 打上它之后，
**每次调用都弹权限窗，而且不给「不再询问」的选项**，allow 规则绕不过去，
`dontAsk` 模式下直接拒绝。这恰好补上了原规则真正在防的那个洞：
不是「模型会调」，而是「用户点了一次『总是允许』之后就再也不问了」。

**留下的判据**：**规则要按「最坏后果的量级」分档，别按「有没有那个属性」一刀切。**
一刀切的规则总是在保护一端的同时废掉另一端，而被废掉的那端通常是高频的那个。


## 踩坑 #96：验红验了三轮才验干净（2026-09-01）

**现象**：给上面那套新闸门写守卫，「故意违反一次」验了三轮才全绿：

| 轮 | 漏了什么 | 为什么漏 |
|---|---|---|
| 一 | pytest 不查「注册了 tool 却不在白名单」 | 只写了「白名单里的要带 confirm」，**没写反方向** |
| 二 | `registry.check()` 查不出「漏了 confirm」 | 传进来 report 时，我拿一个**新造的空 server** 去查 confirm 标记 |
| 三 | `check()` 查不出「白名单写了不存在的入口」 | 那条被塞在 `if got.get('tool')` 里，而没注册 tool 的工具走不到 |

**根因都是同一个**：**只验了「做错事会不会被拦」，没验「什么都不做会不会被拦」。**
三处漏的都是「反方向」或「边界情况」—— 而守卫最该拦的恰恰是那些。

**解法**：验红时把破坏方式列全，至少三类：
① 多做了不该做的（多注册一个）② 少做了该做的（漏 confirm）
③ 名单与现实脱节（写了不存在的）。而且**每一道闸都要在它的每一个入口上验**
（这里是 pytest 与 `server.py --list` 两个入口，前两轮各有一个入口是绿的）。

**推论**：「加了守卫就故意违反一次」这条纪律还不够 ——
**要故意违反的是「守卫覆盖的每一种方向」，不是「随便违反一次」。**
一次验红只证明那一条路会红，不证明这道闸是关着的。


## 踩坑 #97：连不上主力机的四种原因，报错长得完全不一样但都像「连不上」（2026-09-03）

**现象**：要打通 A→B 的远程操作，一路撞了三种不同的失败，
每一种都被我先误判了一次：

| 看到的 | 我一开始以为 | 真相 |
|---|---|---|
| `Connection timed out` | B 关机了 | 对，但当时还没排除路由问题 |
| `Find-NetRoute` 说走 `singbox_tun` | **代理把局域网劫走了** | **错**。同网段网关 `.1` 通得好好的 |
| `kex_exchange_identification: Connection closed` | 密钥或账号有问题 | **错**。密钥交换都没开始，跟认证无关 |

**决定性的对照实验**（这次真正管用的一步）：
去连一个**必定不存在**的 IP 的 22 端口。

- 如果它也「连上了」→ 是代理在伪造 TCP 握手，问题在本机
- 如果它连不上 → 代理没插手，问题在对面

实测：不存在的 IP 连不上 → **代理是清白的**，我的第二个判断是错的。

**最后的结论**：ping 不通、ARP `Unreachable`、但 TCP 22 偶尔能连上、
连上又在打招呼前断 —— 这个组合指向**机器在睡眠，被网络活动短暂唤醒又睡回去**。

**教训（比这几个原因本身更值钱）**：
1. **`Find-NetRoute` 的答案不等于实际走向**。判断路由有没有被劫，
   要用「同网段的另一个地址通不通」当对照组，不是读路由表。
2. **`kex_exchange_identification` 出现的位置就是证据**：它在密钥交换**之前**，
   所以凡是看到它，密钥、账号、authorized_keys 全都不用查 —— 那些都在它后面。
3. 排查网络时，**先做一个「已知答案」的对照**（不存在的 IP、同网段的网关），
   再看目标。没有对照组的观察，怎么解释都说得通。

这四种判据已经写进 `host/deploy/remote.py` 的 `diagnose()`，
连不上时直接把「该往哪查、不该往哪查」打出来。


## 踩坑 #98：授权文件里躺着一条永远匹配不上的规则（2026-09-03）

**现象**：`.claude/settings.local.json` 里那条 SSH 授权写的是
`吧啦吧啦@192.168.123.216` —— 那是主力机的**计算机名**，不是账号。

**根因**：踩坑 #74 修的是**文档**，改完 `docs/` 就算完事了，
**没人想起来授权文件里也抄了一份**。于是那条规则从写下来那天起就没生效过 ——
而它「不生效」的表现是**每次都要人点一下确认**，看起来完全正常，
所以谁都没觉得不对。

**这是「同一个事实被抄了两份」的又一次**（铁律 1 的老问题），

**推论**：修一个「被抄了两份」的错误时，**先 `grep` 一遍那个错误的值**，

## 踩坑 #99：把「输出编码」当成了「读文件编码」（2026-09-03）

**现象**：`remote.py logs` 第一次真连上 B 取日志，中文全是
`[蹇冭烦] 杞姝ｅ父锛屽緟澶勭悊 0 绡?`。而我在这条命令外面**已经**套了 UTF-8 外壳
（`[Console]::OutputEncoding=UTF8` 那一套），所以第一反应是「外壳没生效」。

**根因**：外壳管的是**输出**，管不到**读文件**。
`Get-Content` 读文件时用的是系统代码页（B 机是 GBK），而日志文件是 UTF-8 ——
在它被输出之前就已经解码错了。外壳再对也救不回来。

**解法**：`Get-Content $p -Encoding utf8`。一个参数的事。

**为什么值得单独记**：踩坑 #60 说过「Windows 控制台的编码在三个地方分别咬人」，
这就是**第三个地方**，而且是最容易漏的那个 —— 因为前两个（stdout / stdin）
一旦修好，人就会以为「编码问题已经解决了」。

**判据**：看到乱码先问一句 —— **这段字节是在哪一步被解码的？**
输出编码只管最后一步；中间任何一次「把字节读成字符」都可能是错的那一步。


## 踩坑 #100：连不上，是因为那台机器根本没连这个 WiFi（2026-09-03）

**现象**：从 A 机连不上 B（`192.168.123.216`）。我查了路由、ARP、代理劫持、
睡眠唤醒，写了一整套分类诊断，最后**结论是「B 在睡眠」——错的**。
用户说「我电脑是开着的，UU远程都能连上」，我才发现方向全错。

**根因**：**UU远程走的是公网中转，不经过局域网。**「它能连」完全不能证明
「B 在这个局域网里」。真相是 B 那会儿没连这个 WiFi —— 两台机器压根不在一个网上。

**我为什么绕这么久**：`192.168.123.216` 是 2026-08-28 记下的，那天两台在同一个
路由器下。我把「文档里记着的地址」当成了「现在的事实」，于是所有排查都建立在
「B 应该在这个地址上」这个没被验证的前提上 —— 越查越细，方向却是错的。

**真正该先做的一步**（全网段 ARP 扫描）只要十几秒：

```powershell
1..254 | ForEach-Object { (New-Object System.Net.NetworkInformation.Ping).SendPingAsync("192.168.123.$_", 800) }
Get-NetNeighbor -AddressFamily IPv4 | Where-Object { $_.State -eq 'Reachable' }
```

当时扫出来只有 4 台设备，**没有一台是 B** —— 一眼就能否定前提。

**教训（这条比前面所有网络知识都重要）**：
**先确认「目标在不在」，再研究「为什么连不上」。**
把「记录里的地址」当既成事实，是这次绕远路的唯一原因 ——
而它恰好是零号判据在网络排查上的样子：**记录说的不等于此刻的真实世界。**


## 踩坑 #101：「密钥读不出来」的真凶不是权限，是**登录会话的种类**（2026-09-03）

**现象**：从 A 机 SSH 到 B 机，`get_key('DEEPSEEK_KEY')` 返回空串。
密钥明明在凭据库里，账号也是 Administrator 本人，`whoami` 完全正确。
过去几周一直把它当成「远程发起花钱作业不可能」的天花板，绕着走。

**根因**：直接调 `keyring.get_password` 才拿到真话 ——
`win32ctypes.pywin32.pywintypes.error: (1312, 'CredRead', '指定的登录会话不存在。可能已被终止。')`。
公钥 SSH 建立的是**网络登录会话**，它没有解开 DPAPI 主密钥所需的凭据，
所以凭据管理器整个读不出来。这跟「有没有权限」无关，也跟 sshd 配置无关。

**为什么被拖了这么久**：`get_key()` 对读不到的情况是**返回空串**而不是抛错，
于是这条 1312 从来没被人看见过。症状（空密钥）和根因（会话种类）中间隔着一层静默降级。

**解法**：不去改会话，而是**换一个身份去跑**。计划任务的 principal 若是
`LogonType=Interactive`，它跑在真正的交互会话里（`SessionId=1`），凭据库正常可读 ——
B 上 watcher 一直在花钱、在写 Zotero，就是这条的活证据。
于是有了 `host/deploy/remote.py job`：注册一个按需触发的计划任务，
跑什么由 A 机现写 payload。实测通过：密钥读到（长度 35）、真调了一次 DeepSeek 补全。

**判据留给下次**：凡是「远程能连上但某个本地资源读不出来」，
先问一句**这是哪种登录会话**，别先去查权限和配置。


## 踩坑 #102：编码咬人的第四个地方 —— PowerShell 读 **.ps1 文件本身**按 ANSI（2026-09-03）

**现象**：作业通道刚打通，第一次跑就是 `DEEPSEEK_KEY 闀垮害: 35`。
输出编码明明已经套了 UTF-8 外壳（`[Console]::OutputEncoding` + `PYTHONIOENCODING`）。

**根因**：烂的不是输出，是**输入**。Windows PowerShell 5.1 读 `.ps1` 脚本文件时，
**没有 BOM 就按系统代码页（GBK）解**。脚本里的中文在被解析成命令的那一刻就已经错了，
后面再怎么设输出编码都救不回来 —— 外壳是在脚本被解析**之后**才生效的。

**解法**：生成 payload 与外壳脚本时用 `encoding='utf-8-sig'`（带 BOM）。

**归位**：踩坑 #60 说「编码在三个地方分别咬人」（控制台输出 / 子进程 / 读数据文件），
#99 补了第三个。这是第四个：**读脚本自身**。
下次再见到「明明设了 UTF-8 还是乱码」，先问是哪一段的编码 —— 输出、子进程、读文件、还是读脚本。


## 踩坑 #103：`%USERPROFILE%\Desktop` 不是用户真正的桌面（2026-09-03）

**现象**：给主力机建了 7 个桌面快捷方式，命令全部成功，文件夹也确实存在 ——
用户说桌面上看不到。

**根因**：那台机器的桌面被重定向到了 `D:\桌面`。
我按 `$env:USERPROFILE\Desktop` 拼路径，于是在
`C:\Users\Administrator\Desktop` 下建了一个**谁也看不见的**文件夹。
Windows 允许把「桌面/文档/下载」指到任意位置，中文系统上把桌面挪去 D 盘很常见。

**判据留给下次**：凡是「用户看得见的位置」—— 桌面、开始菜单、文档、下载 ——
都要问系统要，不许用环境变量拼。这类错误的特征是**命令全部成功、结果没人看见**，
从日志里一点异常都看不出来。


## 踩坑 #104：验证界面改动，别去 grep HTML —— 那个页面是接口渲染的（2026-09-03）

**现象**：给控制面板加了一个密钥输入项，重启面板后我抓 `http://127.0.0.1:8777/`
的 HTML 搜关键字，搜不到，于是判断「面板还在跑旧代码」。
实际上新代码早就生效了 —— 密钥列表由 `/api/all` 以 JSON 送出，
HTML 里根本没有那几个字。

**根因**：我用「页面源码里有没有这个词」当成了「这个功能在不在」。
对一个前后端分离的页面，这两件事没有关系。

**代价**：差点去查一个根本不存在的部署问题。**言之凿凿的错判比不给判断更糟** ——
这跟踩坑 #97（把「连不上」全归因成睡眠）是同一类错误的第二次出现。

**解法/判据**：验证界面上的东西，**要去问它真正的数据源**。
面板的数据源是 `/api/all`，一条命令就能列出来：

    Invoke-WebRequest 'http://127.0.0.1:8777/api/all' | ConvertFrom-Json

顺带记住另一半：面板是常驻进程，**改了代码不重启就一直是旧的**（陷阱 2）。
这次两件事撞在一起 —— 先真的踩了重启那条，修好之后又用错的方法验证，
于是得出「没修好」的结论。**修复与验证要各自独立确认，别用一次观察下两个结论。**


## 踩坑 #105：写死在下游的默认值，会让上游刚加的能力**静默失效**（2026-09-03）

**现象**：接好 Gemini、密钥验过、模型清单验过、单条 `chat()` 也通了。
把面板的精读模型改成 `gemini-3.8-flash` 去跑真实精读 —— 请求发去了 **DeepSeek**，
回一句 `The supported API model names are deepseek-v4-pro, ... but you passed gemini-3.8-flash`。

**根因**：`tools/deepread/batch.py` 里写着

    main_text.read_main(..., provider=PROVIDER, key=get_key('DEEPSEEK_KEY'))

`PROVIDER = 'deepseek'` 是模块级常量，`read_main` 的签名里还有一份
`provider='deepseek', model='deepseek-v4-flash'` 的默认值。
新加的「从模型名认出该找哪家」在 `llm_client` 里，而它永远拿不到发言权 ——
调用方每次都**显式**告诉它「去 DeepSeek」。

**为什么这类错误特别贵**：症状出现在**离改动最远的地方**。
我改的是 adapters，验证也在 adapters（单条 chat 通了），
坏掉的却是 tools 里一个三个月前写下的默认参数。
「我改的那块验过了」在这里是**假的安全感**。

**解法**：不去改每一个调用方（十几处，漏一个就复发），
而是让**唯一知道「谁家是谁家」的那一层**说了算 ——
`llm_client._cfg()` 里，模型名一旦点名了另一家，就推翻传进来的 provider，
**并把 key 一起丢掉**（调用方递来的是另一家的钥匙，拿去开门只会得到莫名其妙的 401/400）。

**判据留给下次**：加了一条「自动推断」，先问一句 ——
**有没有人会显式传参把它挡掉？** 推断与显式参数并存时，
要明确写清谁优先，并在自测里锁死。默认值不是中立的，它是一票否决。

## 踩坑 #106：Gemini 3 的思考**关不掉**，而且文档列的合法值它不认（2026-09-03）

三件事叠在一起，任何一件单独看都像别的问题：

1. **思考 token 计入 max_tokens**（跟 DeepSeek V4 同一个坑）。
   试探时给 `max_tokens=300`，结果 300 全被思考吃光，正文 0 字 ——
   报出来是「输出被截断且正文近乎为空」，看着像模型不会写。
2. **关不掉**。官方原话：`reasoning_effort="none"` 只支持 Gemini 2.5，
   2.5 Pro 与 3 系列的思考不能关。所以 `thinking=False` 在 Gemini 上
   只能翻译成「尽量少想」，不是「不想」——精读那类长文，额度要给得比 DeepSeek 更宽。
3. **文档列了 `minimal`，模型不认**。发过去 400：
   `Thinking level MINIMAL is not supported for this model`。改用 `low` 才通。
   → 又一次印证零号判据：**文档也是「预训练记忆」的一种**，以实测为准。

## 踩坑 #107：503 要分清是「对方忙」还是「我们发错了」（2026-09-03）

`gemini-3.8-flash` 连着四次退避重试全 503，看起来像线路不通或被墙。
但同一把 key 列模型是通的 —— 所以不是网络也不是鉴权。

**拆变量测**才看清：同一时刻 `gemini-3.5-flash`（2.4s）与 `gemini-flash-latest`（11s）
都秒通，只有 `3.8-flash` 反复 503，而它的响应体写得明明白白：
`This model is currently experiencing high demand.`

**结论**：最新的那个模型在免费档上最挤。**判据**：报 503 时先读响应体，
再拿同一把 key 换一个模型试一次 —— 两次调用就能把「对方忙」和「我们发错了」分开。
别对着一个模型重试到怀疑人生。


## 踩坑 #108：拿 `ping` 当探活判据 —— 那台机器根本不回 ICMP（2026-09-04）

**现象**：A 连不上 B 时，我顺手 `ping` 了一下，100% 丢包，于是判定
「局域网这一段断了」，并据此排除了一串别的可能，还把这条判据写进了
`remote.py` 的诊断提示里。

**真相**：**B 从来就不回 ping。** 实测：ping 收到 0 个回包的**同一秒**，
SSH 连得好好的。B 的入站防火墙启用了 13 条 ICMP 规则，但没有一条放行
Echo 请求（那几条是「目标不可访问的碎片」「多播侦听」之类）。
Windows 默认就是这样。

**代价**：这个假信号支撑了我至少两轮错误推理，还被我写进工具里去误导下一个人。

**判据留给下次**：
- **探活要探你真正要用的那个端口**，不是 ICMP。这里就该直接试 22。
- 一个「证据」在支撑结论之前，先问一句：**它在正常情况下是什么值？**
  我从没在 B 正常时 ping 过它 —— 如果 ping 过，第一次就会发现它一直不回。
  **没有对照组的观测不是证据。**
- 这是本窗第三次同类错误（#97 睡眠、#105 写死默认值、这条），
  共同点都是：拿一个「看起来支持结论」的观测直接下结论，没验它的基线。
