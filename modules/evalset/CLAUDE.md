# evalset · 精读质量评测集

> 你可能是被单独选中这个积木文件夹打开的，看不到项目其他部分。本文件是你的全部上下文。

## 为什么存在

平台原有的 13 项体检**全在验「能不能跑」，没有一项在验「跑出来的东西好不好」**——
而后者才是用户真正在乎的。

那次「只贴了图没有文字」的废品精读，是用户自己翻到的，不是系统报的。
后来加的 `MIN_OK=3000` 只是单点防护：挡得住「没字」，挡不住「字很多但都是废话」。

## ⚠ 本模块的目的不是攒分数

单纯收集「好/差」用处有限 —— 改完精读逻辑重跑后，没人给新版本打分，
评测集就成了一次性的。

**真正的目的：用用户的主观评分，校准出一个系统能自动算的质量分。**

所以每条评价都连同当时精读的**客观快照**一起记（字数/图数/数值密度/章节完整性）。
等样本够了（好、差各 ≥3 条），就能分析「他说好的」和「他说差的」在客观指标上差在哪，
从此系统能自己发现质量退化。

**改这块之前请先想清楚这个目的还成不成立**，别把它退化成一个评分收集器。

## 对外接口

| 函数 | 说明 |
|---|---|
| `snapshot(key)` | 算客观指标；文件不存在返回 None |
| `save(key, verdict, reasons, note, title)` | 记录评价 + 当时快照。verdict 只能 good/bad |
| `load()` / `get(key)` / `remove(key)` | 读写评测集 |
| `pending(read_keys)` | 「读完但还没评价」的清单 |
| `stats()` | 好/差数量、两组客观指标对比、差评原因排行、样本够不够 |

数据存 `workflow_data/evalset.json`（原子写入，避免写坏）。

## 客观指标的坑（已修，别再犯）

计算指标前**必须先剔除内嵌图片**。精读 HTML 里的图是 base64 内嵌的，
那串编码里全是数字字母 —— 不剔掉会把「数值密度」算成 13471，而正文才 6641 字。

**一个错得离谱的指标比没有指标更糟**：它不会报错，只会安静地污染将来的校准。
自测里已加合理性检查（数值数不得超过字数的 1/5）。

## 三个标签维度（设计要点，别混）

```
【处理状态】系统维护，互斥     待处理 → 正文精读/全文精读/无附件
【阅读状态】用户维护，互斥     在读 / 读完        ← 系统只读，绝不修改
【质量评价】不进 Zotero        存在本地评测集里
```

**混在一起会出事**：若把「读完」塞进处理状态机，会覆盖「全文精读」，
系统就以为这篇没精读过，又去重跑一遍（花钱）。已实测两个标签能正确共存。

**评价刻意不回写 Zotero** —— 用户的标签栏永远只有「在读/读完」两个。
他被 707 个自动标签坑过，不能重蹈覆辙。

## 谁在用它

`平台管理/panel.py` 的「精读评价」卡片：列出待评价的、可直接打开精读、就地评价。
