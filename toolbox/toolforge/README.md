# toolforge · 工具锻造间

把一个大项目里长出来的东西，**一件一件**变成能单独发布、别人也装得上的小工具。

这里不放具体工具的代码，只放**每次拆分都要重复的那些东西**：骨架、发布前体检、
拆分清单与进度、以及「哪份代码是正本」的登记。

> 起因：拆第一件（[remote-machine](https://github.com/balabala-1314/remote-machine)）时，
> README / LICENSE / .gitignore / 装技能的脚本 / 冒烟测试全是现写的，
> 发布前"扫一遍有没有真实 IP 和密钥"也是临场想起来才做的。
> **同一件事要做第二遍时，就该固化。** 骨架的价值不在省时间，在**不会漏**。

## 两个脚本

```bash
python new_project.py <名字> --desc "一句话说它干什么"   # 开一个新工具项目
python preflight.py <仓库目录> --tests                   # 推到公网之前体检
```

`new_project.py` 生成的骨架自带：装两步的 README、填好版权人的 MIT 许可证、
默认挡住配置与密钥的 .gitignore、入口脚本（取参 / UTF-8 输出 / 没配置时说人话）、
`install.py`（把技能装到 `~/.claude/skills/`，装完所有项目都能用）、四条冒烟测试。

`preflight.py` 分两档报：**阻断**（疑似密钥、公网 IP、写死的用户目录、
没填的占位符、缺许可证）和**提醒**（内网 IP、邮箱、README 缺段落、没有测试）。
它只看**进了版本库**的文件 —— 没被 git 跟踪的推不上去，
把它们也算进来只会制造假警报，而**假警报多了真警报就没人看了**。

## 三份记录

| 文件 | 干什么 |
|---|---|
| [拆分计划.md](拆分计划.md) | 哪些模块值得拆、为什么、按什么顺序、每件要带走什么 |
| [正本登记.md](正本登记.md) | 一份代码变两份之后，**哪份是正本** —— 不登记就会漂移 |
| [发布检查单.md](发布检查单.md) | 推上公网之前，脚本查不了的那几件事（合规、命名、说明） |

## 工作方式（2026-09-06 定）

**新功能一律在总项目（文献平台）里做**；某个功能成熟了，再复制一份出来做成独立工具。
于是同一件事既能在总项目里继续演化，也能在别的项目里被调用。

拆出来之后做成什么形式，按这张表选：

| 形式 | 什么时候选 | 代价 |
|---|---|---|
| **skill** | 默认。它是「知识与判断」：什么时候用、有哪些坑、命令怎么敲。装在 `~/.claude/skills/` 就对**所有项目**生效 | 最低，一个 md 文件 |
| **MCP** | 要在**别的客户端**里被模型直接调用，且这个操作**单次、便宜、可重来** | 中。⚠ 调用约 60 秒超时 |
| **plugin** | 要**打包给别人装**（skill + 命令 + MCP 一起） | 最高，只有真要分发时才做 |

**先做 skill 几乎总是对的** —— 模型本来就会敲命令行，skill 补的是它不知道的那半：
什么时候该用、什么时候别用、哪里会咬人。

**长作业不要做成 MCP tool**：精读一篇、全库抽取都要几分钟，必然超时；
而超时之后作业**还在后台跑**，调用方却看到失败 ——
「看起来失败其实成功了」最容易让人重跑一遍、白花一次钱。

## 规矩

1. **复制，不搬走。** 拆出去的是副本，原项目原封不动照跑
   （第一件 `remote-machine` 是真搬走的，那是唯一的例外 —— 原项目确实不再需要它）
2. **一份代码变两份就会漂移** —— 所以每拆一件，当场在正本登记里写清楚哪份是正本
3. **推之前必须 `preflight.py` 全绿**，红的一条都不许剩：
   推到公网的东西，删掉了也已经被抓走、被缓存
4. **不做过早抽象**：等拆够三件，共同点自己会浮出来，那时候再谈"通用框架"
