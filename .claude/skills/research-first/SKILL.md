# 先看真实世界，再做判断

**这条排在项目所有技术判断之前**（`docs/架构宪法_第一性原理.md`【零号判据】，2026-08-09 立）。

用户原话：
> 世界上那么多人，我能想到的各个方面很可能都是有人做的……
> **你下意识回答我的往往还是预训练的结果，我们还是要主动去看真实实时的世界是怎么样。**

## 一、四步（互穿，不是瀑布）

1. **找准则** —— 这领域有没有成熟方法论？（例：文献检索有系统综述规范；引用图扩展有 snowballing）
2. **找现有实现** —— 有没有人做了？商业产品 / 开源 / 研究原型各是什么状态？
3. **评估** —— 做到什么程度？边界在哪？**我们的场景适不适用？**
4. **决定** —— 好 → 用它 + 只做个性化部分；不好或没有 → 再分析难度、意义、价值。

**「互穿」的意思**：看了别人的实现常会改变你对「自己要什么」的理解 →
允许回头修需求。别为了流程完整硬走一遍。

## 二、硬性要求（本判据的核心）

**不许用预训练记忆代替调研。** 模型的直觉回答听起来流畅、具体、可信，
但它来自训练数据的统计，**不是此刻真实世界的状态**。

- 涉及**外部世界现状**（某工具有无某功能、定价、版本、行业惯例、某方案是否已被取代）→ **必须查**
- 涉及**具体数字**（限额、有效期、体积、性能）→ 查到出处才说，查不到就明说查不到
- 涉及**外部 API 行为** → **真实调用实测**，不信文档也不信记忆

> **听起来很具体的数字最像事实，也最可能是编的。**

**现场例证（写下来是为了让后来者知道这不是空话）**：
- 反例：曾断言「MineRU 的 token 通常两周过期」。查证后官方**根本没给任何天数**。
- 正例：问「Sciverse 自己带不带查询扩展」，没有推理，去读文档发现
  `agentic-search` 有 `sub_queries` 参数（默认 0），再**实测对比 0 与 4**，
  得出「有但默认关、本场景提升不明显」。这个结论只能测出来。

**自查方法**：说完一句判断，问自己 ——
这是我**刚查到/测到**的，还是我**本来就「知道」**的？后者一律打问号。

## 三、别吝啬投入，但边界必须清楚

用户原话：
> 这种创新的工作不能吝啬 token 的使用，**如果产出无作用才是最大的浪费**。

省几次查证 = 用「可能白干几天」赌「省下几分钟」，不在一个量级。
本项目的真实账本：精读质量崩塌那次若不做 A/B 实测，会一直以为「模型变笨了」
去换模型（真因是 max_tokens 被推理链吃光，换模型只会白花钱）。

**但唯一的停止判据是：这次调研/实测，能不能改变我接下来的做法？**
- 能改变 → 查
- 不管结果如何我都这么做 → 不查，直接做

**调研要瞄准「决策的分叉点」**（选 A 还是 B、自己做还是用现成、这条路通不通），
不是把一个领域读通。前者一两次实测就够；后者读一天也定不了任何事。

## 四、决定「自己做还是用现成」时的下一把尺子

【首要判据】按**稳定性**决定，不是按复杂度（用户 2026-07-25）：
> 把工作分到不可再分后 —— **稳定存在、后面一直需要的部分自己做；
> 还在发展的东西就用现成的合适的，或稍微改一下。**

对照四环：`core` / `domain` 是「稳定存在」→ 自己做；
`adapters` 面对的是「还在发展」的外部世界 → 用现成、包薄壳、随时可换。

判完之后再看 `docs/架构宪法_第一性原理.md` 的「分层复杂度策略」（次要判据，服从上面两条）。
