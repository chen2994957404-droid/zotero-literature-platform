# pdf_fetch · 出版商全文

> 你可能是被单独选中这个积木文件夹打开的，看不到项目其他部分。本文件是你的全部上下文。

## 这是什么

**一块「公理件」**：一个 DOI → 这篇文献的 PDF 字节。

它**不自己发 HTTP**，而是接管一个人已经开着的真实浏览器（走 CDP 调试口）。

## 职责

- 只做「导航到这篇的落地页」和「把 PDF 的字节取回来」两件不可再分的事。
- **不知道文件该存哪**（那是工具层的活）、**不写 Zotero**（那是 `zotero_client` 的活）、
  **不管元数据**（那是 `crossref` 的活）。

## 为什么要借浏览器，而不是自己发请求（2026-09-04 实测立的）

同一天验过两条路，结论很硬：

| 路子 | 结果 |
|---|---|
| `requests` + 机构 cookie | ❌ 过不了出版商反爬 |
| 驱动真实浏览器 | ✅ 拿到付费全文 |

旧项目 `AutoPAPER-SCU` 走的是第一条，它 `papers/` 里攒了四个 PDF，
**全是开放获取**，一篇付费的都没成功过 —— 当时以为是权限问题，其实是运输方式问题。

借浏览器等于白拿两件最难的东西：

1. **机构订阅权限** —— 靠出口 IP 生效，浏览器天然带着（实测：教育网出口，
   页面上直接显示学校认证，有 View PDF）
2. **反爬通行证** —— 人机验证是「进门验一次」不是「每篇验一次」，
   人工过一次之后，同一个浏览器里后续文章都顺

**所以权限和反爬都不是这块要解决的问题**，它只负责导航和取字节。
这也决定了它必须连**人已经在里面点过验证的**浏览器，新开一个干净的没有这两样。

## 对外接口

| 函数 | 说明 |
|---|---|
| `is_available()` | playwright 装了没 —— 上层据此给人话 |
| `probe(url=None)` | 那个浏览器连不连得上 → dict |
| `fetch(doi, url=None, timeout=90, settle=6)` | → dict(ok, reason, pdf, landing, title, pdf_url) |
| `pdf_url_of(page)` | 当前页上的 PDF 直链候选，排查用 |
| `is_doi(s)` | 长得像不像 DOI |

## 拿不到不是异常

`fetch` **不抛异常表示「这篇没拿到」**。拿不到是常态，而每一种的处置完全不同：

| reason | 该怎么办 |
|---|---|
| `captcha` | 人去那个浏览器点一下，**然后整批都会顺**（所以该停下来叫人，不是跳过） |
| `no_access` | 这本刊没订 —— 跳过，重试没用 |
| `no_pdf_link` | 这家出版商页面改版了 —— 记下来，回头改本文件的选择器 |
| `not_pdf` | 被挡回登录/验证页 —— 多半 `captcha` 的变种 |
| `too_big` | 超过 `MAX_PDF_BYTES`，多半点到了「整期合订本」 |
| `navigate_failed` | 页面打不开 —— 网络或 DOI 本身的问题 |

真正抛异常的只有「环境不对」：`PlaywrightMissing`（没装）、
`BrowserUnavailable`（浏览器没开或没带调试口）。**这两种是人要去做一件事，
不是这篇跳过就好** —— 分开的意义全在这里。

## 页面选择器为什么住在这里

`_JS_STATE` 里那串选择器描述的是「出版商网站长什么样」。出版商改版就只改这一个文件，
工具层一行不动。这正是 adapters 这一环的全部理由。

顺序是有讲究的：`meta[name="citation_pdf_url"]` 排第一（Wiley/Springer/ACS/RSC
普遍支持的标准），Elsevier 那几个 `pdfft` / `download-link` 排后面（它不发那个 meta）。

## 自测

`python shared/adapters/pdf_fetch/selftest.py` —— **纯离线**，只验不碰浏览器也成立的部分。
浏览器那半只能在真机上验：`python -m tools.getpdf --probe`。
