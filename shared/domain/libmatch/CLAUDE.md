# libmatch · 这篇跟我的库是什么关系

> 你可能是被单独选中这个文件夹打开的，看不到项目其他部分。本文件是你的全部上下文。

## 这是什么

**一个原子模块**，住在 `shared/domain/`（纯逻辑层）。

找文献时最先要回答的从来不是「有哪些文献」，而是**「这篇我是不是早就有了」**。
这块就是那个判断，**只有判断，没有取数**。

用户是材料方向研究者（聚硼硅氧烷 / 动态键弹性体），**不懂编程**。
技术决策你自己拿主意，跟他汇报用通俗表述。

## 职责

- 标题归一、余弦相似度、字符重合度、标注「库里有没有」
- 判重与相关性的两个阈值（`DUP_SIM` / `STRONG_SIM`）住在这里，因为它们是
  **我们自己的口径**，不是外部世界的事实

## 它不做什么（都是刻意的）

- **不去取「我库里有哪些」** —— 那要联网，是 `shared/adapters/zotero_client.library_index()` 的活。
  本模块只接收调用方传进来的两个集合。
- **不向量化** —— 那是 `shared/adapters/embed` 的活。本模块只做「两个向量给我，我告诉你像不像」。
- **不知道文件放在哪** —— `domain` 层不许 import `shared.kernel.paths`（硬规则 3）。

## 对外接口

| 函数 | 说明 |
|---|---|
| `norm_title(t)` | 标题归一：去标点、空白、大小写 |
| `cosine(a, b)` | 余弦相似度；维度不一致或全零返回 0，不抛异常 |
| `char_overlap(a, b)` | 字符级重合度，做「标题也像吗」的二次确认 |
| `mark_have(papers, have_titles, have_dois)` | 就地标注 `in_library`，返回命中篇数 |
| `DUP_SIM` / `STRONG_SIM` | 判重阈值 / 强相关阈值 |

## 谁在用它

- `tools/discover` —— 系统性铺一遍（判重 + 排序前的对照）
- `tools/litsearch` —— 对抗式检索取原料（标「这篇我有没有」）

**两个使用者是它有资格住在 `shared/` 的原因**（下沉规则：≥2 个使用者）。
哪天只剩一个使用者了，就该搬回那个工具里去。

## 为什么「宁可多标一篇有」

`mark_have` 两条腿任一命中就算「有」。这是刻意放宽的：
多标一篇让人去核实，代价是看一眼；漏标一篇会让人重复下载、重复精读，
**精读是要花钱的**。两种错的代价不对称，所以偏向前者。
