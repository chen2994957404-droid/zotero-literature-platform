# getpdf 踩过的坑

## 1 · 付费文献下不来，以为是权限，其实是运输方式（2026-09-04）

**现象**：旧项目 `AutoPAPER-SCU` 用 `requests` 带机构 cookie 下载，
开放获取的都成功，付费的一篇都拿不到。当时归因于「学校没订」或「登录态不对」。

**根因**：出版商的反爬看的是真实浏览器指纹，`requests` 过不去。
跟订阅权限完全无关 —— 同一台机器、同一个 IP，用浏览器打开就有 View PDF。

**解法**：不自己发 HTTP，接管一个已经开着的真实浏览器（CDP）。

**判据留给以后**：拿回来的东西不是 PDF（`not_pdf`）时，先别怀疑权限，
先看是不是被反爬挡了 —— 这两种从返回码上分不出来。

## 2 · 必须借「主人平时用的那个」浏览器，不能新开一个（2026-09-04）

**现象**：新开一个干净 profile 的浏览器，一样被人机验证拦住。

**根因**：人机验证的通行证是**跟着浏览器 profile 走的**，而且是「进门验一次」——
人工过一次之后，同一个浏览器里后续文章都顺，新 profile 没有这张票。

**解法**：连一个人已经在里面点过验证的浏览器 —— 专开一个 profile、人工过一次、之后一直留着，比抢日常浏览器省心。这也意味着**无人值守跑不通** ——
撞上验证得有人去点。所以 `fetch_many` 撞上 `captcha` 是**停**不是跳过。

## 3 · 调试口别用惯例的 9222（2026-09-04，全局记为踩坑 #112）

**现象**：运行端上 `connect_over_cdp('http://127.0.0.1:9222')` 报
`Unexpected status 404 ... This does not look like a DevTools server`。

**根因**：9222 被一个**普通** Chrome 进程占着 —— 它的命令行里根本没有
`--remote-debugging-port`（多半是某个扩展在监听），对所有 DevTools 路径回 404。
更阴的是新起的浏览器**抢不到这个口会静默失败**，于是永远连不上，
排查方向很容易跑偏到代码上。

**解法**：默认口改成 **9333**（`pdf_fetch.DEFAULT_CDP`），
需要时用配置项 `BROWSER_CDP_URL` 覆盖。

**判据**：连不上时先看**占口进程的命令行里有没有 `--remote-debugging-port`** ——
有监听 ≠ 有调试口。

## 4 · SI 冒充正文，而且每项检查都过（2026-09-05，全局记为踩坑 #115）

**现象**：Wiley 那篇报「拿到了」，`%PDF` 开头、9 页、`fitz` 打得开 —— 全过。
第一页文字才露馅：`Supporting Information for Adv…`。

**根因**：取字节写成了「先把所有候选直取一遍，再把所有候选导航一遍」。
补充材料是直链 PDF，直取就成；正文被阅读器包了一层，直取拿到 HTML。
于是**排在后面的差候选赢了**。

**解法**：一个候选走完全部办法再换下一个；候选阶段就滤掉 SI 链接。

**验收纪律**：下载类功能**必须看内容**（`fitz` 打开看第一页文字），
不能只看「文件下来了、格式对、大小正常」—— 这三样全对的时候它照样是错的。

## 5 · 出版商的「PDF 链接」有三种花样（2026-09-05，全局记为踩坑 #116）

| 出版商 | 那个链接实际是什么 | 解法 |
|---|---|---|
| RSC | 就是 PDF | 直取 |
| Elsevier | HTML 中转页 → 自跳校验 → 签名直链 | 导航过去再同源取 |
| Wiley | 自家阅读器页面，真身在 iframe 里 | 把嵌着的东西也当候选 |

所以 `fetch()` 对每个候选依次试三招：直取 → 导航后同源取 → 把页面里嵌的东西入队。
