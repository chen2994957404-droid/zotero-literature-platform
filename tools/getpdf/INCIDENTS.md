# getpdf 踩过的坑

## 1 · 付费文献下不来，以为是权限，其实是运输方式（2026-09-04）

**现象**：旧项目 `AutoPAPER-SCU` 用 `requests` 带机构 cookie 下载，
开放获取的都成功，付费的一篇都拿不到。当时归因于「学校没订」或「登录态不对」。

**根因**：出版商的反爬看的是真实浏览器指纹，`requests` 过不去。
跟订阅权限完全无关 —— 同一台机器、同一个 IP，用浏览器打开就有 View PDF。

**解法**：不自己发 HTTP，接管一个已经开着的真实浏览器（CDP）。

**判据留给以后**：拿回来的东西不是 PDF（`not_pdf`）时，先别怀疑权限，
先看是不是被反爬挡了 —— 这两种从返回码上分不出来。

## 2 · 必须借「主人平时用的那个」浏览器，不能新开一个（2026-09-04）

**现象**：新开一个干净 profile 的浏览器，一样被人机验证拦住。

**根因**：人机验证的通行证是**跟着浏览器 profile 走的**，而且是「进门验一次」——
人工过一次之后，同一个浏览器里后续文章都顺，新 profile 没有这张票。

**解法**：连一个人已经在里面点过验证的浏览器 —— 专开一个 profile、人工过一次、之后一直留着，比抢日常浏览器省心。这也意味着**无人值守跑不通** ——
撞上验证得有人去点。所以 `fetch_many` 撞上 `captcha` 是**停**不是跳过。

## 3 · 调试口别用惯例的 9222（2026-09-04，全局记为踩坑 #112）

**现象**：运行端上 `connect_over_cdp('http://127.0.0.1:9222')` 报
`Unexpected status 404 ... This does not look like a DevTools server`。

**根因**：9222 被一个**普通** Chrome 进程占着 —— 它的命令行里根本没有
`--remote-debugging-port`（多半是某个扩展在监听），对所有 DevTools 路径回 404。
更阴的是新起的浏览器**抢不到这个口会静默失败**，于是永远连不上，
排查方向很容易跑偏到代码上。

**解法**：默认口改成 **9333**（`pdf_fetch.DEFAULT_CDP`），
需要时用配置项 `BROWSER_CDP_URL` 覆盖。

**判据**：连不上时先看**占口进程的命令行里有没有 `--remote-debugging-port`** ——
有监听 ≠ 有调试口。

## 4 · SI 冒充正文，而且每项检查都过（2026-09-05，全局记为踩坑 #115）

**现象**：Wiley 那篇报「拿到了」，`%PDF` 开头、9 页、`fitz` 打得开 —— 全过。
第一页文字才露馅：`Supporting Information for Adv…`。

**根因**：取字节写成了「先把所有候选直取一遍，再把所有候选导航一遍」。
补充材料是直链 PDF，直取就成；正文被阅读器包了一层，直取拿到 HTML。
于是**排在后面的差候选赢了**。

**解法**：一个候选走完全部办法再换下一个；候选阶段就滤掉 SI 链接。

**验收纪律**：下载类功能**必须看内容**（`fitz` 打开看第一页文字），
不能只看「文件下来了、格式对、大小正常」—— 这三样全对的时候它照样是错的。

## 5 · 出版商的「PDF 链接」有三种花样（2026-09-05，全局记为踩坑 #116）

| 出版商 | 那个链接实际是什么 | 解法 |
|---|---|---|
| RSC | 就是 PDF | 直取 |
| Elsevier | HTML 中转页 → 自跳校验 → 签名直链 | 导航过去再同源取 |
| Wiley | 自家阅读器页面，真身在 iframe 里 | 把嵌着的东西也当候选 |

所以 `fetch()` 对每个候选依次试三招：直取 → 导航后同源取 → 把页面里嵌的东西入队。

## 6 · 用 Zotero API 的 `q` 搜索查重，连建了三个重复条目（2026-09-05）

**现象**：同一个 DOI 连续 `stash` 三次，库里出现三条一模一样的记录。

**根因**两个叠在一起：
- `q=<doi>&qmode=everything` **不是按字段精确匹配**
- 它的索引**查不到刚写进去的东西**，所以第二次调用时第一次建的那条还「不存在」

**解法**：改成一次取回**全库 DOI → key 的索引**，整批复用；建完一条就顺手更新索引，
这样**同一批里的重复**也当场认得出来。

**教训**：**不准的查重比没有查重更糟** —— 它会让人以为重复问题已经解决了，
于是没人再检查，直到库里攒了一堆只能人工合并的重复条目
（Zotero 里删重复会丢掉那一份的合集和标签，只能合并）。

## 7 · 守卫盯字面而不是盯行为，把自己的注释判红了（2026-09-05）

**现象**：给上面那条加守卫时，写成「源码里不许出现 `qmode=everything`」，
结果匹配到了 `doi_index` 文档字符串里那句**「别用 q 搜索」的警告**，自测直接变红。

**解法**：改成检查**正面行为** —— 有没有 `def doi_index` 和 `index.get(`。

**教训**：判据要盯行为，别盯字面。盯字面的守卫会逼得人不敢在代码里写解释，
而解释正是这些坑最值钱的部分。

## 8 · 附件传上去了，用户点开却「找不到附件」（2026-09-05，全局记为踩坑 #120）

**现象**：`--to-zotero` 报成功，条目也建好了，用户在 Zotero 里点开附件：
> 在此路径无法找到附件：`D:\date\ZoteroData\storage\Z3665WSC	est.pdf`

点「检索」也找不到。查盘：那个文件夹**根本不存在**。

**根因**：`upload_attachment` 传的是 **Zotero 官方存储**，
而用户的文件同步配的是 **WebDAV（坚果云）** —— 桌面端只去 WebDAV 找文件，
官方存储里那份它压根不看。

**解法**：上传之后再调一次 `zotero_client.put_local(att_key, src)`，
把文件铺进本地 storage。

**最气人的地方**：**这个坑平台早就踩过、也早就解决了** ——
`tools/deepread/batch.py` 里那个 `_put_local` 的注释白纸黑字写着
「把产物铺进 Zotero 本地 storage —— 用户点开即最新」，
旁边还有「按它写，用户点开附件才不会『找不到文件』（si_batch 的老教训）」。
我写 `getpdf` 时没看那份代码，于是**同一个坑在第二个工具里又踩了一遍**。

已按下沉规则把 `put_local` 搬进 `shared.adapters.zotero_client`，
两个使用者共用一份，并加了守卫：源码里 `upload_attachment(` 之后必须有 `put_local(`。

**判据留给以后**：要给一个成熟系统加新工具时，**先看已有工具在同一件事上是怎么做的**。
「我这块是新写的」不是重踩老坑的理由 —— 老坑的解法往往就写在隔壁文件的注释里。

## 9 · SI 要按「类型」挑，不能按「顺序」取第一个（2026-09-06）

**做之前先去真实页面上看了**，三家的 SI 清单长这样：

| 出版商 | 挂了什么 |
|---|---|
| Elsevier | `mmc1.docx`(12MB) · `mmc2.mp4`(7MB) · `mmc3.mp4`(10MB) |
| Wiley | `...sup-0001-SuppMat.pdf` · `...sup-0001-**MovieS1**.mp4` |
| ACS | 文章页不列文件，只给一个 `/doi/suppl/<doi>` 入口 |

**「取第一个」在前两家碰巧对，但对的原因是「视频排在后面」**，不是规则本身可靠：
Wiley 那两个的**编号都是 `sup-0001`**，按序号排根本分不开。
而且它的 URL 是 `downloadSupplement?...`，**扩展名只出现在链接文字里** ——
只看 URL 会两个都认不出来。

**解法**：URL 和链接文字**合起来看**，按类型挑（要 pdf/docx，排除 mp4 之类），
同档保持页面原顺序。ACS 单独多跳一层。

**判据留给以后**：一条规则「碰巧对」的时候，要问清楚**它为什么对** ——
如果对的原因是数据恰好这么排，那它随时会错。

## 10 · ACS 的 SI 暂时取不到（2026-09-06，**别再重试同样的办法**）

**现状**：`--with-si` 对 Elsevier、Wiley 有效，**对 ACS 报 `no_si`**。
ACS 是用户最大的来源（85 篇），所以这条缺口是真的疼，但目前无解。

**已经试过、都不行的**（写下来是为了不重复浪费时间）：

| 试法 | 结果 |
|---|---|
| 文章页上找 SI 文件链接 | 只有一个 `?goto=supporting-info` 的**锚点**，不是文件 |
| 进 `/doi/suppl/<doi>` 二级页 | **重定向回文章页**，没有文件列表 |
| 在页面源码里搜 `suppl_file` | **0 个命中**（源码 127 万字符，搜过） |
| 点页面上的「Supporting Information」 | 点不动（30 秒超时） |
| 按老规则拼直链 `/suppl_file/ma6c01758_si_001.pdf` | **软 404** —— 三个猜测全返回同一个 391779 字节的 HTML |

**根因**：ACS 换到了 Silverchair 平台（页面里能看到 `acs.silverchair-cdn.com`），
老的 SI URL 规则连同页面结构一起废了。用户库里那些 ACS 的 SI
（`ma5c00784_si_001.pdf` 之类）是**老平台时期**拿到的。

**当前行为是安全的**：`pick_si` 认出那个锚点不是文件，直接报 `no_si`，
**不会把 391 KB 的 HTML 当成 SI 下回来**。宁可说「没有」，也不下错。

**要翻案先确认**：ACS 页面上是否又出现了可点的 SI 文件链接。
在那之前，ACS 的 SI 只能靠 Zotero Connector 手动存。
