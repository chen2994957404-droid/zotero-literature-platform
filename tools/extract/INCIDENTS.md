## 踩坑 #138：`--stale --list` 不存在，于是它直接走进了全库抽取那条路（2026-09-07）

**现象**：照 `docs/待办与需求.md` 里写的清单命令在 B 机上跑
`python -m tools.extract --stale --list`，本以为只是列个清单，
输出却是 `[1/53] ... [53/53]`、末尾 `完成：本次 42 篇` —— 它跑的是**全库抽取**。

**根因**：`tools/extract/cli.py` 里**根本没有 `--stale` 这个开关**，
`--list` 也只在 `--upgrade-local` 与 `--si-pending` 两个分支里被认。
两个参数都没人认领 → 落到最后的 else → `keys = paths.all_keys()` → 全库作业。
`shared.kernel.cli` 的红线原话就是这个病：
**「没人认识的参数会被当成『没给参数』，于是走进最贵那条路」**（踩坑 #85 是 `--help` 触发全库抽取）。

**这次为什么没花钱**：库里那 42 篇早就是 schema v3，逐篇都被
「已抽过（schema v3），不重抽」跳过，一次模型都没调。
实测佐证：最近 30 分钟被改写的 `structured/*.json` = 0，新建备份目录 = 0。
**换成真有一批过期记录，这条『看起来只是列清单』的命令就会闷头花掉一整轮的钱。**

**解法（待做，见待办）**：
1. 未知参数一律拒绝并打印用法 —— 别再让「不认识」等价于「跑最贵那条」。
2. `--list` 提升成全局开关：任何分支下都只列不做。
3. 把 `--stale` 真的做出来（待办里那句 `jobs.stale('extract', schema_ver=N)` 是对的，只是没接到命令行上）。

**教训**：文档里写给下一个人的命令，**必须真的跑过一次**。
这条命令写进待办时没人跑过，于是它在文档里躺了一天，等着谁去踩。


## 踩坑 #141：比武台说 1b 够用，真跑全篇时它 79% 的答案被判掉（2026-09-08）

**背景**：施工图（`docs/待办与需求.md` 的「脚本优先的抽取流水线」）里有一条结论 ——
> 「0.8 GB 模型 + 脚本校验 ≈ 云端质量、零成本」

依据是 `bench_chunk` 的 8 段比武：`gemma3:1b` 抽 40 条、接地 94%、样品合法 80%。

**真实全篇跑下来不是这样**（5 篇 49 段，`chunk_pass --all --limit 5 --model gemma3:1b`）：

| | 留下 | 判掉 |
|---|---|---|
| 5 篇合计 | **30 条** | **118 条**（判掉率 79%）|
| 其中 2 篇 | **0 条** | 全军覆没 |

同一篇（2T6H4S3D，13 段）换云端 `deepseek-v4-flash`：**留下 34 条、判掉 0 条**，
14 秒跑完（1b 用了 40 秒）。**云端不是贵一点好一点，是三倍产出且零废品，还更快。**

**为什么比武台会骗人**：8 段是**人挑的**样本，而且只统计「抽出来的条数与接地率」，
没统计**判掉率**。真实全篇里有大量「这段其实没有可抽的数」的段落 ——
1b 会硬答（编数字、编样品名），脚本把它们判掉；比武台的指标看不见这一类。

**教训**：
1. **比武台的样本要跟真实作业同分布**，人挑的 8 段不算。
2. **判掉率必须是比武指标之一** —— 它衡量的是「模型在没答案时会不会闭嘴」，
   而这正是小模型最差的那一项。
3. 结论写进施工图时**要标清楚它的证据是几段、什么样本**，
   否则下一个人（就是我）会照着它把全库跑成废品。

**代价**：这次只白花了 5 篇的本地算力（不花钱），因为先跑了 5 篇而不是 42 篇。
**先跑小样再全库，这条纪律今天救了一次。**


## 踩坑 #142：金标一上线，三个模型一起漏掉整整一篇（2026-09-08）

**背景**：建了正文数值抽取的人工金标（3 篇、22 条 core、18 条 negative），
第一次拿它量 `gemma3:1b` / `phi4-mini` / `deepseek-v4-flash`。

**结果**（召回 / 准确 / 错标 / 硬错误）：

| 模型 | CL2HILJ9 | VHJI4A32 | P2Q5TYFR |
|---|---|---|---|
| `gemma3:1b` | 0% / 6% / — / **3** | 0% / 0% / — / 1 | **0% / — / — / 0** |
| `phi4-mini` | 50% / — / 25% / **2** | 50% / 42% / 50% / 2 | **0% / 0% / — / 2** |
| `deepseek-v4-flash` | 50% / 100% / 25% / 0 | 0% / 31% / **100%** / 0 | **0% / 0% / — / 2** |

**三个模型在 P2Q5TYFR 上全军覆没（0/4）——那不是模型的问题。**
那篇的核心数值是 `$10^{-10}$ M`、`>40 000 g/mol`、`-23 mV`：

1. **科学计数法与 LaTeX**：`10^{-10}` 经我们的接地校验一比对必然失败（校验只去空格和逗号），
   模型答对了也会被当成「编的数字」判掉。
2. **千分位空格**：`40 000 g/mol` 同理。

**第二个发现：性能名归一缺位。** 同一个 243 kPa：
云端标 `g_e,exp`（原文里的符号），phi4-mini 标 `storage modulus`，金标写 `plateau elastic modulus`。
第一个其实是对的、第二个是错的（G′ 不等于平台模量），**但我的评分器把两者都算成错标** ——
`PROPERTY_ALIASES` 里没有 `Ge,exp` 这类论文符号名。**尺子也需要被校准。**

**第三个发现：硬错误真实存在，且旧指标完全看不见。**
1b 把引言里 Yang 等人的 `797.4 MPa`、`73.6 MPa` 挂到了本文样品上；
phi4-mini 与云端都把 DFT 算出来的键角 `137.45°`、键长 `1.36 Å` 当成了性能。
**这些数字确实印在这篇 PDF 上，所以接地率对它们全部满分。**

**教训**：金标的第一价值不是「给模型排名」，是**照出流水线自身的洞** ——
三个模型一起零分的地方，八成是我们自己的路断了，不是它们同时变笨了。
