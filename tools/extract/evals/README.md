# extract 的评测

**回答的问题：抽出来的字段对不对、全不全？**（体检回答的是「能不能跑」，那是两件事。）

## 现状：**理解那一半填好了**（2026-09-01）

`golden/records.json` 里 23 条金标，验的是抽完之后那套**确定性的理解**：
是不是综述、属于哪一档、哪些字段算「有值」、性能字符串怎么拆成能比大小的数。
全离线、不花钱、默认就跑。

为什么这一半也值得验：**对比表和查询库的正确性全建在它们上面**。
档次判错，用户就分不清空格是「本来就没有」还是「粗层没抽到」——
对比表的价值当场归零。

**还缺的那一半**：「模型抽得准不准」要拿几篇**人工核对过**的真实
`structured/<KEY>.json` 当金标，人工核对得你来做，比对还要花钱重抽一遍。

## 该怎么填

有值率（`schema.coverage`）与「对照原文有没有漏抽/幻觉」（`evaluate()` 已有自检）。天然的金标：几篇已人工核对过的 `structured/<KEY>.json`。

## 三样东西各放什么

| 位置 | 放什么 |
|---|---|
| `golden/` | 金标输入 + 期望产出（一个案例一个文件，文件名说清它验的是什么）|
| `scorers/` | 评分器：**纯函数**，拿到产出就能打分，不需要联网也不需要真实数据 |
| `thresholds.toml` | 阈值的唯一出处 —— 别在 .py 里再写一遍数字 |

跑评测的测试写在 `../tests/` 里（`tools/extract/tests/test_evals.py`），
参照 `tools/deepread/tests/test_evals.py` 的写法。
