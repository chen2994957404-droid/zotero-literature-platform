# discover 的评测

**回答的问题：找回来的文献跟用户到底相不相关？**（体检回答的是「能不能跑」，那是两件事。）

## 现状：**排序那一半填好了**（2026-09-01）

`golden/ranking.json` 里 12 条金标，验的是**排序规则本身** ——
尤其是踩坑 #38「雪球一开就被高被引通用文献带偏」的解药：
相关度权重压过被引，被引还开了方压缩。不钉住的话，以后有人觉得
「被引权重是不是太低了」顺手一调，找文献就退化成按热度排序，
**而且不会报错**。

**还缺的那一半**：真正的召回质量该用天然金标验 —— 用户后来实际导入了哪几篇。
那份数据只有主力机上有（A 机是测试账号）。

## 该怎么填

拿库里已有的一批文献当种子，看能不能把「他真的会收进库」的那些排到前面。天然金标：他后来实际导入了哪些。

## 三样东西各放什么

| 位置 | 放什么 |
|---|---|
| `golden/` | 金标输入 + 期望产出（一个案例一个文件，文件名说清它验的是什么）|
| `scorers/` | 评分器：**纯函数**，拿到产出就能打分，不需要联网也不需要真实数据 |
| `thresholds.toml` | 阈值的唯一出处 —— 别在 .py 里再写一遍数字 |

跑评测的测试写在 `../tests/` 里（`tools/discover/tests/test_evals.py`），
参照 `tools/deepread/tests/test_evals.py` 的写法。
